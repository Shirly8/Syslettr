Service Discovery System

Service discovery looks simple — services need to find each other — but the hard part is maintaining a consistent, live view of the fleet while tolerating network partitions and node failures without causing cascading outages. Interviewers use it to probe your understanding of distributed consensus, CAP tradeoffs, and how control-plane failures affect data-plane traffic.

Interview

Interviewer
We need to build a service discovery system for a microservices platform. Services spin up and down constantly, and clients need to know which instances are healthy. Where do you start?
You
Before I design anything — what's the scale? Hundreds of services with a few instances each, or thousands of services with thousands of instances? And is client-side load balancing expected, or does a central proxy handle routing? Also, what's our SLA for stale data — can clients briefly talk to a dead instance, or is correctness critical?
Interviewer
Assume 5,000 distinct services, each with 10–500 instances, so roughly 500K total service instances. Clients do their own load balancing. We want health check failures reflected within 10 seconds, and the registry itself must stay available even if some registry nodes die.
You
Got it — 500K instances, each sending a heartbeat (a periodic 'I'm alive' signal) every 5 seconds, that's ~100K heartbeat writes per second. Reads are heavier: assume 1,000 services each making 50 lookups/sec, so ~50K reads/sec. The 'available even if nodes die' requirement means we favor AP (availability + partition tolerance over strong consistency) in CAP terms, so I'll accept brief staleness over downtime. I'll design around a gossip-based registry with a local cache on each client.

Core Components

Interviewer"How does the registry actually store and replicate instance data across its own nodes?"
Service Registry (Control Plane)
  • WHY: Without a shared, replicated source of truth for which instances exist and are healthy, clients have no authoritative place to query — every lookup becomes a guess.
  • I'll run the registry as a cluster of 5–7 nodes using Raft consensus (a leader-election protocol where one node coordinates writes and replicates to a quorum before confirming). Each write — a registration or deregistration event — goes to the leader, which replicates to a majority before acknowledging. Reads can be served by any node from its local state with a version number attached so clients can detect staleness.
  • TRADEOFF: Raft gives strong consistency for writes, but leader failover takes 150–300ms, so during an election window, writes are blocked — registrations stall but existing reads still work from follower state.
Interviewer"How do you detect a dead instance quickly without overwhelming the registry with false positives from transient network blips?"
Health Check Subsystem
  • WHY: Without active health checking, the registry fills with stale dead instances and clients get connection errors, defeating the whole point of discovery.
  • Each service instance sends a heartbeat to the registry every 5 seconds. The registry marks an instance 'unhealthy' only after missing 3 consecutive heartbeats (15 seconds), giving a buffer for transient delays. Additionally, I'll run sidecar health checkers (lightweight agents co-located with each instance) that do active TCP or HTTP probes every 3 seconds and can immediately flag an instance down without waiting for a missed heartbeat cycle — this cuts detection to under 10 seconds as required.
  • TRADEOFF: Aggressive health checking adds ~50K probe connections/sec cluster-wide; sidecar agents consume ~50MB RAM per host, which is a real cost at this scale.
Interviewer"If every client polls the registry for every lookup, won't the registry get hammered at this scale?"
Client-Side Cache & SDK
  • WHY: At 50K lookups/sec across thousands of clients hitting a 7-node registry directly, each registry node would handle ~7K QPS of reads — fine at rest, but any spike would cascade into discovery failures.
  • The client SDK maintains a local in-memory cache of the service instance list for each dependency. On startup it fetches the full list and subscribes to a delta-push stream (long-poll or server-sent events from the registry) so updates are pushed rather than polled. Cache TTL (time-to-live, how long before forcing a refresh) is set to 30 seconds as a fallback, but in practice the push stream keeps it current within 5 seconds of any change.
  • TRADEOFF: The local cache means clients briefly route to dead instances between a failure and the push notification arriving — the 10-second health-check detection window defines the worst-case stale window.
Interviewer"Some teams prefer DNS for discovery — should we support that, and how does it fit?"
DNS-Based Discovery Layer
  • WHY: Many legacy services and infrastructure components (databases, load balancers) use DNS for service resolution and can't easily be retrofitted with an SDK.
  • I'll run a custom DNS resolver that the registry keeps in sync — whenever the registry marks an instance healthy or unhealthy, it updates the DNS A records for that service's name (e.g., `payments.internal`) within 5 seconds using a TTL of 5 seconds on the DNS record. This way, DNS-native clients get reasonably fresh data without needing SDK changes. The registry pushes diffs to the DNS server rather than the DNS server polling, keeping propagation fast.
  • TRADEOFF: DNS caching at the OS and resolver level (negative caching of failed lookups especially) can mean some clients see stale endpoints for 30–60 seconds regardless of what we do at the registry level.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1100K heartbeats/sec write directly to the Raft leader causes write amplification — the leader must replicate every heartbeat to followers, creating a fan-out that saturates the leader's network and slows consensus for real registration events.
Fix: I'll introduce a heartbeat aggregation tier (a stateless layer of nodes) that batches heartbeats from hundreds of instances over a 1-second window and writes a single aggregated 'these N instances are alive' record to the registry instead of N individual writes. This collapses 100K writes/sec into roughly 500–1,000 batch writes/sec to the Raft leader. The aggregation nodes are stateless and horizontally scalable behind a load balancer.
Tradeoff: Batching adds up to 1 second of additional latency before a missed heartbeat is reported, slightly widening the detection window from 15 to 16 seconds in the worst case.
2During a registry leader election (lasting 150–300ms), all new registrations and deregistrations are blocked — services that scale up mid-election are invisible to clients until the new leader is elected.
Fix: I'll make newly started service instances retry registration with exponential backoff (doubling delay on each retry: 100ms, 200ms, 400ms…) and keep broadcasting heartbeats to all registry nodes, not just the leader. Follower nodes queue incoming registrations during the election window and replay them to the new leader once elected. This is a local buffer (in-memory, discarded if the follower crashes) so it's not durable, but elections are rare enough that losing a registration in a crash during a 300ms window is acceptable.
Tradeoff: In the rare case a follower crashes during an election while holding queued registrations, those service instances must re-register, adding ~1 second of discovery delay on startup.
3A thundering herd (mass simultaneous re-registration) after a network partition heals can spike the leader's write rate 10–50x above normal as thousands of instances reconnect at once.
Fix: When a service instance detects it has lost connectivity to the registry for more than its heartbeat interval, it re-registers with a randomized jitter delay (random wait of 0–5 seconds) before reconnecting. The aggregation tier I already described also absorbs a lot of this spike naturally. At the API gateway layer I'll enforce a per-IP rate limit on registration endpoints so a single misbehaving fleet can't DDoS the registry.
Tradeoff: Jitter means some instances won't be visible to clients for up to 5 seconds after a partition heals, but this is acceptable compared to a full registry brownout.

Reference

API
POST/api/v1/services/{service_name}/instances— Register a new instance; body includes host, port, metadata tags; returns instance_id and heartbeat_interval_seconds
PUT/api/v1/services/{service_name}/instances/{instance_id}/heartbeat— Renew heartbeat for an existing instance; returns 200 OK or 410 Gone if instance was deregistered
DELETE/api/v1/services/{service_name}/instances/{instance_id}— Graceful deregistration; immediately marks instance unhealthy and removes from active pool
GET/api/v1/services/{service_name}/instances— Returns list of healthy instances with host, port, metadata; supports ?version= for delta polling
GET/api/v1/services/{service_name}/instances/stream— Long-lived SSE stream pushing delta events (REGISTERED, DEREGISTERED, HEALTH_CHANGED) as they occur
Database & Storage
  • Embedded Raft log store (e.g. custom WAL — write-ahead log, a crash-safe append-only file) — each registry node persists its log locally; no external DB needed for the registry state itself.
  • instances(instance_id VARCHAR(36) PK, service_name VARCHAR(128), host VARCHAR(64), port INT, status ENUM('healthy','unhealthy'), metadata JSONB, last_heartbeat BIGINT, registered_at BIGINT)
  • Index on (service_name, status) — the dominant query is 'give me all healthy instances of service X'; composite index makes this O(log n) not a full scan.
  • JSONB metadata is flexible for tags (region, version, canary flags) but unindexed by default — querying by metadata tag requires a full service scan, so keep tag filtering client-side after fetching the instance list.
