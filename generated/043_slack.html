Systems Design · Tier 2

Slack

Slack looks like a simple chat app until you realize a single message can fan out to thousands of connected WebSocket clients simultaneously, and every user expects sub-200ms delivery. Interviewers use it to probe real-time infrastructure, fan-out strategies, and the tension between read scalability and write amplification.

Interview

Interviewer
Design Slack — the workplace messaging platform. Where do you want to start?
You
Before diving in — what's the scale? How many daily active users and roughly how many messages per day? And should I cover just channel messaging, or also DMs, search, and file uploads?
Interviewer
Assume 10 million DAUs, around 1 billion messages per day. Focus on real-time channel messaging and DMs. Search and file uploads are out of scope today.
You
So roughly 11,500 messages per second at peak (1B / 86,400s, then 2x for spikes). Each message fans out to an average of 20 subscribers — that's 230K WebSocket pushes per second. I'll plan for persistent connections (long-lived WebSocket sessions kept open per client), a fan-out (broadcasting one write to many recipients) pipeline that doesn't block the sender, and eventually-consistent delivery with at-least-once guarantees. Storage: ~1KB per message × 1B/day × 5 years ≈ 1.8PB, so I'll tier hot data in a fast DB and archive cold data.

Core Components

Interviewer"How do you manage millions of persistent WebSocket connections without running out of resources?"
WebSocket Gateway
  • WHY: HTTP is stateless and half-duplex — you can't push server-initiated messages without a persistent connection, so real-time delivery breaks.
  • HOW: I deploy a fleet of stateless gateway servers, each holding up to 100K open WebSocket connections (the OS file-descriptor limit is tuned to 200K per node). A client connects to any gateway; the gateway registers its presence in a distributed session store (Redis cluster) keyed by user_id → gateway_node_id. When a message needs delivery, the fan-out service looks up the target's gateway node and sends an internal RPC to push the frame.
  • TRADEOFF: Stateful connections mean gateway restarts drop active sessions — clients must reconnect and replay missed messages via a cursor.
Interviewer"Walk me through what happens between a user hitting send and the recipients seeing the message."
Message Fan-out Pipeline
  • WHY: Doing fan-out synchronously in the request path means sender latency grows linearly with channel size — a 10K-member channel would be unusable.
  • HOW: The API server writes the message to the message store and immediately publishes an event to a message queue (durable pub/sub — holds events until consumers ACK). A pool of fan-out workers consumes from the queue; each worker fetches the channel's online member list from Redis, groups recipients by their gateway node, and sends one batched RPC per gateway node rather than one RPC per user. The gateway then pushes frames over open WebSocket connections. Offline users get the message on next login via a cursor-based fetch.
  • TRADEOFF: Async fan-out introduces latency jitter — most users get sub-100ms delivery, but a slow worker could add hundreds of milliseconds.
Interviewer"Why Cassandra for messages, and how do you model the data?"
Message Storage (Cassandra)
  • WHY: Relational DBs can't handle the write throughput (11.5K writes/sec) or the petabyte-scale storage without massive sharding complexity.
  • HOW: Cassandra (a wide-column, distributed NoSQL store optimized for time-series writes) lets me model messages as rows partitioned by channel_id and clustered by message_id (a time-ordered UUID, so scans return messages in order without a sort). Each partition holds one channel's history. I keep the partition size manageable by bucketing: partition key = (channel_id, bucket) where bucket = month. Reads for recent messages hit one partition; older history crosses bucket boundaries.
  • TRADEOFF: Cassandra doesn't support cross-partition transactions, so features like editing across buckets require application-level logic.
Interviewer"How do you handle presence — knowing who's online — without hammering your infrastructure?"
Presence & Typing Indicators
  • WHY: Naively polling presence state for every channel member on every heartbeat produces O(members × channels) database reads — completely unscalable.
  • HOW: Each connected client sends a heartbeat every 5 seconds to its gateway. The gateway updates a Redis key (user_id → {gateway, last_seen, TTL=15s}) — the TTL (time-to-live, the key auto-expires after 15 seconds with no heartbeat) handles disconnects without explicit cleanup. Presence reads are served directly from Redis, not the DB. Typing indicators are ephemeral: the client fires a WebSocket event, the gateway fans it out via the same pipeline but we never persist it.
  • TRADEOFF: 15-second TTL means presence can lag by up to 15 seconds after a client crashes — acceptable for most use cases.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Large channels (10K+ members) cause fan-out workers to generate tens of thousands of gateway RPCs per message, saturating the internal network.
Fix: I switch to a pub/sub broadcast model for large channels. Each gateway subscribes to a Redis pub/sub channel keyed by workspace_id or large_channel_id. The fan-out worker publishes once to Redis; every gateway node receives the event and pushes only to its locally connected members. This reduces fan-out worker RPC count from O(members) to O(gateway_nodes), typically 50–200 nodes instead of 10K.
Tradeoff: Every gateway receives every large-channel message even if zero of its connected clients are members — slightly wasteful but far better than per-member RPCs.
2Hot partitions in Cassandra when a single viral channel receives thousands of writes per second, overwhelming one node.
Fix: I add a shard suffix to the partition key: partition = (channel_id, bucket, shard) where shard = message_id % N (default N=8). Writes spread across N Cassandra nodes. Reads for a channel page must query N partitions in parallel and merge-sort client-side, but with N=8 this is fast and the parallelism is cheap.
Tradeoff: Read logic is more complex — the application must scatter-gather (fan out a read to N partitions and merge results) instead of a single partition scan.
3The session store (Redis) becomes a single point of failure — if it goes down, fan-out workers can't locate any user's gateway node.
Fix: I run Redis in cluster mode (data sharded across 6 primary nodes with 6 replicas). Each shard owns 1/6 of the hash slots (segments of the key space). A node failure triggers automatic replica promotion in under 10 seconds. Fan-out workers connect via a cluster-aware client that re-routes requests after failover. I also cache the gateway→user mapping locally in each fan-out worker with a 2-second TTL so a brief Redis outage doesn't halt delivery.
Tradeoff: Cluster mode adds operational complexity and cross-slot operations (looking up multiple users in one call) require multi-key scatter, not a single command.

Reference

API
POST/api/v1/channels/{channel_id}/messages— Send a message; body: {text, attachments}; returns message_id, timestamp, and channel_id
GET/api/v1/channels/{channel_id}/messages?before={cursor}&limit=50— Paginated history fetch using cursor (message_id) for stable pagination; returns messages array + next_cursor
GET/api/v1/channels/{channel_id}/members/presence— Returns online/offline status map for all channel members, served from Redis
POST/api/v1/channels/{channel_id}/typing— Fire-and-forget typing indicator; no persistence, fan-out via WebSocket only
POST/api/v1/users/me/workspaces/{workspace_id}/channels/{channel_id}/ack— Mark channel as read up to message_id; updates last_read cursor for unread badge counts
GET/api/v1/ws/connect— WebSocket upgrade handshake; returns connection to assigned gateway node with auth token validation
Database & Storage
  • Cassandra — wide-column store optimized for high-throughput time-series writes and range scans by time; handles 1B+ messages/day and petabyte scale horizontally
  • Schema: messages((channel_id TEXT, bucket TEXT, shard INT) PK, message_id TIMEUUID CLUSTERING, sender_id TEXT, content TEXT, created_at TIMESTAMP) — composite partition key spreads hot channels
  • PostgreSQL — relational store for users, workspaces, channels, memberships, and ACLs (access-control lists — permissions rules); low write volume, complex joins needed
  • Schema: channels(channel_id UUID PK, workspace_id UUID FK, name TEXT, created_at TIMESTAMP) | memberships(user_id UUID, channel_id UUID, joined_at TIMESTAMP, last_read_message_id TIMEUUID)
  • Index strategy: Cassandra queries by (channel_id, bucket) then TIMEUUID range — no secondary indexes needed; PostgreSQL indexes on workspace_id and user_id FK columns for membership lookups
  • Redis key schema: session:{user_id} → {gateway_node, last_seen} with 15s TTL; presence is eventually consistent by design — not source of truth, just fast read layer
  • Key tradeoff: Cassandra's eventual consistency (replication_factor=3, quorum reads) means a just-sent message may not appear in a concurrent history read for up to ~100ms
