Webhook Delivery System

Webhook delivery looks simple — make an HTTP call when an event happens — but the hard part is guaranteeing delivery to external servers you don't control, which can be slow, flaky, or offline. Interviews use this system to test queue design, retry semantics, fan-out patterns, and observability under failure.

Interview

Interviewer
We want to build a webhook delivery system — something like what Stripe or GitHub uses to notify customers when events happen. Where would you start?
You
Before diving in — what's the event volume we're targeting? Thousands per second or millions? And are we delivering to one endpoint per event or potentially many subscribers per event? Also, what's the SLA — do we guarantee delivery at least once, or is best-effort acceptable?
Interviewer
Expect around 100,000 events per second at peak, with up to 50 subscribers per event. We need at least-once delivery with retries, and endpoints should receive events within 30 seconds under normal conditions.
You
So worst-case fan-out (sending the same event to multiple recipients) gives us up to 5 million HTTP calls per second — that's the number to design against. At-least-once delivery means I need a durable queue (a persistent log that survives crashes) and idempotency keys so subscribers can safely deduplicate. The 30-second SLA drives how aggressive my retry backoff can be before it counts as a failure. I'll assume endpoints can be slow or unavailable and design the retry path as a first-class concern, not an afterthought.

Core Components

Interviewer"How do you handle a sudden spike — say a customer triggers a million events in a second?"
Event Ingestion API
  • WHY: Without an ingestion buffer, a spike in upstream events would directly overwhelm the delivery workers and cause dropped events or cascading failures.
  • HOW: I expose a lightweight HTTP endpoint that validates the event payload, assigns a UUID and timestamp, then writes directly to a durable message queue (Kafka or similar append-only log). The API never calls subscriber endpoints — it just produces to the queue and returns 202 Accepted immediately. This decouples ingestion throughput from delivery speed.
  • TRADEOFF: Producers get async acknowledgment, so they can't know if delivery ultimately succeeds at write time — they need to track that separately.
Interviewer"How do you expand one event into potentially 50 delivery jobs without that expansion step becoming a bottleneck?"
Fan-out Worker
  • WHY: Without a dedicated fan-out step, you'd either block ingestion doing subscriber lookups or lose the mapping between events and their target endpoints.
  • HOW: A pool of fan-out workers consumes from the inbound event topic, queries a subscriptions store to find all active endpoints for that event type, and writes one delivery job per (event, endpoint) pair into a separate delivery queue. Each delivery job is a self-contained record — event payload, target URL, retry count, next_attempt timestamp. Workers are stateless and horizontally scalable.
  • TRADEOFF: If a subscriber has thousands of registered endpoints, fan-out amplifies queue depth significantly — you need per-tenant rate limits to prevent one customer from starving others.
Interviewer"What happens when the subscriber's endpoint is down for two hours — how do you handle retries without hammering a dead server?"
Delivery Worker + Retry Engine
  • WHY: Without a retry engine, any transient failure (slow endpoint, 503, timeout) results in permanent event loss, breaking the at-least-once guarantee.
  • HOW: Delivery workers pull jobs from the delivery queue and make the HTTP POST to the subscriber's endpoint. On failure (non-2xx or timeout), I write the job back to a delayed retry queue with exponential backoff (doubling the wait time each attempt: 10s, 20s, 40s…) up to a configured max (e.g., 72 hours). I track attempt count and last error on the job record. After the max attempts, the job moves to a dead-letter queue (DLQ — a holding area for permanently failed jobs) so the customer can inspect and replay.
  • TRADEOFF: Exponential backoff means late-arriving retries can pile up and create a thundering herd when a downed server comes back online — I'd add jitter (random delay offset) to spread them out.
Interviewer"Customers will want to see delivery history and debug failures — how do you build that without it becoming a write bottleneck?"
Delivery Log & Observability Store
  • WHY: Without a delivery log, customers have no visibility into whether their endpoints received events, and you can't debug failures or prove SLA compliance.
  • HOW: Every delivery attempt — success or failure — appends a record to an append-only log store (high write throughput, cheap sequential writes) with event ID, endpoint, HTTP status, response time, attempt number, and timestamp. I keep only the last 30 days hot and archive the rest to cold object storage. The customer-facing dashboard reads from this log, not from the delivery queue.
  • TRADEOFF: Append-only logs are fast to write but slow to query by arbitrary filters — I'd add a secondary index on (customer_id, event_id) to support the common lookup patterns.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A slow or unresponsive subscriber endpoint causes delivery workers to block on HTTP calls, starving all other subscribers sharing the same worker pool.
Fix: I partition the delivery queue by tenant (customer ID) and assign isolated worker pools per tenant bucket. A slow endpoint in tenant A can only exhaust its own worker allocation — it can't block tenant B. I also enforce a strict per-request timeout (e.g., 10 seconds) and use a circuit breaker (a pattern that stops sending requests to a failing endpoint after N consecutive failures, giving it time to recover) to avoid hammering a known-bad endpoint.
Tradeoff: Per-tenant partitioning increases operational complexity — you need dynamic scaling logic to redistribute worker capacity when tenants vary in traffic.
2When a failed endpoint recovers after hours of downtime, thousands of backed-up retry jobs fire simultaneously, creating a thundering herd that overwhelms it immediately.
Fix: I add jitter (a random delay added to the backoff interval, e.g. ±30% of the calculated wait) to spread retry attempts across a time window rather than synchronizing them. I also implement a circuit breaker per endpoint: after 5 consecutive failures it opens (stops sending) for a probe interval, then sends one test request — only if that succeeds does it close (resume full delivery).
Tradeoff: Circuit breakers add state that must be shared across worker instances — requires a lightweight distributed store (like a shared cache) to track open/closed state per endpoint.
3The delivery log becomes a write hotspot at 5M events/sec — a single append store can't absorb that volume and serve dashboard queries simultaneously.
Fix: I shard (split data across multiple DB machines) the delivery log by tenant ID so writes distribute across shards. Workers write to the log asynchronously via a small buffer — they don't wait for the log write to confirm delivery to the subscriber. For dashboard queries I serve from a read replica (a copy of the DB that only handles reads) with a short replication lag, keeping the write path clean.
Tradeoff: Async log writes mean a worker crash between HTTP delivery and log write creates a gap — the event was delivered but not recorded, which is a minor observability inconsistency but doesn't violate the at-least-once guarantee.

Reference

API
POST/api/v1/events— Ingests an event; validates payload, enqueues, returns 202 Accepted with event_id
POST/api/v1/subscriptions— Registers a webhook endpoint URL for a given event type; returns subscription_id
DELETE/api/v1/subscriptions/{subscription_id}— Removes a subscriber endpoint; stops future deliveries immediately
GET/api/v1/events/{event_id}/deliveries— Returns delivery attempt history for an event — status, timestamps, HTTP codes per endpoint
POST/api/v1/events/{event_id}/replay— Re-enqueues delivery for a specific event; used to recover from DLQ or customer-requested replay
GET/api/v1/subscriptions/{subscription_id}/health— Returns circuit breaker state and recent success/failure rate for an endpoint
Database & Storage
  • PostgreSQL — subscriptions registry; relational, low write volume, needs JOIN on (customer_id, event_type)
  • Schema: subscriptions(id UUID PK, customer_id UUID, event_type VARCHAR, endpoint_url TEXT, secret_key TEXT, active BOOL, created_at TIMESTAMP)
  • Schema: delivery_attempts(id UUID PK, event_id UUID, subscription_id UUID, attempt INT, status SMALLINT, response_ms INT, attempted_at TIMESTAMP)
  • Index: subscriptions(customer_id, event_type, active) — fan-out workers hit this on every event
  • Index: delivery_attempts(event_id, subscription_id) — covers dashboard query pattern
  • Tradeoff: delivery_attempts grows unboundedly — partition by month and drop partitions older than 30 days to control storage
  • Kafka — event queue and delivery queue; chosen for sequential writes (high throughput), durable replay, and per-partition consumer isolation
  • Redis — circuit breaker state per endpoint (open/closed/half-open) and per-tenant rate limit counters; in-memory, TTL-based, cheap reads
