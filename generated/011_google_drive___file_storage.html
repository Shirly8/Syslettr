Google Drive / File Storage

File storage sounds simple until you hit large files, concurrent edits, and cross-device sync — the consistency and delta-sync problems are genuinely hard. Interviewers use it to probe how candidates handle binary data pipelines, versioning, and storage cost at petabyte scale.

Interview

Interviewer
Design a Google Drive-like file storage system. Users should be able to upload, download, and sync files across devices. Where do you start?
You
Before diving in — what's the scale? Tens of millions of users or hundreds of millions? Are we supporting collaborative editing like Google Docs, or just upload/download/sync? And what's the max file size we need to handle?
Interviewer
500 million users, 200 million daily active. No real-time collaborative editing — just file sync. Max file size is 5 GB. Strong consistency on metadata, eventual consistency on file bytes is acceptable.
You
OK. Assuming average file size of 500 KB and each DAU uploads 2 files/day: that's 400 million uploads/day, roughly 4,600 writes/sec at peak. Downloads will be 10–20x that — call it 80K reads/sec. Storage: 500M users × 15 GB average quota = ~7.5 PB total, growing. I'll plan chunked uploads (splitting files into fixed blocks, e.g. 4 MB each) as the core primitive — that's what makes resumable uploads and delta sync (only syncing changed blocks, not whole files) possible. Metadata lives in a relational DB with strong consistency. File bytes go to a distributed blob store.

Core Components

Interviewer"How does the chunked upload actually work end-to-end, and how do you handle a client that drops mid-upload?"
Chunked Upload Service
  • WHY: A 5 GB file uploaded atomically means any network blip loses the entire transfer — chunking makes uploads resumable and enables delta sync.
  • HOW: The client splits the file into 4 MB chunks and hashes each one (SHA-256). It sends the list of chunk hashes to the Upload Service, which tells the client which chunks are already stored (deduplication check). The client only uploads missing chunks. Each chunk lands on the Blob Store (distributed object storage) and gets an upload session ID stored in Redis so the client can resume from the last acknowledged chunk after a drop.
  • TRADEOFF: Chunk coordination adds latency and client complexity — simple small-file uploads pay overhead they don't need.
Interviewer"What does your metadata layer look like and how do you handle file versioning?"
Metadata Service
  • WHY: Without a consistent metadata layer, clients can't reconstruct the file tree, resolve conflicts, or know which chunk hashes compose a file.
  • HOW: Metadata (file name, owner, parent folder, list of chunk IDs in order, version number, timestamps) lives in a sharded (data split across machines by user_id) relational DB — PostgreSQL with one shard per range of user IDs. Each upload creates a new FileVersion row pointing to the ordered chunk list rather than overwriting; we keep the last 30 versions by default. A write to metadata is transactional — the file only becomes visible to other devices after all chunk uploads are confirmed and the metadata commit succeeds.
  • TRADEOFF: Keeping 30 versions per file multiplies metadata storage; we cap version count and purge old ones async.
Interviewer"How do clients on different devices know when to pull updates, and how do you minimize what they download?"
Sync Engine
  • WHY: Without a sync protocol, clients either poll constantly (expensive) or miss updates (bad UX).
  • HOW: Each client maintains a sync cursor — a monotonically increasing change sequence number stored server-side per user. When a file changes, we append an event to a per-user change log. Clients open a long-poll (client holds connection open until server has new data) or SSE (server-sent events — one-way push stream) connection to the Sync Service. On reconnect, the client sends its last cursor and gets back only the changed file entries since then. Because we track chunk hashes, the client downloads only chunks it doesn't already have locally.
  • TRADEOFF: Long-poll connections at 200M DAU require careful connection management — we shard the Sync Service by user_id to keep connection counts bounded per host.
Interviewer"Are you rolling your own blob store or using something external? How does CDN fit in for downloads?"
Blob Store
  • WHY: Serving petabytes of binary data from application servers is wasteful — we need a purpose-built system with direct client access.
  • HOW: I'd use a tiered blob store: hot chunks served via CDN (edge caches geographically close to users) using pre-signed URLs (time-limited direct access tokens) so clients download bytes without hitting our app servers at all. The CDN pulls from regional object storage on miss. Cold chunks (not accessed in 90 days) are tiered to cheap archival storage automatically. Deduplication is content-addressed — chunk hash is the storage key, so identical chunks across users are stored once.
  • TRADEOFF: Content-addressed dedup means a chunk collision (two different files producing the same hash) is catastrophic — SHA-256 makes this astronomically unlikely but it's a real risk to acknowledge.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Upload throughput collapses under peak load because all chunk writes fan through a single upload service fleet hitting object storage synchronously.
Fix: I'd decouple chunk persistence from the upload acknowledgment using a write-ahead queue (buffer that records intent before slow I/O). The Upload Service writes chunk metadata to the queue and returns a 202 Accepted immediately. A pool of async chunk workers consumes the queue and writes to object storage. This absorbs traffic spikes without dropping connections. Session state in Redis tracks which chunks are durably persisted so clients know what's safe.
Tradeoff: There's now a window where a chunk is queued but not yet in the blob store — if a worker crashes in that window, the client must retry that chunk.
2Metadata DB becomes a hotspot under heavy write load — every upload commits a new FileVersion row and updates the change log.
Fix: I'd shard (split) the metadata DB by user_id using consistent hashing (maps keys to shards so adding shards requires minimal data movement). Each shard owns a range of user IDs. The change log for sync cursors is co-located on the same shard as the user, keeping all of a user's writes on one machine and avoiding cross-shard transactions for normal operations. We add read replicas per shard to scale metadata reads independently.
Tradeoff: Cross-user sharing features (shared folders) now require cross-shard joins or a separate mapping table — we handle them with a dedicated ACL (access control list) service that resolves permissions before routing queries.
3Download latency spikes for users far from the origin blob store — p99 latency (99th percentile, the slow tail) can exceed 5 seconds for large files.
Fix: I'd serve all downloads via CDN using pre-signed URLs (time-limited tokens the Download Service generates and hands to clients). The client goes directly to the CDN edge node nearest them. On a CDN miss, the edge pulls from regional object storage, not from our app servers. Most files accessed within 24 hours of upload will be warm in the CDN — for cold files we accept the origin pull latency.
Tradeoff: Pre-signed URLs expire (we use 15-minute TTLs) — clients that cache the URL too long will get 403s and need to request a fresh one.

Reference

API
POST/api/v1/files/init— Starts upload session; body has file name, size, chunk hashes; returns session_id and list of missing chunk indices
PUT/api/v1/files/chunks/{session_id}/{chunk_index}— Uploads a single chunk binary; returns 200 when persisted, 202 when queued
POST/api/v1/files/complete/{session_id}— Commits all chunks to a new FileVersion; returns file_id and version_id once metadata is written
GET/api/v1/files/{file_id}— Returns file metadata including current version chunk list and pre-signed download URLs per chunk
GET/api/v1/changes— Long-poll; query param cursor=; returns list of changed file entries since that cursor for the authenticated user
GET/api/v1/files/{file_id}/versions— Lists all stored versions for a file; returns version_id, timestamp, size per version
DELETE/api/v1/files/{file_id}— Soft-deletes file (marks metadata deleted, schedules blob GC); returns 204
Database & Storage
  • PostgreSQL (sharded by user_id) — strong transactional guarantees for metadata, ACID commits for file version creation
  • Schema: files(file_id UUID PK, owner_id UUID, parent_folder_id UUID, name TEXT, created_at TIMESTAMPTZ, deleted_at TIMESTAMPTZ)
  • Schema: file_versions(version_id UUID PK, file_id UUID, version_num INT, chunk_ids UUID[], size_bytes BIGINT, created_at TIMESTAMPTZ)
  • Schema: chunks(chunk_id UUID PK, hash CHAR(64) UNIQUE, blob_key TEXT, size_bytes INT, ref_count INT)
  • Schema: change_log(seq BIGSERIAL PK, user_id UUID, file_id UUID, event_type TEXT, version_id UUID, ts TIMESTAMPTZ)
  • Index: files(owner_id, parent_folder_id) for folder listing; file_versions(file_id, version_num DESC) for version history; change_log(user_id, seq) for sync cursor queries
  • Tradeoff: Storing chunk_ids as a UUID array in file_versions is simple and fast for reconstruction but makes querying 'which files reference this chunk' for GC (garbage collection — deleting unreferenced blobs) require a separate ref_count column on chunks rather than a join scan
