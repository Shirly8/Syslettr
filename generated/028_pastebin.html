Systems Design · Tier 1

Pastebin

Pastebin looks trivial — it's just storing text — but collision-free short-URL generation at scale without a single point of failure is genuinely tricky. Interviewers use it to probe ID generation strategies, read-heavy caching, blob storage separation, and TTL-based cleanup.

Interview

Interviewer
Design a Pastebin-like service where users can paste text and get a short URL back. Where do you start?
You
Before diving in — what's the scale? Millions of pastes or tens of millions per day? Do users get custom aliases or only auto-generated codes? And do we need expiration, syntax highlighting, or is raw text storage enough for now?
Interviewer
About 5 million new pastes per day. Auto-generated codes only, no custom aliases. Pastes expire after 30 days by default, optional never-expire tier. Plain text only, max 10MB per paste.
You
5M pastes/day is ~58 writes/sec at peak — manageable. Reads are typically 10x writes on a sharing-heavy service, so ~580 reads/sec sustained, with spikes higher. A 7-character base62 code (letters + digits, ~3.5 trillion combinations) gives us ID space for centuries. At 10MB max per paste, that's 50GB of raw content added per day, or ~1.5TB/month — I'll store content in an object store (a distributed blob storage system like S3) and only keep metadata plus the short code in a relational DB. Caching hot pastes in memory is the core read optimization.

Core Components

Interviewer"How do you generate those 7-character codes without collisions, especially across multiple app servers?"
Short Code Generation
  • WHY: Two servers generating the same code simultaneously would overwrite or reject a paste — users lose data silently.
  • HOW: I pre-generate batches of unique codes using a token server (a dedicated service that hands out pre-validated ID ranges). Each app server requests a batch of, say, 1,000 codes at startup and refills when it drops below 100. Within each batch, codes are issued sequentially so no coordination is needed mid-request. The token server uses a single auto-increment counter in a small dedicated DB — writes to it are rare (one per batch) so it doesn't become a bottleneck.
  • TRADEOFF: Pre-allocated codes that are never used (e.g., app server crashes) are wasted, but with 3.5 trillion possible codes that's a negligible loss.
Interviewer"Where does the actual paste content live, and how does retrieval work?"
Paste Storage (Metadata + Content Split)
  • WHY: Storing 10MB blobs inline in a relational DB bloats row sizes, wrecks index performance, and makes backups painful.
  • HOW: I split storage into two layers. Metadata (short code, owner, created_at, expires_at, content_key) lives in a relational DB — rows are tiny, indexed on short code for O(log n) lookup. The actual text content is stored as a file in an object store keyed by a UUID (universally unique identifier — a 128-bit random key). On write: save content to object store, get back the content_key, then write one metadata row. On read: look up metadata by short code, fetch content from object store using content_key.
  • TRADEOFF: Two-hop reads (DB then object store) add latency — mitigated by caching full paste content in memory for hot pastes.
Interviewer"Which pastes do you cache and how do you handle cache invalidation when a paste expires or is deleted?"
Read Cache Layer
  • WHY: Without caching, every read hits the DB and then the object store — latency spikes and object store costs scale with traffic.
  • HOW: I cache full paste content (text + metadata) keyed by short code using an in-memory cache with LRU eviction (drops least-recently-used entries when cache is full). TTL (time-to-live — how long an entry stays cached) on each cache entry is set to min(paste expiry, 24 hours) so expired pastes are never served stale. On explicit delete, I issue a cache invalidation (active removal of the stale key) to keep consistency.
  • TRADEOFF: Cache memory is finite — very large pastes near the 10MB limit will evict many smaller hot pastes, so I cap cached paste size at 1MB and let large pastes always hit the object store.
Interviewer"How do you actually delete pastes that have passed their expiry time without scanning the whole table?"
Expiration & Cleanup
  • WHY: Without active cleanup, expired pastes accumulate indefinitely — storage costs grow unbounded and legal/compliance obligations aren't met.
  • HOW: I run a background cleanup worker (an async job that runs independently of request handling) on a cron schedule — every hour it queries for rows WHERE expires_at < NOW() LIMIT 10000, deletes the metadata rows, and enqueues the corresponding content_keys for object store deletion via a queue (a durable message buffer that decouples producers from consumers). This prevents the deletion spike from blocking read/write paths. I index expires_at so the query is fast.
  • TRADEOFF: Pastes can live slightly past their expiry window (up to one cleanup cycle), but this is a common acceptable lag for storage cleanup.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1The Metadata DB becomes a write bottleneck when millions of new pastes arrive in bursts — single-leader replication (one primary accepting all writes) can't keep up.
Fix: I shard (split data across multiple DB machines) the metadata table by the first character of the short code — 62 shards for base62, each handling roughly 1/62 of traffic. App servers hash the short code to determine which shard to hit. Each shard has its own primary + read replicas. This distributes write load without needing cross-shard joins since all paste queries are single-key lookups by short code.
Tradeoff: Operational complexity jumps — adding a shard requires a resharding migration, and any analytics that aggregate across all pastes must scatter-gather across all shards.
2A single viral paste drives a thundering herd (thousands of simultaneous cache misses all hitting the DB at once) when the cache entry expires.
Fix: I use a cache-aside pattern with mutex (mutual exclusion lock — only one thread fetches from DB at a time) on cache miss. The first request that misses acquires a short-lived lock and fetches from DB; subsequent concurrent misses wait and then read from the now-warm cache. I also use probabilistic early expiration — refresh the cache entry slightly before it actually expires, so the expiry never catches live traffic off-guard.
Tradeoff: Mutex adds a small latency spike for the first requester on a cold key, but eliminates the DB spike from hundreds of concurrent misses.
3Object store read costs spike when large pastes are fetched repeatedly at high frequency — object stores charge per-request.
Fix: I add a size cap of 1MB for cache eligibility. Pastes above 1MB bypass the in-memory cache and instead get cached at the CDN (content delivery network — globally distributed edge servers that cache responses closer to users) edge using long Cache-Control headers. Since large pastes change less often and have fixed content after creation, CDN caching gives excellent hit rates with no per-request object store cost.
Tradeoff: CDN cache invalidation on delete/expiry requires purging the CDN edge — adds operational overhead and a brief window where deleted content could still be served.

Reference

API
POST/api/v1/pastes— Creates a paste; body: {content, expires_in_seconds?}; returns {short_code, url, expires_at}
GET/api/v1/pastes/{short_code}— Returns paste content and metadata; 404 if expired or not found
DELETE/api/v1/pastes/{short_code}— Deletes paste immediately; requires auth token matching creator; returns 204
GET/api/v1/pastes/{short_code}/meta— Returns metadata only (no content) — created_at, expires_at, size — for link preview use cases
Database & Storage
  • PostgreSQL — relational, strong consistency for metadata; simple indexed lookup by short code; handles TTL queries efficiently with a partial index on expires_at
  • Schema: pastes(short_code CHAR(7) PK, content_key UUID NOT NULL, owner_token CHAR(64), created_at TIMESTAMPTZ NOT NULL, expires_at TIMESTAMPTZ, size_bytes INT NOT NULL)
  • Index strategy: PRIMARY KEY on short_code (B-tree, O(log n) lookups); secondary index on expires_at WHERE expires_at IS NOT NULL for cleanup worker scans — partial index keeps it small
  • Key tradeoff: PostgreSQL gives ACID guarantees (atomicity, consistency, isolation, durability — all-or-nothing writes that survive crashes) but vertical scaling limits write throughput; sharding by short_code prefix is the escape hatch when single-node write capacity is exhausted
