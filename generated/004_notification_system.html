Notification System

A notification system looks simple until you realize fan-out (sending one event to millions of recipients) at scale creates thundering-herd problems, and guaranteeing exactly-once delivery across email, push, and SMS requires careful idempotency design. Interviewers use this to probe your understanding of async pipelines, rate limiting, and graceful degradation under partial failures.

Interview

Interviewer
We want to build a notification system for a product like Facebook — users get notified about likes, comments, friend requests, and so on. Where do you start?
You
Before diving in — what channels are we supporting: push, email, SMS, or all three? What's the scale — millions of users or hundreds of millions? And are we optimizing for real-time delivery under a second, or is a few seconds of lag acceptable?
Interviewer
All three channels. 500 million active users, up to 10 billion notifications per day. Push should feel real-time — under 5 seconds. Email and SMS can tolerate up to 30 seconds.
You
10 billion per day is roughly 115K notifications/sec at peak with typical 2x spike headroom, so I'll design for ~230K/sec. Fan-out (broadcasting one event to many recipients) is the core challenge — a single viral post could trigger millions of pushes in seconds. I'll separate the ingestion path from the delivery path with a queue layer and per-channel workers, and I'll assume idempotency keys (unique event IDs used to deduplicate retries) are required to prevent double delivery.

Core Components

Interviewer"How does an upstream service like the Feed service actually trigger a notification — and how do you prevent it from overwhelming your system?"
Event Ingestion API
  • WHY: Without a controlled ingestion layer, upstream services can burst-write at unpredictable rates and directly spike every downstream component.
  • HOW: I expose a thin REST/gRPC endpoint that accepts a notification event (event type, actor ID, recipient list or topic, payload). Before writing anywhere, I validate the schema and apply per-caller rate limiting (token bucket — callers get a fixed quota per second, excess is rejected with 429). Validated events are written atomically to a durable inbound queue — I never write to DB synchronously on this path.
  • TRADEOFF: Rejecting bursts with 429 means the caller must implement retries with backoff — we shift retry responsibility upstream.
Interviewer"A celebrity with 50 million followers likes a post — how do you fan that out without melting your pipeline?"
Fan-out Service
  • WHY: Naive synchronous fan-out blocks the ingestion path for seconds and creates a cascading queue backlog on every high-follower event.
  • HOW: I pull events from the inbound queue and look up recipient lists from a follower store (pre-sharded by actor ID). For accounts under a threshold (say, 10K followers) I do push fan-out — write one message per recipient into the per-channel queues immediately. For large accounts I use pull fan-out — write a single 'pending notification' record and let each recipient's client fetch it on next poll or app open. This is the hybrid fan-out strategy used by systems like Twitter.
  • TRADEOFF: Pull fan-out means truly inactive users may never see the notification if they never open the app — acceptable for non-critical events.
Interviewer"How do you actually send a push notification versus an email — and what happens when one of those third-party providers is down?"
Per-Channel Delivery Workers
  • WHY: Each channel has completely different throughput limits, latency SLAs, and third-party provider APIs — treating them identically would mean the slowest channel (email) blocks the fastest (push).
  • HOW: I run independent worker pools per channel, each consuming from its own queue. Push workers call APNs (Apple's push service) and FCM (Google's Firebase Cloud Messaging) with exponential backoff (retry wait that doubles each attempt — prevents hammering a degraded provider). Email workers call an SMTP relay and SMS workers call an aggregator like Twilio. Each delivery attempt writes a result (delivered/failed/retried) to a delivery log table keyed by idempotency key (event ID + recipient ID + channel).
  • TRADEOFF: Independent queues mean a spike in email volume can't be absorbed by idle push workers — capacity is siloed per channel.
Interviewer"How do you make sure a user who opted out of email notifications doesn't get spammed?"
User Preference & Routing Service
  • WHY: Without preference checking, every channel fires for every event — users churn, spam rates increase, and we risk regulatory violations like CAN-SPAM or GDPR opt-out requirements.
  • HOW: I maintain a preferences table keyed by user ID storing per-channel opt-in flags and per-event-type mute rules. The fan-out service reads this table before writing to channel queues — it's a lightweight read-through cache (cache sits in front of DB; a miss fetches from DB and populates cache) keyed by user ID with a TTL (time-to-live — entry expiry after N seconds) of 60 seconds. Stale preferences are acceptable given the TTL; the user will see the effect of a preference change within a minute.
  • TRADEOFF: 60-second TTL means a user who opts out today might get one more notification before the cache expires — acceptable UX tradeoff to avoid hot DB reads.
Interviewer"What happens when APNs returns a 503 — how do you retry without delivering duplicates?"
Delivery Tracking & Retry Engine
  • WHY: Third-party providers fail transiently; without a structured retry mechanism, failed notifications are silently dropped.
  • HOW: Each delivery attempt writes a row to a delivery_log table with status (pending/sent/failed) and an idempotency key (event_id + user_id + channel). On a transient failure, the worker re-enqueues the message with a visibility delay (message stays hidden in queue for N seconds before reappearing) implementing exponential backoff. Before attempting delivery, the worker checks if idempotency key already has status=sent — if yes, it skips and acks the message. Permanent failures (invalid device token, unsubscribed email) are marked dead-letter and trigger a cleanup job to prune stale device registrations.
  • TRADEOFF: The idempotency check requires a DB read on every delivery attempt — at 230K/sec this is a meaningful load, so I'd front it with a Bloom filter (probabilistic data structure — fast membership check with no false negatives) to skip the DB read for clearly-new events.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A celebrity with 50M followers triggers a fan-out spike that floods the channel queues and causes push latency to jump to 30+ seconds.
Fix: I apply back-pressure at the fan-out layer: large-account fan-outs are throttled to a maximum enqueue rate (say, 50K messages/sec per event) using a token bucket per event ID. The fan-out worker spreads the remaining enqueues over time by scheduling them with a small delay. This keeps channel queue depth bounded and preserves the 5-second SLA for normal accounts whose pushes aren't queued behind the celebrity spike.
Tradeoff: Large-account recipients get their notification delayed by up to 60 seconds during a spike — acceptable for a viral post but not for a direct message.
2The delivery_log DB becomes a write bottleneck at 230K writes/sec when every delivery attempt records its status.
Fix: I partition the delivery_log table by (channel, date) — a form of sharding where each shard holds one day's data per channel. Writes fan out across shards naturally. I also batch delivery status updates: workers accumulate 50 writes in memory and flush as a single bulk insert every 200ms. For the idempotency check I use an in-process Bloom filter to short-circuit most DB reads — only possible duplicates hit the DB.
Tradeoff: Batching introduces up to 200ms of state lag — if a worker crashes mid-batch, those 50 records are lost and those notifications could be retried and delivered twice.
3Device token churn (users reinstall apps, tokens go stale) causes APNs to return permanent errors that clog the push queue with undeliverable messages.
Fix: I handle APNs 410 (token invalidated) responses immediately in the push worker: on a 410 I write the token as invalid in a device_registry table and skip requeuing. A nightly cleanup job removes all invalid tokens from the registry so they're never targeted for push fan-out again. I also track per-provider error rates — if APNs error rate exceeds 5% in a 60-second window, I circuit-break (stop sending, wait N seconds before retrying) and alert on-call.
Tradeoff: Circuit breaking means no pushes go out during an APNs outage — users see nothing until the circuit closes, rather than getting delayed notifications.

Reference

API
POST/api/v1/notifications— Enqueues a notification event; accepts {event_type, actor_id, recipient_ids[], payload, idempotency_key}; returns 202 Accepted with event_id
POST/api/v1/notifications/topic— Fan-out to a topic (e.g. all followers of actor_id); returns 202 with job_id for async tracking
GET/api/v1/notifications/{user_id}— Returns paginated notification history for a user; supports cursor-based pagination and channel filter
PUT/api/v1/users/{user_id}/preferences— Updates per-channel and per-event-type opt-in flags; invalidates preference cache entry for user_id
GET/api/v1/notifications/events/{event_id}/status— Returns delivery status per channel for a given event_id; used by producers to confirm delivery
Database & Storage
  • PostgreSQL — relational integrity for user preferences and device registry; low write volume on these tables makes row locking acceptable
  • Schema: notifications(event_id UUID PK, actor_id BIGINT, event_type VARCHAR, payload JSONB, created_at TIMESTAMP)
  • Schema: delivery_log(id BIGINT PK, event_id UUID, user_id BIGINT, channel VARCHAR, status VARCHAR, idempotency_key VARCHAR UNIQUE, attempted_at TIMESTAMP) — partitioned by (channel, DATE(attempted_at))
  • Schema: user_preferences(user_id BIGINT PK, push_enabled BOOL, email_enabled BOOL, sms_enabled BOOL, muted_event_types JSONB, updated_at TIMESTAMP)
  • Schema: device_registry(device_id UUID PK, user_id BIGINT, platform VARCHAR, token VARCHAR, is_valid BOOL, updated_at TIMESTAMP)
  • Cassandra — for high-write delivery_log at scale; partition key (user_id, month) enables fast per-user notification history reads with time-sorted clustering
  • Index strategy: delivery_log indexed on (user_id, created_at DESC) for history queries; unique index on idempotency_key for dedup enforcement; device_registry indexed on user_id for fan-out token lookups
  • Key tradeoff: Cassandra gives write scalability but eventual consistency (writes replicate asynchronously) means a freshly delivered notification may not appear in history queries for a few hundred milliseconds
