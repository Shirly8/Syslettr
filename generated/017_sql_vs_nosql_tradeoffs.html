SQL vs NoSQL Tradeoffs

The choice between SQL and NoSQL isn't about hype — it's about data shape, access patterns, and consistency guarantees that are genuinely hard to change post-launch. Interviewers ask this because the wrong choice cascades into every architectural decision downstream.

Interview

Interviewer
We're building a platform that handles both user account data and a high-volume activity feed — think social posts, likes, and follows. Walk me through how you'd approach the storage layer.
You
Before I pick any database — what's the write volume on the activity feed versus the user accounts? And do we need strong consistency (every read sees the latest write) on the feed, or is eventual consistency acceptable? Also, are we doing complex relational queries on this data, or mostly key-based lookups?
Interviewer
User base is 50 million accounts with complex relationships — followers, blocks, permissions. Feed is 100K writes/sec at peak, reads are 10x that. Staleness of a few seconds on the feed is fine, but account/auth data must be strongly consistent.
You
Got it — so roughly 100K feed writes/sec and 1M feed reads/sec, plus a heavily relational user graph that needs ACID (Atomicity, Consistency, Isolation, Durability — guarantees that DB operations complete fully or not at all). I'll split storage: SQL for user accounts and relationships where consistency and joins are non-negotiable, and a wide-column NoSQL store for the feed where we need horizontal scale (adding more machines to distribute load) and high write throughput. The key insight is that these two workloads have fundamentally different shapes — you can't optimize a single database for both without painful compromise.

Core Components

Interviewer"Why not just put everything in PostgreSQL and scale it vertically? It's simpler."
SQL Layer — User Accounts & Graph
  • WHY: User data has rich relational structure — follower graphs, permission rules, account state — where JOIN queries and foreign-key constraints prevent bad data states that are catastrophically hard to fix later.
  • HOW: I'd use a relational database with a normalized schema for users, follow relationships, and auth tokens. Writes go through a primary node; reads fan out to read replicas (copies of the primary that handle read traffic). For the follower graph specifically, I'd index both directions of the follow relationship so 'who follows user X' and 'who does user X follow' are both fast lookups.
  • TRADEOFF: Vertical scaling (buying a bigger machine) hits a ceiling around a few TB and tens of thousands of write ops/sec — fine for user accounts since write volume is modest, but it would buckle under feed-level traffic.
Interviewer"Why a wide-column store specifically? Couldn't a document store like MongoDB handle this?"
NoSQL Layer — Activity Feed
  • WHY: Feed reads are almost always 'give me user X's 50 most recent posts' — a time-range scan on a partition key. Wide-column stores (databases that group rows by a partition key and sort within partitions) are purpose-built for this; document stores add overhead for a query shape that doesn't need document flexibility.
  • HOW: I'd model the feed table with user_id as the partition key and post_timestamp as the clustering key (sort order within a partition). That means a feed read is one sequential disk read on a pre-sorted partition — no scatter-gather across nodes. I'd cap partition size with a TTL (time-to-live, auto-deletes old rows after N days) so hot users don't create unbounded partitions.
  • TRADEOFF: No ad-hoc queries — you design your schema around your access pattern upfront. Changing the query shape later means a backfill migration on hundreds of terabytes.
Interviewer"How do you handle operations that span both databases — like when a user deletes their account and we need to purge their feed?"
Consistency Boundary Management
  • WHY: Two-phase commit (a protocol that locks both databases until both confirm a write) across SQL and NoSQL is impractical at scale — it creates distributed locking that kills throughput and is fragile under partial failures.
  • HOW: I'd use an outbox pattern (write a 'pending deletion' event to a table in the SQL DB atomically with the account deletion, then a background worker reads that table and drives the NoSQL purge). The SQL outbox write is part of the same ACID transaction as the account deletion, so it's atomic. The NoSQL purge becomes eventually consistent — the feed data disappears within seconds to minutes, not instantly.
  • TRADEOFF: There's a window where a deleted account's feed content is still visible; you need application-layer checks to hide it while the purge propagates.
Interviewer"At 1M feed reads/sec, even a fast NoSQL store is going to sweat. What's your caching strategy?"
Read Cache Layer
  • WHY: At 1M reads/sec, even microsecond-latency NoSQL clusters require massive hardware; caching the hot tail (top 1% of users generate ~50% of reads) collapses the actual DB load by an order of magnitude.
  • HOW: I'd put an in-memory cache (stores data in RAM for sub-millisecond reads) in front of the feed store, keyed by user_id with LRU eviction (drops least-recently-used entries when cache is full). Cache the most recent 50 posts per user — that covers the p99 (99th percentile — the worst-case latency for 99% of users) read case. TTL on cache entries is 30 seconds to bound staleness within our acceptable window.
  • TRADEOFF: Cache invalidation on a new post requires either a write-through (update cache on every write) or accepting up to 30 seconds of staleness — write-through at 100K writes/sec adds latency to the write path.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1The SQL primary becomes the write bottleneck if follower graph mutations (follow/unfollow events) spike — a viral moment can drive tens of thousands of graph writes/sec against a single node.
Fix: I'd introduce functional partitioning (splitting the SQL database by domain, not random hash) — user auth/profiles stay on one cluster, and the follow-graph relationship table moves to a separate SQL cluster. This doubles write headroom without adding NoSQL complexity to a dataset that genuinely needs JOIN semantics. If that's still not enough, I'd shard the graph table by user_id range across multiple primaries.
Tradeoff: Cross-cluster joins are now impossible — any query spanning users and their graph must be done in application logic with two queries, increasing latency and complexity.
2At 1M feed reads/sec, cache stampede (when the cache entry for a hot user expires and thousands of requests hit the DB simultaneously) can cause a NoSQL availability event.
Fix: I'd use probabilistic early expiration — recompute the cache entry slightly before it expires, based on a formula that factors in how expensive the query is and current traffic rate. Combined with a distributed lock (a flag only one server can hold at a time) on cache miss so only one request fetches from the DB while others wait for the updated cache entry, this collapses the thundering herd to a single DB read.
Tradeoff: The distributed lock adds a small latency spike (tens of milliseconds) for the unlucky request that gets the lock miss — acceptable given it prevents DB overload.

Reference

API
POST/api/v1/users— Creates user account; writes to SQL primary; returns user_id and auth token
GET/api/v1/users/{user_id}— Fetches profile; reads from SQL read replica; returns user object
POST/api/v1/users/{user_id}/follows— Creates follow relationship; ACID write to SQL graph cluster; returns 201
POST/api/v1/feed/posts— Creates post; writes to NoSQL feed partition keyed by user_id; returns post_id
GET/api/v1/feed/{user_id}?limit=50&before={timestamp}— Returns paginated feed; served from cache on hit, NoSQL partition scan on miss
DELETE/api/v1/users/{user_id}— Deletes account in SQL atomically with outbox event; triggers async NoSQL purge
Database & Storage
  • SQL (PostgreSQL) — relational user data, follow graph, auth tokens; needs ACID, foreign keys, and JOIN support
  • Schema: users(user_id UUID PK, username TEXT UNIQUE, email TEXT UNIQUE, created_at TIMESTAMPTZ, status TEXT) | follows(follower_id UUID FK, followee_id UUID FK, created_at TIMESTAMPTZ, PRIMARY KEY(follower_id, followee_id))
  • Indexes: follows(followee_id, follower_id) for reverse lookups; users(username) for login; both directions of follow indexed to avoid full-table scans on either side of the relationship
  • Wide-Column NoSQL (Cassandra-style) — feed posts partitioned by user_id, clustered by post_timestamp DESC; TTL 90 days auto-purges old rows; no cross-partition queries allowed by design
  • Key tradeoff — SQL gives you schema enforcement and ad-hoc queries at the cost of limited write throughput per primary; NoSQL gives you linear horizontal write scale at the cost of query inflexibility and eventual consistency
