Systems Design · Tier 2

OAuth 2.0 / SSO

OAuth 2.0 looks like a simple redirect flow until you have to build the authorization server itself — token issuance, revocation, scope enforcement, and multi-tenant SSO at scale expose a dozen failure modes. Interviewers use it to probe security-conscious design, distributed session state, and the tradeoffs between stateless JWTs and revocable opaque tokens.

Interview

Interviewer
We want to build our own OAuth 2.0 authorization server that also serves as a single sign-on provider for a suite of internal and third-party applications. Where do you start?
You
Before diving in — how many registered client applications are we supporting, and what's the DAU (daily active users) hitting the auth layer? Are we issuing short-lived JWTs, opaque tokens, or both? And do we need to support the full four OAuth grant types, or is Authorization Code with PKCE the primary flow?
Interviewer
Roughly 50 million DAU, 200 registered client apps spanning web, mobile, and server-to-server. Prioritize Authorization Code with PKCE for user-facing apps and Client Credentials for machine-to-machine. Target sub-100ms token issuance p99 (99th percentile — the slow tail, not the average).
You
So at peak I'm planning for roughly 5,000–8,000 token issuance requests per second, with authorization code exchanges being short-lived and bursty. I'll issue short-lived JWTs (JSON Web Tokens — self-contained, cryptographically signed blobs) for access tokens so resource servers can verify offline, paired with opaque refresh tokens stored server-side so we can revoke them. SSO state will be a server-side session cookie pointing to a session record — not a JWT — so we can invalidate it on logout. That asymmetry is intentional: JWTs give us fast resource-server validation without a network call, opaque refresh tokens give us real revocation.

Core Components

Interviewer"Walk me through what happens when a user hits the authorization endpoint — what state do you need to protect against CSRF and code interception attacks?"
Authorization Endpoint
  • WHY: Without a validated, short-lived authorization code tied to the exact client and redirect URI, an attacker can steal the code in transit or replay it.
  • I generate a cryptographically random authorization code (typically 32 bytes, base64url-encoded), store it in a fast key-value store like Redis with a 60-second TTL (time-to-live — auto-expiry), and bind it to: client_id, redirect_uri, requested scopes, user_id, and the SHA-256 hash of the PKCE (Proof Key for Code Exchange — prevents code interception by binding the exchange to a secret only the original caller knows) code_verifier. On exchange, I verify the code_challenge matches and then immediately delete the code — one-time use.
  • TRADEOFF: The Redis round-trip on every code exchange adds ~1–2ms latency, but the alternative — encoding state in the code itself — makes revocation impossible.
Interviewer"How do you sign JWTs at 5,000 requests per second without the signing key becoming a bottleneck or a single point of compromise?"
Token Issuance Service
  • WHY: Centralizing signing in a single process means one crash takes down all token issuance, and a leaked private key compromises every issued token across all clients.
  • I use RS256 (RSA asymmetric signing — private key signs, public key verifies) so resource servers can validate tokens without calling home. The private key lives in an HSM (Hardware Security Module — tamper-resistant key store) or a secrets manager with in-process caching of the signing handle — not the raw key bytes. I publish a JWKS (JSON Web Key Set — public keys at a well-known URL) endpoint so resource servers rotate public keys automatically. For performance, the signing operation itself is CPU-bound but fast — RSA-2048 signs in ~0.5ms, so 5K/s needs maybe 4–6 cores worth of headroom, easily handled with a stateless horizontally-scaled service.
  • TRADEOFF: RS256 tokens are ~50% larger than HS256 (HMAC — symmetric, shared secret) tokens, which matters for mobile clients on every request.
Interviewer"How does SSO actually work across multiple apps — what's the session state model?"
SSO Session Store
  • WHY: Without a shared, server-side session, a user logging out of one app can't be signed out of others, and you can't invalidate sessions on account compromise.
  • When a user authenticates, I create an SSO session record keyed by a random session ID stored in a secure, HttpOnly, SameSite=Strict cookie on the authorization server's domain. The session record holds: user_id, authenticated_at, last_seen, device fingerprint, and a list of client apps that have active tokens tied to this session — enabling global logout (back-channel signaling to all registered clients to drop their tokens). I store this in Redis with a sliding TTL (refreshed on each SSO check) of 8 hours, with a hard cap at 24 hours.
  • TRADEOFF: Server-side sessions require a Redis lookup on every SSO check — that's the cost of real revocability.
Interviewer"JWTs are stateless — how do you revoke an access token before it expires if a user reports account compromise?"
Token Revocation & Refresh Token Store
  • WHY: A stolen JWT with 15 minutes left is valid at every resource server unless you add a revocation check — pure stateless verification has no way to stop it.
  • I keep access token lifetimes short — 15 minutes — so the blast radius of a stolen token is bounded. For immediate revocation I maintain a jti (JWT ID — a unique claim baked into each token) blocklist in Redis. On compromise, I add the jti with TTL equal to the token's remaining lifetime. Resource servers check the blocklist on sensitive operations only — not every request — to avoid making the cache a hot bottleneck. Refresh tokens are opaque and stored in a database with a refresh_tokens table; revoking one cascades to the SSO session's client list.
  • TRADEOFF: The jti blocklist grows proportionally to revocation events and requires Redis to be in the critical path for sensitive operations.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1The Redis auth code store becomes a hot spot during login bursts — millions of users hitting SSO simultaneously (after a marketing email, for example) create a write stampede on a single Redis primary.
Fix: I shard (split data across multiple Redis nodes) the auth code store by the first byte of the code itself — 256 possible shards — so no single node handles more than 1/256th of writes. Auth codes are random, so distribution is naturally uniform. Separately, I put a local in-process cache (per auth server instance, ~10ms LRU eviction) in front of SSO session reads — the same user's session gets checked repeatedly within a short window, so local cache hit rate is high and Redis read load drops significantly.
Tradeoff: Local per-instance caching means a session revocation takes up to the cache TTL (I'd set it to ~30 seconds) to propagate — acceptable for most cases but not zero-latency revocation.
2Resource servers making a synchronous call to check the jti blocklist on every sensitive request creates a latency chain — if Redis goes down, those endpoints go down too.
Fix: I decouple sensitive-operation validation from the synchronous request path using a two-tier approach: resource servers maintain a local bloom filter (a probabilistic data structure — fast 'probably in set / definitely not in set' check) of revoked jtis, refreshed every 30 seconds via a background pull from Redis. Only if the bloom filter says 'probably revoked' does the server make a synchronous Redis call to confirm. False positive rate is tunable — at 0.1% I need ~2 bytes per revoked token entry.
Tradeoff: Revocations take up to 30 seconds to appear in the local bloom filter — a stolen token is valid for that window at resource servers that haven't refreshed yet.
3Token endpoint throughput collapses during key rotation — if all instances simultaneously request the new private key from the HSM, the HSM becomes the bottleneck.
Fix: I treat key rotation as a controlled rollout: one elected leader instance fetches the new key material from the HSM and propagates it via an internal pub/sub channel (event broadcast within the cluster) to peers. Each instance caches the signing handle in-process. The old key continues to be used for in-flight requests for a 5-minute overlap window — resource servers accept tokens signed by any key in the JWKS set, which I version with a kid (key ID — a claim in the JWT header identifying which key signed it) claim.
Tradeoff: The leader-election mechanism adds complexity — if the leader dies during rotation, a new leader must detect the partial state and resume, requiring rotation state to be durably stored.

Reference

API
GET/oauth/authorize?response_type=code&client_id=&redirect_uri=&scope=&state=&code_challenge=&code_challenge_method=S256— Initiates Authorization Code flow; redirects to redirect_uri with code and state on success
POST/oauth/token— Exchanges auth code or refresh token for access_token (JWT) + refresh_token (opaque); body: grant_type, code, code_verifier, client_id
POST/oauth/revoke— Revokes a refresh token or access token by jti; cascades to SSO session client list on refresh token revocation
POST/oauth/introspect— RFC 7662 token introspection — returns active status, scope, user_id, exp for opaque tokens; requires client auth
GET/.well-known/oauth-authorization-server— Returns server metadata: issuer, JWKS URI, supported grant types, scopes — enables client auto-configuration
GET/.well-known/jwks.json— Returns current public keys as JWKS; served via CDN with Cache-Control: max-age=3600, must-revalidate
Database & Storage
  • PostgreSQL — durable source of truth for registered clients, users, and refresh tokens; supports complex relational queries for client scope validation
  • Schema: oauth_clients(client_id UUID PK, client_secret_hash TEXT, redirect_uris TEXT[], allowed_scopes TEXT[], token_endpoint_auth_method TEXT, created_at TIMESTAMPTZ)
  • Schema: refresh_tokens(token_hash TEXT PK, user_id UUID, client_id UUID, scopes TEXT[], session_id TEXT, issued_at TIMESTAMPTZ, expires_at TIMESTAMPTZ, revoked_at TIMESTAMPTZ)
  • Schema: sso_sessions(session_id TEXT PK, user_id UUID, authenticated_at TIMESTAMPTZ, last_seen TIMESTAMPTZ, active_clients JSONB)
  • Redis — ephemeral fast store for auth codes (60s TTL), SSO session cache (8h sliding TTL), and jti blocklist (TTL = remaining token lifetime)
  • Index: refresh_tokens(user_id, revoked_at) — supports 'list all active sessions for user' and global logout fan-out queries
  • Index: refresh_tokens(expires_at) WHERE revoked_at IS NULL — supports background cleanup job for expired tokens without full table scan
  • Key tradeoff: storing refresh tokens by hash (not plaintext) means the token is unrecoverable server-side — correct for security, but a lost token requires re-authentication with no recovery path
