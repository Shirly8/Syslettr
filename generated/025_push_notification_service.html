Push Notification Service

A push notification service looks like a simple message relay, but fan-out (broadcasting one event to millions of devices simultaneously) creates brutal write amplification and third-party rate-limit pressure. Interviewers use it to probe queueing strategy, idempotency, and how you handle the unreliable external gateway layer — APNs, FCM — that you don't control.

Interview

Interviewer
We need to design a push notification service — think mobile app alerts, marketing campaigns, transactional messages. Walk me through how you'd approach this.
You
Before diving in — what's the daily notification volume and how many registered devices are we targeting? Are we sending to individual users, segments, or broadcast-to-all? And do we need delivery receipts — confirmation the device actually received it?
Interviewer
Roughly 1 billion notifications per day, 500 million registered devices. Mix of targeted (user-level), segment-based, and occasional full broadcasts. Delivery receipts are required — at-least-once delivery with deduplication on the client.
You
So about 11,500 notifications/sec average, but campaign fan-out can spike 10x — I'll design for 115K/sec peak. At-least-once delivery means I need idempotency keys (unique IDs that prevent duplicate processing) end-to-end. Each device record is ~200 bytes, so 500M devices is ~100GB — fits in a distributed cache with a DB backing store. The hardest part is segment fan-out: a campaign to 50M users can't block the hot path, so fan-out must be async through a queue.

Core Components

Interviewer"How does this API handle a campaign blast to 50 million users without falling over?"
Notification Intake API
  • WHY: Without rate-limiting and async handoff, a single large campaign synchronously writes 50M records and stalls every other sender.
  • HOW: The API accepts a notification payload with a target spec — user ID, segment ID, or 'all' — validates auth, writes one campaign record to the DB, drops a single fan-out job onto a distributed queue (a durable ordered message buffer), and returns 202 Accepted immediately. The caller gets a campaign ID to poll for status. The actual device-level expansion happens downstream.
  • TRADEOFF: Callers get eventual, not immediate, confirmation of per-device delivery — polling or webhooks required.
Interviewer"Walk me through how the fan-out worker expands a segment campaign to individual device tokens."
Fan-out Worker
  • WHY: Without a dedicated expansion step, the gateway layer would need to understand segments — coupling business logic to the delivery layer and making it unscalable.
  • HOW: Workers pull a fan-out job from the queue and read the target segment in paginated chunks of 10K device tokens from the device registry. For each chunk they write individual notification tasks onto per-platform queues — one for APNs (Apple's push gateway) and one for FCM (Firebase Cloud Messaging, Google's gateway). Each task carries an idempotency key derived from campaign ID + device token. Workers are stateless and horizontally scalable — I scale them based on queue depth.
  • TRADEOFF: Segment reads during fan-out create a read spike on the device registry; I mitigate with read replicas but can't fully eliminate the load.
Interviewer"APNs and FCM have their own rate limits and failure modes — how do you handle that?"
Gateway Delivery Worker
  • WHY: APNs and FCM reject requests if you exceed their per-second connection limits, and they return different error codes for expired tokens vs. transient failures — conflating them causes unnecessary retries and token churn.
  • HOW: Per-platform workers consume from their respective queues, maintain a persistent HTTP/2 connection pool to the gateway (reusing connections avoids TLS handshake overhead), and send requests with exponential backoff (doubling wait time on each retry) capped at 3 retries. On a 'BadDeviceToken' error I mark the token invalid in the device registry immediately and don't retry. On 5xx I retry with backoff. I track delivery outcomes in a status table keyed by idempotency key.
  • TRADEOFF: Persistent connection pools require careful lifecycle management — a crashed worker leaks connections until the gateway times them out.
Interviewer"How do you model and store 500 million device token records efficiently?"
Device Registry
  • WHY: Device tokens expire and rotate — if the registry is stale, fan-out wastes cycles and you burn gateway quota on dead tokens.
  • HOW: I store device records in a partitioned relational DB — sharded (split across machines) by user ID so all devices for a user land on one shard. Each row holds user_id, device_token, platform (ios/android), and a valid boolean that the delivery worker flips on BadDeviceToken. Hot user lookups go through a distributed cache with a 1-hour TTL (time-to-live — expiry on cache entries).
  • TRADEOFF: Sharding by user_id means a full-broadcast segment scan must hit every shard in parallel — adds scatter-gather latency.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A broadcast campaign fan-out creates a thundering herd: all fan-out workers simultaneously hammer the device registry, saturating DB read I/O and stalling normal traffic.
Fix: I rate-limit each fan-out worker to consume paginated chunks at a controlled pace — e.g., 10K tokens per second per worker — using a token bucket (a counter that refills at a fixed rate, throttling bursts). I also separate the device registry read replica pool used by fan-out workers from the one serving real-time device lookups, so campaign scans can't crowd out live traffic.
Tradeoff: Rate-limiting fan-out means large campaigns take longer to fully enqueue — delivery of a 50M-device broadcast shifts from seconds to minutes.
2APNs and FCM impose per-second rate limits per connection; naive horizontal scaling of delivery workers opens too many connections and triggers 429 rejections.
Fix: I front each gateway queue with a connection manager — a small stateful process that owns a bounded pool of persistent HTTP/2 connections (e.g., 100 connections per gateway) and multiplexes streams (concurrent requests over one connection, HTTP/2 feature) from multiple workers through them. All delivery workers route requests through this manager rather than opening direct connections. The pool size is tuned to just under the gateway's documented limit.
Tradeoff: The connection manager becomes a single point of failure; I run two instances with consistent hashing (routing the same device-token ranges to the same instance) for failover.
3Delivery status writes for 1B daily notifications create a hot write path that a single status DB can't absorb without becoming a bottleneck.
Fix: I buffer status updates in the delivery workers using a local write-back batch — accumulate 500 updates in memory and flush as a bulk insert every 200ms. I also time-partition (split DB tables by time window, e.g., daily) the status table so recent data lives in a hot partition and old data is cold-tiered to cheaper storage. The idempotency key lookup on retry checks the cache first before hitting the DB.
Tradeoff: Batching means status visibility lags by up to 200ms — acceptable for delivery receipts, but callers querying status need to account for eventual consistency.

Reference

API
POST/api/v1/notifications— Create and enqueue a notification or campaign; accepts target (user_id | segment_id | 'all'), payload, and optional schedule_time; returns campaign_id and 202 Accepted
GET/api/v1/notifications/{campaign_id}/status— Poll delivery status for a campaign; returns sent_count, delivered_count, failed_count, and state (queued | in_progress | done)
POST/api/v1/devices— Register or refresh a device token; accepts user_id, device_token, platform (ios | android); upserts the registry record; returns 200
DELETE/api/v1/devices/{device_token}— Deregister a device token on app uninstall; marks the token invalid in the registry; returns 204
GET/api/v1/notifications/{campaign_id}/failures— Retrieve failed delivery records for a campaign with error codes; paginated; returns list of {device_token, error_code, attempts}
Database & Storage
  • Relational DB (PostgreSQL) for campaigns and device registry — ACID guarantees matter for campaign state transitions and token validity flips
  • campaigns(campaign_id UUID PK, target_type VARCHAR, target_value TEXT, payload JSONB, status VARCHAR, created_at TIMESTAMPTZ, scheduled_at TIMESTAMPTZ)
  • devices(device_id UUID PK, user_id UUID, device_token VARCHAR, platform VARCHAR, valid BOOLEAN, updated_at TIMESTAMPTZ) — sharded by user_id
  • delivery_status(status_id UUID PK, campaign_id UUID, device_token VARCHAR, idempotency_key VARCHAR UNIQUE, outcome VARCHAR, attempts INT, updated_at TIMESTAMPTZ) — time-partitioned by day
  • Index on devices(user_id) for fan-out token lookups; index on delivery_status(campaign_id, outcome) for status aggregation queries
  • Distributed cache (Redis) for device token hot path — key: user_id, value: serialized list of device tokens, TTL 1hr; reduces device registry read pressure during fan-out
