Systems Design · Tier 2

Collaborative Document Editor

The hard part isn't storing documents — it's reconciling simultaneous edits from multiple users so every client converges to the same state without losing anyone's work. Interviewers use this to probe distributed consistency, real-time architecture, and your ability to reason about ordering and causality under concurrency.

Interview

Interviewer
Design a collaborative document editor like Google Docs. Where do you start?
You
Before diving in — how many concurrent editors per document, and how many total active documents? Are we supporting rich text only, or also spreadsheets and drawings? And what's the latency target for seeing a collaborator's edit on my screen?
Interviewer
Assume up to 100 concurrent editors per document, 10 million active documents globally. Rich text only. Edits should appear within 200ms for users in the same region.
You
So roughly 10M documents × say 10 average concurrent users in peak bursts = 100M active WebSocket connections across the fleet. Each user might send 2–5 operations per second while typing, so ~200–500M ops/sec globally — write-heavy and latency-sensitive. I'll target sub-100ms server processing so the 200ms budget survives a round trip. I'll design around OT (Operational Transformation — a method to reorder and adjust concurrent edits so they commute safely), with a WebSocket gateway layer and a persistent operation log as the source of truth.

Core Components

Interviewer"How do you handle 100M persistent connections without every server holding every session?"
WebSocket Gateway
  • WHY: HTTP polling (repeated requests to check for updates) can't deliver sub-200ms latency at this scale — you need a persistent, bidirectional channel.
  • HOW: I run a horizontally-scaled gateway tier where each node holds open WebSocket connections for a subset of clients. When a client opens a document, the gateway hashes the document ID to assign it to a specific collaboration session server — so all editors of document X talk to the same session server. The gateway itself is stateless; it only routes frames to the correct session server over an internal pub/sub bus.
  • TRADEOFF: Pinning all editors of a document to one session server means a session server crash evicts all active collaborators on its documents simultaneously — I mitigate this with fast reconnect and session state stored externally, not in memory.
Interviewer"Walk me through what actually happens when two users type at the same position at the same time."
OT Engine (Conflict Resolution)
  • WHY: Without transformation, user A inserting 'X' at index 5 while user B deletes index 5 simultaneously will corrupt the document — one operation must be adjusted relative to the other.
  • HOW: Each operation carries a revision number (the document version the client last saw). The session server maintains a total-ordered operation log per document. When op B arrives and the server is already at revision R+1 due to op A, the OT engine transforms B against A — adjusting B's position index so it applies correctly to the post-A document. The transformed B is then broadcast to all connected clients, and each client applies its own local mirror of OT to keep its local state consistent.
  • TRADEOFF: OT is correct for linear text but becomes exponentially complex for rich structures like tables — for those, CRDT (Conflict-free Replicated Data Type — a data structure that mathematically guarantees convergence without a central arbiter) is often preferred, at the cost of higher memory per document.
Interviewer"How do you reconstruct a document when a user opens it, or when a new collaborator joins mid-session?"
Operation Log & Snapshot Store
  • WHY: Replaying millions of ops from the beginning of a document's life to serve a page load is unacceptable — cold open must be fast.
  • HOW: I keep a persistent, append-only operation log (every edit ever made, in order) as the source of truth. On top of that, I run a background snapshotting job that periodically materializes (collapses all ops up to version N into a full document state) and writes the snapshot to object storage. On open, the server fetches the nearest snapshot and replays only the delta ops since that snapshot — typically milliseconds of ops rather than years.
  • TRADEOFF: Snapshots add write amplification and storage cost; I tune snapshot frequency based on op rate per document rather than a fixed interval.
Interviewer"How do you show live cursors and user avatars without those updates overwhelming your main edit pipeline?"
Presence & Awareness Service
  • WHY: Cursor position updates are ephemeral (lost data doesn't corrupt documents) but extremely frequent — merging them into the OT pipeline adds latency to real edits.
  • HOW: I separate presence into its own lightweight pub/sub (publish-subscribe — a messaging pattern where senders publish to topics and receivers subscribe) channel per document. Clients broadcast cursor position and selection range at ~10 Hz. The session server fans these out to co-editors over their existing WebSocket connections. Because presence state is ephemeral, I hold it only in memory on the session server — no persistence needed. Clients set a 3-second TTL (time-to-live — auto-expiry after inactivity) so stale cursors disappear automatically.
  • TRADEOFF: Separating presence from the OT pipeline means cursor positions and document state can momentarily drift apart on slow connections, but that's visually acceptable.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single session server owning a viral document (e.g. a company-wide shared roadmap with 500 simultaneous editors) becomes a CPU and memory hotspot, creating a 'hot document' problem.
Fix: I introduce a document partition proxy layer. For documents exceeding a concurrent-editor threshold (say, 200), I split the editor set into shards — each shard has its own session sub-server, and a thin coordinator merges ops between shards using a bounded merge queue. Shards see the same OT-ordered log, so convergence is preserved. Below the threshold, a single session server handles the document as before — no overhead for the common case.
Tradeoff: Cross-shard coordination adds ~5–10ms of merge latency for very large documents, which is acceptable given the alternative is a crashed session server evicting all 500 editors.
2Loading a document with millions of historical operations from the op log on every open is O(n) in op count and blows the 200ms SLA.
Fix: I run a snapshot worker that reads the op log, materializes the full document state every 1,000 ops (or every 30 minutes, whichever comes first), and writes the result to object storage. On document open, the session server fetches the latest snapshot (~1 object storage read), then replays only the delta ops since that snapshot from the op log — typically fewer than 1,000 ops, which replays in under 20ms.
Tradeoff: Snapshots consume storage proportional to document size × snapshot frequency — for very large documents with high edit rates, storage costs compound quickly.
3WebSocket connections are stateful; a load balancer restart or gateway node failure drops all active connections, causing mass reconnects that cascade into a thundering herd against session servers.
Fix: I use a connection draining strategy: before taking a gateway node offline, I signal it to stop accepting new connections and wait up to 30 seconds for in-flight ops to flush. For unplanned failures, I add jittered (randomly delayed) exponential backoff on the client reconnect — each client waits a random delay drawn from 0 to 2^attempt seconds before retrying. Session servers restore client state from the op log rather than in-memory state, so reconnected clients resync cleanly.
Tradeoff: Jittered backoff means some clients wait several seconds before reconnecting — a visible disruption, but far better than a retry storm crashing session servers.

Reference

API
POST/api/v1/documents— Create a new document; returns doc_id, initial_revision=0, and a WebSocket URL to connect for editing
GET/api/v1/documents/{doc_id}— Fetch document metadata, snapshot URL, and latest revision number for cold open
GET/api/v1/documents/{doc_id}/ops?since_revision={n}— Fetch ordered ops from revision n to HEAD; used by client to catch up after reconnect
POST/api/v1/documents/{doc_id}/ops— Submit a single operation (fallback REST path); returns transformed op and server revision
WS/ws/v1/documents/{doc_id}— Persistent WebSocket channel — bidirectional stream of ops and presence updates for active editing
GET/api/v1/documents/{doc_id}/history?page={n}— Paginated version history; returns snapshot+op-range metadata for each version checkpoint
POST/api/v1/documents/{doc_id}/share— Set sharing permissions (viewer/commenter/editor) for a user or link; returns updated ACL
Database & Storage
  • PostgreSQL — relational model for document metadata, user accounts, ACL (Access Control List — who can read/write a doc); ACID (Atomicity, Consistency, Isolation, Durability — guarantees every write fully completes or fully rolls back) for permission changes.
  • Schema: documents(doc_id UUID PK, owner_id UUID, title TEXT, created_at TIMESTAMPTZ, latest_revision INT); operations(op_id UUID PK, doc_id UUID, revision INT, user_id UUID, op_data JSONB, applied_at TIMESTAMPTZ); snapshots(doc_id UUID, revision INT, storage_url TEXT, created_at TIMESTAMPTZ, PRIMARY KEY(doc_id, revision))
  • Index: UNIQUE(doc_id, revision) on operations table ensures no two ops share the same revision per document — this is the OT ordering guarantee enforced at the DB layer; secondary index on doc_id for range scans since_revision.
  • Key tradeoff: storing op_data as JSONB gives schema flexibility for different operation types (insert, delete, format) but sacrifices the ability to index or query inside operations efficiently — acceptable since op replay is always sequential, never filtered by op content.
