Systems Design · Tier 2

Instagram

Instagram looks like a CRUD app but hides brutal fan-out problems: a single post from a celebrity with 100M followers must populate hundreds of millions of feeds near-instantly. Interviewers use it to probe how candidates handle asymmetric write amplification, media storage at petabyte scale, and the tradeoff between precomputed and on-demand feed generation.

Interview

Interviewer
Design Instagram — photo/video sharing with a social feed. Where do you start?
You
Before diving in — what scale are we targeting? Instagram-current (1B+ users) or an MVP at hundreds of millions? And are we scoping just the core feed and uploads, or do Stories and Reels count too? Finally, what's the freshness SLA on the feed — seconds or minutes is fine?
Interviewer
Assume 500M daily active users, each viewing their feed 5–10 times a day and uploading ~2M photos per hour. Focus on photo upload, the social graph, and the home feed. Feed freshness within a few seconds is ideal but up to 30 seconds is acceptable.
You
So roughly 550 photo writes/sec and around 50K–100K feed reads/sec — heavily read-skewed. I'll treat photos as blob (binary large object — raw file bytes) storage, metadata separately in a relational DB, and the feed as a precomputed timeline cached per user. The killer constraint is celebrity fan-out (one write triggers millions of feed updates), which I'll handle with a hybrid push/pull model. Storage estimate: 2M photos/hour at ~3MB average compressed = ~6TB/day, ~2PB over a year — so object storage is non-negotiable.

Core Components

Interviewer"Walk me through what happens from the moment a user hits 'post' to the photo being visible."
Photo Upload Pipeline
  • WHY: Upload is slow and CPU-heavy; blocking the client on transcoding (converting to multiple resolutions) kills UX and wastes mobile bandwidth.
  • HOW: Client uploads the raw photo directly to object storage (e.g., a distributed blob store like S3) via a pre-signed URL (a time-limited, permission-scoped upload link) the API server issues. Once upload completes, the client notifies the API server which drops a job on an async queue. Worker nodes transcode the image into multiple resolutions (thumbnail, feed, full) and write all variants back to object storage, then commit photo metadata (photo_id, user_id, S3 keys, timestamp) to the Photos table. A CDN (content delivery network — edge servers geographically close to users) is fronted on all read URLs.
  • TRADEOFF: Pre-signed direct uploads skip the API server entirely for bytes, so API servers stay stateless, but we lose the ability to inspect content synchronously before it hits storage — moderation must be async.
Interviewer"How do you store and query the follow graph efficiently?"
Social Graph Service
  • WHY: Every feed generation and notification decision requires fast follower/following lookups; a naive relational join over billions of edges is too slow.
  • HOW: Store edges in a dedicated graph store — a wide-column store (a DB that groups related columns together per row key) like Cassandra works well. Schema: `follows(follower_id UUID, followee_id UUID, created_at TIMESTAMP)` with the partition key being `follower_id` so 'who does user X follow?' is a single partition scan. Reverse mapping `followed_by(followee_id, follower_id)` in a separate table handles 'who follows celebrity Y?' for fan-out. Cache hot celebrity follower counts and first-page follower IDs in-memory.
  • TRADEOFF: Denormalizing into two tables doubles write cost but makes both query directions O(1) partition lookups instead of full scans.
Interviewer"How do you build the home feed without melting your infrastructure when a celebrity posts?"
Feed Generation Service
  • WHY: Pure push (writing to every follower's feed inbox on post) works for normal users but generates billions of writes for celebrities — fan-out-on-write at that scale is catastrophic.
  • HOW: I use a hybrid model. For regular users (< 10K followers), push their new post_id into each follower's feed queue immediately — this is fan-out-on-write (precomputing feeds at write time). For celebrities (> threshold), skip the push entirely and use fan-out-on-read (merging celebrity posts at read time). When a user opens their feed, the Feed Service pulls: (1) their precomputed inbox from a feed cache (Redis sorted set keyed by timestamp), (2) any celebrity posts from those they follow via a direct query. Results are merged, ranked, and returned.
  • TRADEOFF: Celebrity posts have slightly higher read latency (the merge step) and we need to track which accounts are 'celebrity-tier', but we avoid billions of redundant writes on viral posts.
Interviewer"With petabytes of photos, how do you handle storage costs and global read latency?"
Media Storage and CDN Layer
  • WHY: Serving raw full-res images from a single origin region at 100K reads/sec would saturate bandwidth and destroy latency for global users.
  • HOW: All photo variants live in object storage (distributed blob store) partitioned by photo_id prefix to avoid hot-prefix issues. CDN edge nodes cache the most-requested images close to users — cache hit rates for popular content routinely hit 95%+. For long-tail images (rarely accessed), CDN misses fall back to origin. I use immutable URLs with content-hash segments so CDN caching is permanent (no cache invalidation needed — the URL changes when content changes).
  • TRADEOFF: Immutable URLs mean deleted content requires CDN purge calls and token-based access control at the edge, adding operational complexity.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Feed reads for users following many celebrities all hit the same hot photo-metadata rows simultaneously, causing DB read hotspots.
Fix: I add a read replica layer (read-only DB copies that lag the primary by milliseconds) and route all feed-read queries to replicas, keeping the primary for writes only. On top of that, I cache photo metadata aggressively in a distributed in-memory cache with TTL (time-to-live — automatic expiry after N seconds) of 10 minutes. For truly viral photos, the cache hit rate approaches 99%, so the DB almost never sees repeated reads for the same photo.
Tradeoff: Replicas introduce replication lag (usually <100ms) so very fresh posts may not appear on the first feed load for some users — acceptable given our 30-second freshness SLA.
2Fan-out for normal users is synchronous — if the write queue backs up, post visibility delays spike for all followers.
Fix: I make the fan-out queue durable with at-least-once delivery guarantees (messages persist to disk, redelivered on worker crash). Workers are horizontally scaled (adding more machines to share the load) and consume from partitioned queues (each partition assigned to one worker) so throughput scales linearly with worker count. I also add a dead-letter queue (a separate queue that captures messages that repeatedly fail) so a bad message doesn't block the whole pipeline.
Tradeoff: At-least-once delivery means occasional duplicate feed entries — the feed read layer deduplicates by post_id before rendering.
3Storage costs grow unboundedly as 6TB of new photos land daily, including photos nobody ever views again.
Fix: I implement tiered storage (moving data between storage classes by access frequency). Photos not accessed in 30 days move from hot storage (low-latency, high-cost SSD-backed object store) to cold storage (high-latency, low-cost archival object store). A background job tracks per-photo last-access timestamps in a lightweight KV store (key-value store — simple lookup by ID). CDN misses on cold objects trigger an async warm-up back to hot storage if the photo starts getting traffic again.
Tradeoff: First-access latency for cold photos jumps from ~50ms to ~1–3 seconds, which is noticeable but acceptable for long-tail content.

Reference

API
POST/api/v1/media/upload-url— Returns a pre-signed upload URL + media_id; client uploads bytes directly to object store
POST/api/v1/photos— Commits photo metadata (media_id, caption, location) after upload completes; triggers fan-out
GET/api/v1/feed?cursor={ts}&limit=20— Returns paginated feed of post objects for the authenticated user, cursor-based for consistency
POST/api/v1/users/{user_id}/follow— Creates follow edge; returns updated follower count
DELETE/api/v1/users/{user_id}/follow— Removes follow edge; async cleanup of that user's posts from caller's feed cache
GET/api/v1/photos/{photo_id}— Returns photo metadata + CDN URLs for all resolution variants
Database & Storage
  • PostgreSQL (sharded by user_id) — structured metadata with strong consistency; users and photos tables fit relational model
  • Schema: photos(photo_id UUID PK, user_id UUID, s3_key_thumb TEXT, s3_key_feed TEXT, s3_key_full TEXT, caption TEXT, created_at TIMESTAMPTZ, like_count INT)
  • Schema: users(user_id UUID PK, username TEXT UNIQUE, display_name TEXT, bio TEXT, avatar_s3_key TEXT, created_at TIMESTAMPTZ)
  • Cassandra — social graph edges; partition key = follower_id for O(1) 'who do I follow?' scans; separate table with partition key = followee_id for fan-out lookups
  • Schema (graph): follows(follower_id UUID, followee_id UUID, created_at TIMESTAMP, PRIMARY KEY (follower_id, followee_id))
  • Redis — feed timelines as sorted sets (score = post timestamp), user sessions, and hot photo metadata with 10-minute TTL
  • Object Store (S3-compatible) — all photo binary data; keys structured as {user_id_prefix}/{photo_id}/{resolution}.jpg for efficient prefix-based listing
  • Index strategy: photos table indexed on (user_id, created_at DESC) for profile page queries; users table indexed on username for search
  • Key tradeoff: sharding photos by user_id makes per-user queries fast but risks hot shards for celebrities — mitigated by read replicas and caching above the DB layer
