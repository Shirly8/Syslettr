Payment System

Payment systems are deceptively hard because money is stateful — a double-charge or missed refund is a real-world disaster, not just a bug. Interviewers use this problem to probe consistency guarantees, distributed transaction patterns, and failure recovery under partial network outages.

Interview

Interviewer
Design a payment processing system like the one behind a major e-commerce platform. Users can pay for orders, request refunds, and view transaction history. Where do you start?
You
A few quick questions before I structure anything. What's the transaction volume — thousands per second or hundreds of thousands? Are we building the card-network integration ourselves or sitting on top of a payment processor like Stripe? And what's the acceptable failure mode — is it worse to double-charge or to miss a charge?
Interviewer
Assume 50,000 transactions per second at peak, globally distributed. You're sitting on top of an external payment processor — your job is everything between the user and that processor. Missing a charge is worse than a declined retry; double-charging is catastrophic.
You
Got it. 50K TPS (transactions per second) means ~4.3 billion transactions per day at peak — though realistically with flash sales we should plan for 3x bursts, so ~150K TPS headroom. The core constraint is exactly-once execution: every payment must complete exactly once even if the network drops mid-flight or a server crashes. I'll center the design on idempotency keys (client-generated tokens that deduplicate retries), an event-driven ledger (append-only log of all money movements), and strong consistency for balance reads. Latency SLA I'll target p99 (99th percentile — worst 1% of requests) under 500ms for the payment initiation path.

Core Components

Interviewer"How do you guarantee a payment isn't processed twice if the client retries after a timeout?"
Idempotency Layer
  • WHY: Without this, a client retry after a dropped connection charges the user twice — a trust-destroying bug.
  • HOW: The client generates a UUID idempotency key and sends it with every payment request. My API gateway writes this key plus a 'pending' status to a Redis (in-memory key-value store) entry with a 24-hour TTL (time-to-live — expiry duration) before forwarding to the payment service. Any retry with the same key hits the cache and returns the stored result — the processor is never called again.
  • TRADEOFF: Redis is not durable by default — a crash between writing the key and committing the DB record creates a gap; I mitigate this with Redis AOF persistence (append-only file — writes every operation to disk before acknowledging) but it adds ~1ms write latency.
Interviewer"Walk me through what happens internally when a payment request arrives — how do you coordinate with the external processor and ensure the record is committed exactly once?"
Payment Orchestration Service
  • WHY: Without a coordinator, partial failures between DB write and processor call leave money in an undefined state — charged but not recorded, or recorded but not charged.
  • HOW: I use the outbox pattern (write the payment intent to a local DB transaction alongside an 'outbox' event row — both commit atomically, then a relay process reads the outbox and calls the external processor). If the processor call fails, the relay retries from the outbox. Once the processor confirms, the relay marks the record 'settled' and publishes a completion event to the event bus.
  • TRADEOFF: The outbox relay introduces ~100-200ms additional latency versus a direct synchronous call, but eliminates the dual-write problem (non-atomic writes to two systems that can diverge on failure).
Interviewer"How do you model the financial state — how do you know at any point what a user's balance is and that the books balance?"
Ledger Service
  • WHY: A mutable balance field is easy to corrupt under concurrent writes; if it's wrong, you can't audit how you got there.
  • HOW: I store an append-only double-entry ledger (every transaction creates two rows — a debit on one account, a credit on another — so the sum of all entries is always zero). Balance is derived by summing ledger entries, but that's expensive, so I maintain a materialized balance table updated by the ledger writer and reconcile it nightly against the full ledger sum.
  • TRADEOFF: Balances are eventually consistent (a few seconds behind the ledger) during high write bursts; real-time balance reads must query the ledger directly, which is slower.
Interviewer"Where does fraud detection fit in the payment flow — synchronous or asynchronous?"
Fraud Detection Service
  • WHY: Skipping fraud checks lets bad actors drain accounts; blocking the payment path on a slow ML model kills latency.
  • HOW: I run a fast rule-based check synchronously (velocity limits, known bad cards, country blocks) — this takes <10ms. A heavier ML model runs asynchronously post-authorization: if it flags the transaction, I trigger a hold and notify the user. High-risk signals from the ML model feed back into the rule engine within minutes via a feature store (low-latency read store for ML feature vectors).
  • TRADEOFF: Async ML means some fraudulent transactions are authorized before the model catches them — acceptable for most fraud profiles, not for high-velocity card-testing attacks, which the synchronous rules must handle.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1At 150K TPS burst, synchronous calls from the orchestrator to the external processor become the chokepoint — the processor's rate limits and latency crush throughput.
Fix: I decouple the orchestrator from the processor using the outbox pattern with a dedicated relay pool. The relay maintains a connection pool to the processor and sends charges asynchronously, so the orchestrator just writes to the DB and returns a 'pending' response to the client immediately. Webhooks from the processor confirm settlement. This converts a synchronous latency dependency into a throughput-controlled async queue.
Tradeoff: Payments now go through a 'pending' state visible to users — the UX has to communicate that the charge is processing, not instant, which requires product design changes.
2A single PostgreSQL primary handling 150K TPS write spikes will saturate disk I/O and lock contention, especially on the ledger table.
Fix: I partition (split the table by a range or hash key — here, partition by user_id range) the ledger table across multiple DB shards (independent DB instances each owning a partition). Each shard handles writes for a user subset. Cross-shard queries for reporting are served by the async analytics store, not the OLTP (online transaction processing — optimized for concurrent short writes) primary.
Tradeoff: Cross-user transactions (e.g. a marketplace payout that debits merchant and credits platform) now span shards — I handle these with a saga pattern (sequence of local transactions with compensating rollbacks), which adds complexity.
3Fraud ML model latency spikes to 800ms under load, blocking the synchronous pre-auth path and causing timeouts.
Fix: I move the ML model fully async post-authorization — only the rule-based engine (velocity checks, block lists) runs synchronously, target <15ms. After the processor authorizes, I publish the transaction event to the fraud queue; the ML service consumes it and can trigger a hold within seconds if it flags the transaction.
Tradeoff: A small window exists where a fraudulent transaction is authorized before the ML model runs; chargebacks for this window are the business cost of the latency improvement.

Reference

API
POST/api/v1/payments— Initiates a payment; requires idempotency-key header; returns payment_id and status=pending
GET/api/v1/payments/{payment_id}— Returns current payment status (pending/settled/failed) and metadata
POST/api/v1/payments/{payment_id}/refund— Initiates full or partial refund; idempotency-key required; returns refund_id and status
GET/api/v1/accounts/{account_id}/transactions— Paginated ledger history for an account; cursor-based pagination; max 100 per page
POST/api/v1/webhooks/processor— Internal endpoint for external processor callbacks; HMAC-signed; updates payment status to settled or failed
Database & Storage
  • PostgreSQL — ACID guarantees essential for financial records; supports row-level locking and serializable isolation
  • Schema: payments(payment_id UUID PK, account_id UUID, amount_cents BIGINT, currency CHAR(3), status VARCHAR(20), idempotency_key VARCHAR(128) UNIQUE, processor_ref VARCHAR(128), created_at TIMESTAMPTZ, settled_at TIMESTAMPTZ)
  • Schema: ledger_entries(entry_id UUID PK, payment_id UUID, account_id UUID, direction CHAR(1), amount_cents BIGINT, balance_after BIGINT, created_at TIMESTAMPTZ) — partitioned by account_id hash mod 16
  • Indexes: payments(idempotency_key) unique for dedup lookups; payments(account_id, created_at DESC) for history queries; ledger_entries(payment_id) for reconciliation joins
  • Ledger is append-only — no UPDATE or DELETE ever issued; balance correctness auditable by summing all entries; balance_after is denormalized for fast current-balance reads but reconciled nightly against the true sum
