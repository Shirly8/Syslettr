Distributed Job Scheduler

A distributed job scheduler sounds like a simple cron replacement, but guaranteeing exactly-once execution across flaky workers, clock skew, and partial failures is genuinely hard. Interviewers use it to probe distributed systems fundamentals: consensus, idempotency, and failure recovery under real constraints.

Interview

Interviewer
We want to build a distributed job scheduler — something that can run millions of jobs reliably across many machines. Where do you start?
You
Before diving in — what's the job volume? Millions per day or per second? Are jobs one-off or recurring? And what's the execution SLA — fire-and-forget, or do we need at-least-once delivery with result tracking?
Interviewer
About 100 million jobs per day, mix of one-off and recurring (cron-style). Jobs must execute at-least-once, and we need status tracking — submitted, running, succeeded, failed. P99 end-to-end scheduling latency under 5 seconds.
You
So roughly 1,160 job submissions per second on average, with burst headroom to maybe 5x that. At-least-once means I need idempotency (jobs are safe to retry without side effects) baked into every worker. I'll design around three planes: a scheduling plane that decides when jobs run, a dispatch plane that queues them, and an execution plane of workers that pick them up. I'll plan storage for job metadata at ~500 bytes per job — about 50GB per day, 18TB per year, manageable in a partitioned SQL store.

Core Components

Interviewer"How do you store and look up jobs efficiently, especially recurring ones that need to fire millions of times?"
Job Metadata Store
  • WHY: Without durable metadata, a scheduler restart loses all pending and recurring job definitions.
  • HOW: I use a partitioned relational database sharded (split across DB machines) by job_id. Each job row holds the schedule expression (cron string or exact timestamp), current status, next_run_at, and an idempotency key (unique token to detect duplicate executions). For recurring jobs, after each dispatch I compute and write the next_run_at atomically in the same transaction that marks the current run as dispatched — prevents double-dispatch on restart.
  • TRADEOFF: Sharding by job_id gives even write distribution but range scans on next_run_at require a secondary index across shards, which is expensive to keep consistent.
Interviewer"How does the scheduler know when a job is due, and how do you avoid multiple scheduler instances firing the same job?"
Scheduling Engine (Trigger Loop)
  • WHY: Without a coordinated trigger mechanism, two scheduler instances polling the same DB will double-dispatch the same job.
  • HOW: I run multiple scheduler nodes but use optimistic locking (version field incremented on update — only the node that wins the CAS wins the dispatch) on each job row. Each node polls its assigned shard partition for rows where next_run_at <= now() AND status = 'pending'. The winner atomically sets status = 'dispatched' and publishes to the dispatch queue. Nodes use a consistent hash ring so each shard is owned by one scheduler node, with failover via leader election using a distributed lock (e.g., a TTL-based lock in a strongly consistent store).
  • TRADEOFF: Optimistic locking means contention under high throughput causes retries and latency spikes; too-frequent polling burns DB read capacity.
Interviewer"What happens between the scheduler deciding a job should run and a worker actually picking it up?"
Dispatch Queue
  • WHY: Without a durable queue between scheduler and workers, a worker crash before completing means the job is silently lost.
  • HOW: I publish dispatched jobs to a partitioned, durable message queue. Workers pull messages with a visibility timeout (message is hidden from other consumers while one worker holds it — like a lease). If the worker doesn't ACK within the timeout, the message reappears and another worker picks it up. Workers write a run_log row with the idempotency_key before doing any work, so a re-delivered message gets rejected at the DB layer if already processed.
  • TRADEOFF: Visibility timeouts must be longer than the slowest expected job, or you get spurious re-deliveries; too long means slow failure detection.
Interviewer"How do workers handle failures, and how do you prevent runaway jobs from starving others?"
Worker Pool
  • WHY: Without isolation and timeout enforcement, a single stuck job can block a worker thread indefinitely, starving all other jobs.
  • HOW: Workers are stateless processes in an auto-scaling group. Each job runs in a subprocess with a hard wall-clock timeout enforced by the worker harness. On completion the worker ACKs the queue message and writes status + result to the job store. On failure or timeout the worker NACKs (negative acknowledge — returns the message to the queue) up to a configured retry limit, then dead-letters (moves to a separate failure queue for inspection) the job. I use priority queues — one queue tier per job priority level — so high-priority jobs aren't blocked by a flood of low-priority ones.
  • TRADEOFF: Subprocess isolation adds ~50ms overhead per job; fine for long jobs, noticeable for sub-second ones.
Interviewer"Clients want to poll for job status — how do you make that efficient without hammering the job store?"
Status & Result Tracking
  • WHY: Thousands of clients polling the DB directly for job status will saturate read capacity and inflate costs.
  • HOW: I put a read-through cache (cache checks itself first; on miss, fetches from DB and populates) in front of the job store keyed by job_id. TTL (time-to-live — how long a cache entry is kept before expiry) is short (5s) for running jobs and longer (60s) for terminal states (succeeded/failed) since terminal state never changes. Workers push status updates via a lightweight pub/sub channel so interested clients can subscribe instead of poll; polling is the fallback.
  • TRADEOFF: Short TTL on running jobs means cache hit rate is low for frequently-polled active jobs, so the cache helps most for terminal lookups.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Polling the job store for due jobs at high frequency generates enormous read load on the DB, especially with millions of pending rows.
Fix: I introduce a sorted set in a cache layer (keyed by next_run_at score) as a fast due-job index. Scheduler nodes query the cache for jobs due in the next N seconds and only hit the DB to confirm and lock those specific rows. This reduces DB read fan-out by ~95% since the hot polling path never touches the DB directly. The cache is repopulated from the DB on startup or cache miss.
Tradeoff: Cache is not the source of truth — a cache failure or stale entry means jobs may be delayed until the next DB-backed reconciliation sweep.
2A single scheduler node owning a shard is a single point of failure — if it crashes, all jobs on that shard stall until a new node acquires the lease.
Fix: I set the lock TTL short enough (15–30s) that failover is fast. A standby scheduler node continuously tries to acquire any expired shard lease. I also run a sweeper process that periodically scans for jobs stuck in 'dispatched' state longer than their expected execution time and re-queues them — this catches any jobs that slipped through during a failover window.
Tradeoff: Short TTL means a slow-but-alive scheduler node may lose its lease and cause a brief double-dispatch window; idempotency at the worker layer is the last-line defense.
3At-least-once delivery can cause duplicate job executions when a worker crashes after doing work but before ACKing the queue.
Fix: Workers write a run_log row with the idempotency_key (derived from job_id + run_attempt number) inside a DB transaction before executing any side effects. On re-delivery the worker checks for an existing run_log row with that key — if found, it skips execution and ACKs immediately. This makes the execution path idempotent at the storage layer regardless of how many times the message is delivered.
Tradeoff: Every job execution requires an extra DB write and read for the idempotency check, adding latency and DB load proportional to job throughput.

Reference

API
POST/api/v1/jobs— Submit a new job; body includes schedule, payload, priority, idempotency_key; returns job_id and status=pending
GET/api/v1/jobs/{job_id}— Fetch current job status, last_run_at, next_run_at, result; served from cache with DB fallback
DELETE/api/v1/jobs/{job_id}— Cancel a pending or recurring job; sets status=cancelled atomically; in-flight run completes
GET/api/v1/jobs/{job_id}/runs— Paginated list of historical run attempts with status, start_time, duration, error for auditing
PATCH/api/v1/jobs/{job_id}— Update schedule expression or payload for a recurring job; takes effect on next trigger cycle
Database & Storage
  • Sharded relational DB — ACID transactions needed for CAS dispatch and idempotency_key uniqueness enforcement
  • Schema: jobs(job_id UUID PK, owner_id UUID, schedule TEXT, status ENUM, next_run_at TIMESTAMPTZ, idempotency_key TEXT UNIQUE, payload JSONB, version INT, created_at TIMESTAMPTZ)
  • Schema: run_log(run_id UUID PK, job_id UUID FK, attempt INT, idempotency_key TEXT UNIQUE, status ENUM, started_at TIMESTAMPTZ, finished_at TIMESTAMPTZ, result JSONB)
  • Primary index on jobs(next_run_at, status) per shard — enables efficient due-job polling; secondary index on jobs(owner_id) for user-facing list queries
  • Sharding by hash(job_id) distributes writes evenly but requires scatter-gather for owner_id queries — acceptable since scheduling is the hot path, not listing
