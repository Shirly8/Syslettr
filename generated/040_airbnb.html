Systems Design · Tier 2

Airbnb

Airbnb's core challenge is coordinating real-time inventory (property availability) across a distributed system where two guests can attempt to book the same night simultaneously. It's asked in interviews because it combines geo-search, calendar-based filtering, and transactional consistency in a single product.

Interview

Interviewer
Design the core Airbnb platform — search, listing pages, and booking. Where do you start?
You
Before diving in — what's the user scale? Tens of millions of active users or hundreds of millions? Are we building the full platform including payments, or focusing on search and booking? And what's the acceptable booking failure rate — do we tolerate occasional double-books or is that a hard zero?
Interviewer
100 million monthly active users, roughly 6 million active listings globally. Focus on search, listing detail, and booking — payments are a black box. Zero double-bookings is a hard requirement.
You
So roughly 100M MAU — assuming 10% book in a given month, that's 10M bookings/month, or about 4 bookings/sec at peak. Search is far heavier — maybe 500 searches/sec sustained, 2–3x that at peak. With 6M listings each having calendar data, that's roughly 6M * 365 * 2 years of availability = ~4.4B availability records to store. The zero double-book constraint means I need pessimistic locking (holding a DB lock during a transaction so no concurrent write can interfere) or idempotent reservation slots — I'll come back to that. I'll design around: geo-search index, availability service, and a booking service with strong transactional guarantees.

Core Components

Interviewer"How does search actually work when I filter by location, dates, and price? That's a lot of dimensions to filter simultaneously."
Search Service
  • WHY: A naive SQL query joining listings, availability, and geo data at 500 req/sec would be far too slow — we need a purpose-built search index.
  • HOW: I'd push listing metadata into Elasticsearch (a distributed search engine optimized for full-text and geo queries). Each listing document contains location as a geo_point (a lat/lng pair Elasticsearch can index spatially), price, amenities, and a precomputed availability bitmap (a bitfield where each bit represents one day — 1 = available). When a search comes in, I filter by geo bounding box, price range, and then check the availability bitmap for the requested date range using a bitwise AND. This keeps the search layer stateless and fast — no joins.
  • TRADEOFF: The availability bitmap in Elasticsearch is eventually consistent with the source of truth, so a listing might appear available in search but fail at booking — we accept that and handle it at booking time.
Interviewer"How do you store and query availability for 6 million listings across a rolling 2-year window without it becoming a bottleneck?"
Availability Service
  • WHY: Availability is queried on every listing page load and every search — it must be sub-10ms or the UX breaks.
  • HOW: I store availability as a per-listing bitset (one bit per calendar day, 730 bits for 2 years) in Redis, keyed by listing ID. A check-in/check-out range query becomes a BITCOUNT on a slice of that key — extremely fast. The source of truth is a Postgres table with one row per listing per blocked date, which we sync into Redis on write. When a host blocks dates, we update Postgres first, then set the bits in Redis. On cache miss, we rebuild the bitset from Postgres.
  • TRADEOFF: Storing availability in Redis means we need careful cache invalidation on every booking or host calendar update — a stale bit could show a booked night as available in search.
Interviewer"Walk me through exactly how you prevent two guests from booking the same listing on the same night."
Booking Service
  • WHY: Without a serialization point (a place where concurrent requests are forced to execute one at a time), two simultaneous booking requests can both read 'available', both commit, and create a double-booking.
  • HOW: I use a database-level row lock on the availability record. When a booking request arrives, I open a Postgres transaction, SELECT FOR UPDATE on all date rows for that listing (which acquires an exclusive lock on those rows), verify they're all still available, insert the booking, mark dates as blocked, and commit. Any concurrent request trying to lock the same rows blocks until the first transaction commits or rolls back. This is pessimistic locking — it's slower than optimistic approaches but guarantees zero double-books.
  • TRADEOFF: SELECT FOR UPDATE serializes requests per listing, which limits throughput on high-demand listings — a hot listing during a surge (e.g., New Year's Eve in NYC) becomes a serialization bottleneck.
Interviewer"How do you handle the listing creation flow — photos, descriptions, and making it searchable?"
Listing Ingestion & CDN
  • WHY: Photos are large blobs (2–10MB each) that can't go through the API tier — they need a direct upload path or the API servers become I/O-saturated.
  • HOW: I use a presigned URL flow (a short-lived URL the client uploads directly to object storage, bypassing our servers). The client calls our API to get a presigned S3 URL, uploads the image directly to S3, then calls our API to confirm upload. A background worker picks up a Kafka event (a durable distributed message queue), generates thumbnails, and updates the listing record. Once the listing is saved to Postgres, a CDC (change data capture — a stream of DB write events) worker syncs it into Elasticsearch so it's searchable.
  • TRADEOFF: The async indexing pipeline means a newly created listing isn't searchable for up to 30 seconds — acceptable for a marketplace, but we should communicate this to hosts.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Hot listings (e.g., a popular NYC loft during New Year's) serialize all booking attempts through a single Postgres row lock, collapsing throughput to near-zero for that listing.
Fix: I add a Redis-based distributed lock (a lock held in Redis using SET NX EX — set if not exists, with expiry) as a fast pre-filter before hitting Postgres. Requests for a given listing compete for the Redis lock first; the winner proceeds to Postgres SELECT FOR UPDATE, while losers get an immediate 'unavailable' response rather than queuing at the DB. This caps DB concurrency per listing at 1 without holding DB connections open while other requests spin.
Tradeoff: If the Redis node holding the lock fails mid-transaction, we need Redlock (a multi-node distributed lock protocol) or we risk two processes holding the lock simultaneously — adding operational complexity.
2Search at 500–1500 req/sec with geo, date, and price filters on 6M listings makes Elasticsearch the primary read bottleneck — query latency spikes under load.
Fix: I add a two-layer cache in front of Elasticsearch. First, an application-level cache (Redis) for popular search queries (e.g., 'Paris, 2 adults, this weekend') keyed by a hash of search params, with a 60-second TTL (time-to-live — expiry after which the cache entry is deleted). Second, I pre-warm cache entries for top-100 city/date combinations using an offline job that runs every 30 minutes. This turns the majority of peak traffic into Redis lookups at sub-millisecond latency.
Tradeoff: A 60-second TTL means availability shown in search results can be 60 seconds stale — a listing that just got booked can still appear in results, but we handle that gracefully at booking time.
3Photo uploads through the API tier saturate server bandwidth and I/O when multiple hosts upload high-res images simultaneously.
Fix: I route uploads around the API tier entirely using presigned S3 URLs (short-lived upload credentials generated by our API that let clients write directly to S3). The client requests a presigned URL from our API (a lightweight call returning a token), uploads directly to S3 (bypassing all our servers), then POSTs a confirmation to our API. Our API never touches the binary data — it only handles metadata.
Tradeoff: We lose the ability to validate image content (e.g., NSFW detection) inline — that has to move to an async post-upload worker, so a bad image is briefly stored before it's caught.

Reference

API
GET/api/v1/search?lat=40.7&lng=-73.9&checkin=2024-12-31&checkout=2025-01-02&guests=2&price_max=300— Returns paginated listing summaries matching geo+date+price filters; availability pre-filtered via ES bitmap
GET/api/v1/listings/{listing_id}?checkin=2024-12-31&checkout=2025-01-02— Returns full listing detail, photos (CDN URLs), and confirmed availability for given date range
POST/api/v1/listings/{listing_id}/bookings— Creates a booking; body: {checkin, checkout, guests, payment_token}; acquires row lock, returns booking_id or 409 conflict
GET/api/v1/bookings/{booking_id}— Returns booking status, listing summary, and host contact info for confirmed bookings
POST/api/v1/listings/{listing_id}/photos/upload-url— Returns a presigned S3 URL for direct client upload; body: {filename, content_type}
PUT/api/v1/listings/{listing_id}/availability— Host blocks or unblocks dates; body: {dates: [...], blocked: bool}; updates Postgres then Redis bitset
Database & Storage
  • Postgres — source of truth for listings, bookings, and blocked dates; ACID transactions required for booking integrity
  • Schema: listings(listing_id UUID PK, host_id UUID, title TEXT, lat FLOAT, lng FLOAT, price_per_night INT, created_at TIMESTAMPTZ) | bookings(booking_id UUID PK, listing_id UUID FK, guest_id UUID, checkin DATE, checkout DATE, status ENUM, created_at TIMESTAMPTZ) | blocked_dates(listing_id UUID, date DATE, reason ENUM, PRIMARY KEY(listing_id, date))
  • Indexes: listings(lat, lng) for geo queries (partial index); blocked_dates(listing_id, date) composite PK doubles as range scan index; bookings(listing_id, checkin, checkout) for overlap detection
  • Elasticsearch — secondary index for search only; documents denormalize listing metadata + availability bitmap; updated via CDC pipeline, not written by API directly
  • Redis — availability bitsets keyed by listing_id (BITFIELD, 730 bits per listing); also used for search result caching (TTL 60s) and distributed booking locks (SET NX EX 10)
  • Tradeoff: The Postgres + Elasticsearch + Redis triad means three systems must stay in sync — CDC lag and cache TTLs create windows of stale data, which is acceptable everywhere except the booking transaction itself
