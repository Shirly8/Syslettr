Systems Design · Tier 1

Monitoring & Alerting System

A monitoring system must ingest millions of data points per second while simultaneously querying that same data for dashboards and alert evaluation — two workloads with almost opposite optimization requirements. Interviewers use it to probe time-series data modeling, write amplification, and how candidates think about reliability in a system whose job is to report on reliability.

Interview

Interviewer
We want to build an internal monitoring and alerting system — think something like Datadog or Prometheus at scale. Where do you start?
You
Before diving in — what's the source of metrics? Are we talking infrastructure hosts, application services, or both? What's the cardinality we expect — tens of thousands of unique metric series or hundreds of millions? And what's the SLA on alert delivery: best-effort or guaranteed sub-minute?
Interviewer
Both infra and app metrics. Assume 100,000 hosts each emitting 200 metrics every 10 seconds. Alerts must fire within 60 seconds of a threshold breach. Dashboards need p99 query latency under 2 seconds over 30-day windows.
You
So 100K hosts × 200 metrics ÷ 10s = 2 million data points per second on ingestion. Each data point is a time-series sample (a {metric_name, tags, timestamp, value} tuple) — roughly 100 bytes, so ~200MB/s raw write throughput. Over 30 days that's about 500TB before compression; time-series data compresses 10–20x, so call it ~30TB stored. I'll design around a write-optimized ingestion path that fans into a TSDB (time-series database, a DB built for append-heavy numeric streams), a separate alert evaluation loop, and a notification fanout layer.

Core Components

Interviewer"Two million writes per second is a lot. How do you keep ingestion from becoming a bottleneck or dropping data?"
Metrics Ingestion Pipeline
  • WHY: If ingestion blocks on storage writes, backpressure (upstream pressure causing senders to slow or drop) cascades to the emitting agents — you lose the very data you need during an incident.
  • HOW: Agents on each host push metric batches every 10s over UDP or a lightweight TCP protocol to a fleet of stateless ingest nodes. Those nodes parse, validate, and publish to a distributed write-ahead log (a durable ordered log; Kafka fits here). Consumers pull from the log and write to the TSDB in configurable batch sizes — decoupling ingest rate from storage write rate. The log acts as a buffer: if the TSDB slows down, data queues rather than dropping.
  • TRADEOFF: The queue adds ~5–15 seconds of end-to-end latency before data lands in storage, so real-time alert evaluation must read from the log directly, not from the TSDB.
Interviewer"How do you actually store 30TB of time-series data and still serve 30-day range queries under 2 seconds?"
Time-Series Storage (TSDB)
  • WHY: Naive row-per-sample storage in a relational DB (a DB that stores data in tables with rows and columns) collapses under range scans — reading 30 days of a metric at 10s granularity means 259,200 rows per series per query.
  • HOW: I'd use a columnar storage format (stores all values for a column together on disk, enabling fast range scans) with delta-XOR compression (encodes the difference between consecutive timestamps/values, achieving 10–20x compression). Data is partitioned into time-bounded chunks — say, 2-hour blocks — so a query narrows down to a small set of chunks rather than scanning everything. Hot chunks (last 24 hours) live on fast SSD nodes; older chunks are tiered (moved) to cheaper object storage. An index maps {metric_name + tag set} → chunk locations.
  • TRADEOFF: Tiered storage introduces a latency cliff — queries touching cold data on object storage can spike to 5–10 seconds without aggressive pre-warming.
Interviewer"How does the alert engine decide when to fire, and how do you avoid both missed alerts and alert storms?"
Alert Evaluation Engine
  • WHY: Evaluating alert rules against millions of series every 15–30 seconds is CPU-intensive; naive approaches either fall behind real-time or over-fire during transient spikes.
  • HOW: Each alert rule (e.g., 'CPU > 90% for 5 consecutive minutes') is a stateful task assigned to a worker in a consistent-hash ring (a ring that maps keys to workers so re-sharding affects minimal tasks). Workers tail the write-ahead log directly — bypassing the TSDB for freshness — and maintain a per-series state machine: OK → PENDING → FIRING. A rule only transitions to FIRING after the threshold holds for the configured duration window, which suppresses transient spikes. De-duplication runs at the notification layer: identical alert fingerprints within a 5-minute window collapse into one notification.
  • TRADEOFF: Reading from the log rather than the TSDB means alert evaluators can't easily backfill historical context for complex anomaly rules.
Interviewer"An alert fires — how does it actually reach the right on-call engineer without drowning them in duplicates?"
Notification Fanout & Routing
  • WHY: Without routing logic, a single cascading failure that trips 10,000 alert rules generates 10,000 pages to the same on-call — which is worse than no monitoring at all.
  • HOW: The notification service receives FIRING events and applies a routing tree: labels on the alert (team, severity, environment) map to a route that selects the channel (PagerDuty, Slack, email) and the inhibition rules (rules that suppress child alerts when a parent is already firing — e.g., suppress host-level CPU alerts if a datacenter-level network alert is active). It also applies grouping — batching alerts with the same labels into a single notification per route per 5-minute window. Delivery is async via a queue to absorb storm bursts.
  • TRADEOFF: Grouping and inhibition add configuration complexity — misconfigured rules can silently swallow real incidents.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1High-cardinality metrics (e.g., per-request trace IDs as tags) explode the series index — millions of unique time series exhaust memory in the index and cause write amplification (more disk writes than logical data written) in the TSDB.
Fix: I'd enforce a cardinality budget at ingestion: the ingest node checks a bloom filter (a probabilistic data structure that quickly says 'definitely not seen' or 'maybe seen') against known series; new series beyond the budget are rejected with a 429 and an error label. Separately, I'd strip high-cardinality tag dimensions at the SDK level before they ever enter the pipeline. Existing high-cardinality data gets downsampled — aggregated into coarser resolutions — on the compaction pass.
Tradeoff: Hard cardinality limits mean some legitimate high-dimension metrics (per-user latency breakdown) can't be stored at full granularity.
2A single large incident triggers thousands of simultaneous alert state transitions, overwhelming the notification service and spamming on-call channels.
Fix: I'd add a queue between the alert eval workers and the notification service, so bursts are absorbed rather than dropped or causing timeouts. The notification service consumes from the queue at a controlled rate and applies grouping — collapsing all alerts sharing the same {team, severity, environment} labels within a 5-minute window into one notification. Inhibition rules additionally suppress lower-severity alerts when a datacenter-level alert is already active.
Tradeoff: Grouping delays delivery of the first notification by up to the grouping window (5 minutes), which conflicts with the 60-second alert SLA — so the first occurrence in a group fires immediately, and subsequent ones are batched.
3Dashboard range queries over 30 days touch hundreds of cold chunks on object storage, blowing the 2-second p99 latency (99th percentile — the slow tail, not the average) target.
Fix: I'd pre-compute rollup aggregates (downsampled views at 5m, 1h, 1d resolutions) during compaction and store them as separate chunk sets. The query router selects the coarsest resolution that satisfies the requested step interval — a 30-day query with minute-level granularity doesn't need raw 10-second samples. For frequently accessed time ranges (last 7 days), I'd keep rollups pinned on SSD rather than letting them tier to cold storage.
Tradeoff: Rollups lose sub-resolution precision — a 1-hour rollup can't show a 30-second CPU spike that didn't persist long enough to distort the hourly average.

Reference

API
POST/api/v1/metrics/ingest— Accepts a batch of time-series samples [{metric, tags, timestamp, value}]; returns 204 on success, 429 if cardinality budget exceeded
GET/api/v1/query_range— Query metric by selector + time range + step; returns time-aligned value arrays; routes to TSDB rollup or raw chunks based on step
POST/api/v1/alerts/rules— Create or update an alert rule (expression, duration, labels, routing); returns rule ID and eval schedule
GET/api/v1/alerts/active— List currently FIRING alerts with labels and start time; supports filtering by team and severity
DELETE/api/v1/alerts/rules/{rule_id}— Deactivate an alert rule; in-flight PENDING state for that rule is resolved as OK
GET/api/v1/series— List distinct series matching a label selector; used by dashboard autocomplete; capped at 10K results to protect index
Database & Storage
  • TSDB (e.g., column-store with delta-XOR encoding): purpose-built for append-heavy numeric time-series with fast range scans — a relational DB can't match its compression or scan performance at this volume
  • Schema: chunks(series_id BIGINT PK, chunk_start_ts BIGINT PK, chunk_end_ts BIGINT, resolution_secs INT, data BYTES) — one row per compressed 2-hour block per series
  • Schema: series_index(series_id BIGINT PK, metric_name VARCHAR, tags JSONB, created_at BIGINT) — tags are indexed with a GIN index (inverted index that maps tag values to matching series IDs) for O(log n) label-set lookups
  • Schema: alert_rules(rule_id UUID PK, team VARCHAR, expression TEXT, for_duration_secs INT, severity VARCHAR, routing_labels JSONB, updated_at BIGINT)
  • Schema: alert_state(rule_id UUID, series_id BIGINT, state ENUM(OK,PENDING,FIRING), transitioned_at BIGINT, PRIMARY KEY(rule_id, series_id)) — written by alert eval workers, read by notification service
  • Chunk index partitioned by chunk_start_ts (range partitioning — splits table by time ranges so old partitions can be dropped or archived without full-table scans)
  • Series index kept entirely in memory on index nodes (fits in ~50GB for 100M series at ~500 bytes/entry) — disk is only for durability via WAL (write-ahead log replay on restart)
  • Key tradeoff: storing alert state in a relational store (rather than in-memory on workers) makes it durable across restarts but adds ~5ms of write latency per state transition — acceptable given 60-second alert SLA
