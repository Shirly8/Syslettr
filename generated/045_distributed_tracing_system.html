Systems Design · Tier 2

Distributed Tracing System

The hardest part isn't collecting traces — it's doing it at near-zero overhead across thousands of services while keeping data queryable for days. Interviewers use this problem to probe sampling strategies, write-heavy storage design, and how you reason about observability infrastructure that can't itself become a bottleneck.

Interview

Interviewer
We want to build a distributed tracing system — something like Jaeger or Zipkin — for our microservices platform. Where do you start?
You
Before diving in — what's the scale? How many services, and roughly how many requests per second flow through them? Are we doing head-based or tail-based sampling, or do we need to support both? And what's the retention window — hours, days, weeks?
Interviewer
About 500 services, 100K requests per second at peak. Tail-based sampling is preferred but head-based should be configurable. Retain traces for 7 days, with p99 query latency (99th percentile — the slow tail, not the average) under 2 seconds.
You
Got it. At 100K RPS with an average of ~20 spans (a single timed operation within one service) per request, that's 2M spans/sec at peak. Even at 1% tail sampling that's 20K spans/sec persisted — still significant write volume. Each span is roughly 1–2KB, so sustained storage write is ~20–40MB/sec, or about 12–25TB over 7 days. I'll design around a high-throughput ingest pipeline, a central span collector with tail-sampling buffers, and a columnar (column-oriented, optimized for analytical reads) store for queries. The collector tier is where most of the complexity lives.

Core Components

Interviewer"How does the SDK avoid adding latency to the services it instruments?"
Instrumentation & SDK Layer
  • WHY: If span creation and export block the request thread even briefly, the tracing system becomes a liability — services will disable it.
  • HOW: The SDK creates spans in-process using a lock-free (no mutex required — threads don't block each other) ring buffer and flushes asynchronously to a local agent sidecar (a lightweight process co-deployed alongside each service). The sidecar batches spans and forwards over UDP or a local Unix socket — both fire-and-forget, so the service never blocks on export. Context propagation (passing trace-id and span-id between services) happens via HTTP headers like W3C TraceContext.
  • TRADEOFF: Fire-and-forget means spans can be lost if the sidecar crashes or falls behind — you trade completeness for zero-overhead instrumentation.
Interviewer"Tail-based sampling means you decide to keep a trace only after it completes — how do you buffer spans for an in-flight trace without losing them or OOMing?"
Tail-Based Sampling Collector
  • WHY: Tail-based sampling (keep traces only when something interesting happens — slow, errored) requires seeing the full trace before deciding, which means buffering all spans for potentially seconds.
  • HOW: I route spans by trace-id (a unique ID shared by all spans in one request) to a consistent set of collector nodes using consistent hashing (a hash ring so re-routing is minimal when nodes join/leave). Each collector holds an in-memory trace buffer keyed by trace-id with a TTL (time-to-live — evict after max trace duration, say 30s). When a root span arrives with a final status, the collector evaluates the policy — error, latency > p99 threshold, or random 0.1% — and either flushes the trace to the write queue or drops it.
  • TRADEOFF: Buffering full traces in memory means each collector node needs significant RAM — 30s × 20K spans/sec × 1.5KB ≈ ~900MB per node at peak, before replication.
Interviewer"Why put a queue between the collector and storage instead of writing directly?"
Span Ingestion Queue
  • WHY: Storage writes are the slowest step — without a queue, a storage hiccup backpressures all the way to the service, causing span loss or collector OOM.
  • HOW: Sampled trace batches are published to a partitioned durable queue (a log where each partition is an ordered, replicated stream), partitioned by trace-id so all spans for a trace land on the same partition. Storage writers consume at their own pace, and the queue retains messages for 24h so we can replay on writer failure.
  • TRADEOFF: Adds ~1–2 seconds of end-to-end latency before traces are queryable — acceptable for observability but not for real-time alerting.
Interviewer"What database do you use here, and how do you structure the data for the query patterns you need?"
Trace Storage Layer
  • WHY: Traces have two very different query patterns — fetch a single trace by ID (point lookup) and search traces by service, duration, or error tag (analytical scan) — no single DB serves both cheaply.
  • HOW: I split into two stores. A wide-column store (rows identified by trace-id, columns are spans — fast point lookups by trace-id) handles fetch-by-ID. A columnar store (stores each field as its own column, fast for filtering and aggregation) handles indexed search on service name, duration, status, and custom tags. Writers fan out to both. The columnar store gets a TTL-based partition drop (delete entire date partition instead of row-by-row) to handle 7-day retention efficiently.
  • TRADEOFF: Dual writes add complexity and risk inconsistency — if the columnar write fails, the trace is fetchable but not discoverable by search.
Interviewer"How do you hit the 2-second p99 query target for something like 'show me all slow traces for service X in the last hour'?"
Query Service
  • WHY: Without pre-built indexes, a full scan over 7 days of columnar data would blow the latency budget even on fast storage.
  • HOW: The query service translates UI filters into columnar store queries against pre-indexed columns — service_name, timestamp (bucketed to hourly partitions), duration_ms, and status_code. Queries hit only the relevant time partition. Results are trace-id lists that the service then hydrates (fetches full span trees) from the wide-column store in parallel. A short-lived result cache (LRU eviction — drops least-recently-used entries when cache is full) holds recent query results for 30 seconds to absorb repeated dashboard refreshes.
  • TRADEOFF: The 30s result cache means dashboards can show slightly stale data during active incidents — exactly when freshness matters most.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1All spans for a given trace-id must land on the same collector for tail-sampling to work — if that collector node dies, all buffered in-flight traces are lost.
Fix: I add a two-layer routing scheme. The first layer is a stateless load balancer that routes by trace-id using consistent hashing — so the same trace always goes to the same collector. The second layer is a replication group: each collector forwards its buffer state to one hot-standby replica using a lightweight gossip (peer-to-peer state synchronization) protocol. If the primary dies, the standby takes over the hash ring slot within one heartbeat interval (~5s), losing at most 5 seconds of in-flight traces rather than the full 30s TTL buffer.
Tradeoff: Replication doubles the memory footprint of the collector tier and adds network overhead for buffer sync.
2The columnar store write throughput becomes a bottleneck during traffic spikes — bursty writes cause latency to spike and can exhaust write connections.
Fix: I put a batching writer pool between the queue and the columnar store. Workers consume from the ingest queue and accumulate spans into micro-batches (aggregate many small writes into one large insert) of ~5K rows or 500ms, whichever comes first, before issuing a single bulk insert. This converts thousands of tiny random writes into sequential bulk operations that columnar stores handle orders of magnitude more efficiently. The queue's retention (24h) provides the slack to absorb bursts without data loss.
Tradeoff: Micro-batching adds up to 500ms of write latency — traces won't be queryable for up to half a second after they complete.

Reference

API
POST/api/v1/spans— Receives a batch of spans from a sidecar agent; returns 202 Accepted — fire-and-forget, no span-level ack
GET/api/v1/traces/{trace_id}— Returns full span tree for a single trace by ID; 404 if not sampled or expired
GET/api/v1/traces?service=&status=&min_duration_ms=&start=&end=&limit=— Searches indexed traces by filter params; returns paginated list of trace summaries with trace_id and root span metadata
GET/api/v1/services— Returns list of all instrumented service names seen in the retention window — used to populate filter dropdowns
POST/api/v1/sampling-config— Updates sampling rules (rate, service-specific overrides, tail policies) — applied to collectors within one config propagation cycle
Database & Storage
  • Wide-column store (e.g. Cassandra-class) for trace fetch: fast point lookup by trace-id, handles high write throughput with LSM-tree (log-structured merge — appends fast, compacts later) storage engine
  • Schema: spans(trace_id UUID PK, span_id UUID PK, parent_span_id UUID, service_name TEXT, operation TEXT, start_ts TIMESTAMP, duration_ms INT, status_code SMALLINT, tags MAP)
  • Columnar store (e.g. ClickHouse-class) for search: schema mirrors above but stored column-per-field; partition key is (service_name, date) for efficient TTL drops and range scans
  • Primary index on (service_name, start_ts) in columnar store; secondary index on (status_code, duration_ms) for error and slow-trace queries
  • Wide-column store TTL set to 7 days at row level; columnar store drops entire date partitions older than 7 days — partition drop is O(1) vs O(n) row-by-row deletes
