Typeahead Search

Typeahead looks like a simple autocomplete box but hides brutal latency requirements — sub-100ms end-to-end while querying billions of strings across distributed machines. Interviews use it to probe prefix data structures, ranking pipelines, and the tension between freshness and speed.

Interview

Interviewer
Design the typeahead search system you'd find on Google Search — the dropdown suggestions that appear as you type. Walk me through where you'd start.
You
Before diving in — what's the DAU (daily active users) and query volume? Are suggestions global or personalized per user? And what's the acceptable end-to-end latency budget for a suggestion response?
Interviewer
Assume 500 million DAU, roughly 10 billion queries per day. Suggestions are global, not personalized. Target p99 latency under 100ms at the client.
You
10 billion queries per day is about 115,000 QPS (queries per second) on average, with likely 3-5x spikes — so I'll design for 500K QPS peak. Each keystroke fires a query, so if users average 5 keystrokes per search, that multiplies the backend load. Global suggestions means a shared ranking model — no per-user state. 100ms p99 (99th percentile — the slow tail, not the average) end-to-end means the suggestion service itself needs to respond in under 20ms after network is accounted for. I'll plan the data path around an in-memory prefix index rather than hitting disk on each keystroke.

Core Components

Interviewer"How do you actually store and query the prefix suggestions at this scale — do you use a trie, and how does that survive 500K QPS?"
Prefix Trie / Index Layer
  • WHY: Without a prefix-optimized structure, every keystroke requires a full-table scan or expensive B-tree traversal — latency blows past 100ms instantly.
  • HOW: I build a compressed trie (a tree where each node represents a character prefix, and paths spell out query strings) and store the top-k ranked completions directly at each trie node — this is denormalized storage, meaning we duplicate data to avoid tree traversal at query time. The trie is serialized to a memory-mapped file and loaded into RAM on each suggestion server. A query for 'appl' jumps to that node in O(len) time and returns the pre-ranked list in microseconds.
  • TRADEOFF: Storing top-k at every node inflates memory — a trie with 1 billion unique prefixes can consume 100GB+ RAM, so I need to shard (split data across multiple machines) by prefix range.
Interviewer"How do you decide which suggestions bubble to the top — what's the ranking model and how does it stay fresh?"
Query Ranking Pipeline
  • WHY: Raw prefix matches are useless without ranking — 'apple' should beat 'applesauce accessories' — and staleness kills trust if trending queries don't appear for hours.
  • HOW: I run an offline batch pipeline every 1-2 hours that aggregates raw query logs from the past 7 days, computes a score per query using a weighted formula — primarily query frequency, decayed by recency (recent queries weighted 2x), and adjusted by a quality signal like click-through rate (CTR, fraction of times a suggestion was clicked). That score is written into the trie nodes. For breaking-news freshness I layer on a real-time stream processor that tails the query log and bumps scores for queries spiking in the last 10 minutes, writing directly to a Redis cache (an in-memory key-value store) that the suggestion servers check before hitting the trie.
  • TRADEOFF: Two-tier ranking (batch + real-time) adds operational complexity — the real-time layer can temporarily diverge from the batch baseline during a pipeline failure.
Interviewer"The trie can't fit on one machine — how do you split it across servers without making queries cross multiple nodes?"
Trie Sharding & Replication
  • WHY: A single-machine trie for billions of queries blows past RAM limits and becomes a single point of failure — one crash takes down all suggestions.
  • HOW: I shard by prefix range — one shard owns prefixes 'a'-'b', another owns 'c'-'d', etc. The split points are chosen by query frequency distribution, not alphabet, to avoid hot shards (machines receiving disproportionate traffic). A consistent-hashing ring (a scheme where nodes are mapped to a circle so adding/removing nodes shifts minimal keys) routes each query to the right shard. Each shard is replicated 3x for read throughput and fault tolerance — all replicas serve reads, writes propagate from a primary.
  • TRADEOFF: Prefix-range sharding can still create hotspots for popular first letters like 's' or 'c' — I'd monitor and manually split those shards if needed.
Interviewer"How do you keep 500K QPS from actually hitting your backend — there must be a client-side layer?"
Client-Side Debouncing & CDN Edge Cache
  • WHY: Without client-side throttling, every keypress from 500M users fires a backend request — that's 2-5x more traffic than necessary and burns money.
  • HOW: The client debounces (delays firing a request until 80-100ms after the last keystroke) — this alone cuts backend QPS by ~40% because most intermediate characters never trigger a request. Beyond that, I cache suggestion results at CDN edge nodes (servers geographically close to users) keyed by prefix string — 'appl' always returns the same top-k globally, so a cache hit at the edge adds zero backend load. CDN TTL (time-to-live, how long the edge holds a cached response) is set to 60 seconds for most prefixes, 10 seconds for trending ones.
  • TRADEOFF: CDN caching means a trending query can take up to 60 seconds to surface in suggestions — acceptable for most cases but not for breaking news.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Trie rebuild takes 20-30 minutes every cycle, during which all suggestion servers read a stale snapshot — any freshness SLA below 2 hours is broken.
Fix: I decouple trie updates from full rebuilds using a delta-update protocol: each suggestion server holds the current trie in memory and applies incremental score patches (small diffs, not full reloads) pushed from the batch scorer. Only structural changes — new queries entering the vocabulary — require a partial trie rebuild on the affected prefix shard. This cuts the 'dark window' from 20 minutes to under 30 seconds.
Tradeoff: Delta patching adds implementation complexity — a buggy patch can corrupt a live trie, so I need a rollback checkpoint before each patch batch.
2Popular prefixes like 's' or 'th' hit a single shard at massively disproportionate QPS, saturating that machine while others sit idle.
Fix: I detect hot shards via per-shard QPS metrics and split them dynamically — 's' becomes 'sa'-'sl' and 'sm'-'sz' on two separate machines. I also add read replicas (copies of a shard that serve reads only) for top hot shards so traffic fans out across 3-5 machines instead of 1.
Tradeoff: Dynamic splitting requires a brief re-routing window where some requests may land on the wrong shard and need a redirect — adds one network hop of latency during splits.
3A CDN cache miss storm during a cold start or CDN node failure sends millions of requests directly to suggestion servers simultaneously.
Fix: I implement request coalescing (collapsing multiple identical in-flight requests for the same prefix into one backend call) at the load balancer layer. While the single backend call is in flight, all duplicate requests wait and receive the same response. This limits cold-start thundering herd (many clients simultaneously hammering a backend) to one backend request per unique prefix per CDN node.
Tradeoff: Coalescing adds latency for the waiting requests — they get the result only when the first request completes, not immediately.

Reference

API
GET/api/v1/suggest?q={prefix}&limit={k}— Returns top-k suggestions for prefix; response: {suggestions: [{text, score}], latency_ms}
POST/api/v1/query-log— Client logs a completed query event with selected suggestion for CTR tracking; async, fire-and-forget
GET/api/v1/health/shard/{shard_id}— Internal: returns shard QPS, memory usage, and trie freshness timestamp for ops monitoring
Database & Storage
  • In-memory Trie: primary suggestion store — sub-millisecond prefix lookup with O(len) time, no disk I/O on hot path
  • Schema (Trie Node): prefix VARCHAR PK, top_k JSONB (array of {text, score}), updated_at TIMESTAMP — persisted to disk as recovery snapshot
  • Redis: key = prefix string, value = JSON top-k list, TTL = 10-60s — serves real-time trending overrides without touching trie
  • Append-only query log: (query_text VARCHAR, timestamp BIGINT, user_region CHAR(2), clicked_suggestion VARCHAR) — partitioned by day for batch scoring
  • Index strategy: trie structure is itself the index — prefix walks are O(prefix_length); query log indexed on (query_text, timestamp) for aggregation scans
  • Key tradeoff: trie lives in RAM for speed but requires periodic snapshotting to durable storage — a crash without a recent snapshot means replaying hours of query logs to rebuild scores
