Flash Sale System

A flash sale compresses millions of purchase attempts into seconds, turning every component into a potential bottleneck — especially inventory, which must never oversell. Interviewers use it to probe distributed locking, queue-based load shedding, and graceful degradation under traffic spikes.

Interview

Interviewer
We want to build a flash sale system — think 10,000 limited-edition items that go on sale at noon and sell out in under a minute. Walk me through how you'd design it.
You
Before diving in — what's the peak concurrency we're planning for? Tens of thousands of simultaneous buyers or hundreds of thousands? And is this a single global sale or do we need to support multiple concurrent flash sales? Also, what's the acceptable oversell tolerance — strictly zero, or is a small buffer okay?
Interviewer
Assume 500,000 concurrent users hammering the buy endpoint at sale start. Single sale at a time, 10,000 items. Oversell is strictly zero — we can't sell inventory we don't have.
You
So we're absorbing roughly 500K requests in the first few seconds — call it 100K–200K RPS (requests per second) at peak on the purchase path. Only 10K will succeed; the rest get rejected fast. Strict zero oversell means I can't rely on eventual consistency (where replicas catch up asynchronously) for inventory — I need atomic decrements (an indivisible read-modify-write) on a single source of truth. My main constraints are: shed load before it hits the DB, guarantee atomic inventory deduction, and keep the happy path latency under 500ms p99 (99th percentile — the slow tail, not the average).

Core Components

Interviewer"How do you prevent 500,000 requests from simultaneously slamming your backend the moment the sale opens?"
Pre-Sale Queue / Virtual Waiting Room
  • WHY: Without traffic shaping, even a perfectly designed backend will collapse under 200K RPS of synchronous writes arriving in the same second.
  • HOW: I put a virtual waiting room in front — clients poll a lightweight endpoint that returns their queue position. At sale start, I release tokens (admission tickets) at a controlled rate, say 5K/sec, into a distributed queue (an ordered buffer that decouples producers from consumers). Only token holders get routed to the purchase service. Everyone else gets a 'you're in line' response immediately.
  • TRADEOFF: Adds perceived latency for legitimate buyers — people may abandon if the wait feels too long.
Interviewer"How do you guarantee zero oversell when thousands of requests pass the queue simultaneously?"
Atomic Inventory Counter (Redis)
  • WHY: A relational DB doing read-then-write inventory updates under concurrent load will race — two threads can both read '1 item left' and both decrement, selling 2 items.
  • HOW: I store inventory as an integer in Redis (an in-memory data store) and use DECRBY with a Lua script (a server-side atomic script that runs without interruption) that checks for zero before decrementing. The script returns 1 on success, 0 if sold out. Because Redis is single-threaded for commands, this is inherently atomic — no distributed lock (a mechanism to serialize access across machines) needed for the counter itself.
  • TRADEOFF: Redis is in-memory — a crash before persistence (writing to disk) loses the counter state, so I need AOF (append-only file, a Redis durability log) enabled with fsync every second.
Interviewer"Once a purchase is confirmed by Redis, how do you persist the order without the DB becoming a bottleneck?"
Order Write Queue
  • WHY: Even 10K successful purchases hitting the DB synchronously during a spike can cause write contention and slow down the confirmation response.
  • HOW: After Redis confirms the decrement, I push an order event onto a durable message queue (a persistent buffer that survives crashes). The purchase API immediately returns a 'pending confirmation' response with an order ID. A consumer service (an async worker reading from the queue) writes the order to the DB, sends confirmation email, and updates the order status — all out of the critical path.
  • TRADEOFF: Order confirmation is eventually consistent — users see 'pending' briefly before 'confirmed', which requires clear UX messaging.
Interviewer"You'll have hundreds of thousands of users loading the sale page simultaneously. How do you handle those reads?"
Product Page Caching
  • WHY: Without caching, every page load hits the DB for product details — at 500K concurrent users, even read queries will saturate DB connection pools.
  • HOW: I cache the product page HTML or product JSON in a CDN (content delivery network — edge servers geographically close to users) with a short TTL (time-to-live — cache expiry duration) of 10–30 seconds pre-sale. When the sale goes live, I serve inventory status from a read replica or a separate Redis key, not the inventory counter itself. The counter is write-path only.
  • TRADEOFF: Slightly stale inventory display (e.g. showing '10K available' when it's actually 9,800) — acceptable since the authoritative check happens at purchase time.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1At sale start, 200K+ RPS hits the Purchase API simultaneously — even the Redis atomic counter becomes a hotspot under that request fan-in.
Fix: I pre-shard (split) inventory into N virtual buckets — e.g. 10 Redis keys each holding 1,000 units. Each incoming request hashes to a random bucket and tries DECRBY on that bucket. If it's empty, it tries adjacent buckets. This spreads the write load across 10 Redis nodes instead of hammering one key. I reconcile actual sold count asynchronously from all buckets.
Tradeoff: Adds complexity to the sold-out detection — I have to check all buckets to confirm global sell-out, which adds latency to that edge case.
2If Redis goes down mid-sale, the inventory counter is lost and the system either oversells or stops accepting purchases entirely.
Fix: I run Redis in a primary-replica setup with Redis Sentinel (an automatic failover coordinator) watching for primary failure. AOF persistence is enabled so on restart the counter recovers from the log. I also keep a 'floor' check in the DB — orders written asynchronously are counted and if DB order count reaches item limit, the Purchase API returns sold-out as a fallback, even without Redis.
Tradeoff: Failover takes 5–30 seconds during which purchases are blocked — I show users a 'processing' spinner rather than rejecting them.
3The Order Queue consumer may lag under burst, causing order confirmation emails to be delayed by minutes during the spike.
Fix: I scale the Order Worker consumer horizontally — each worker pulls from the same queue topic and processes in parallel. I partition the queue by order ID mod N so each consumer owns a subset, avoiding duplicate processing. I also prioritize DB writes (fast) over email sends (slow) by using two separate consumer groups with different processing SLAs.
Tradeoff: More consumer instances mean more DB write connections — I need a connection pool (a pre-allocated set of reusable DB connections) to avoid overwhelming the Orders DB.

Reference

API
GET/api/v1/sales/{sale_id}— Returns sale metadata and current inventory display count (from cache); cached at CDN edge for 15s
POST/api/v1/sales/{sale_id}/queue— Registers user in virtual waiting room; returns queue position and polling token
GET/api/v1/sales/{sale_id}/queue/status— Polls queue position; returns position, estimated wait, or admission token when ready
POST/api/v1/sales/{sale_id}/purchase— Authenticated; requires valid admission token; atomically decrements inventory and enqueues order; returns order_id + 'pending' status
GET/api/v1/orders/{order_id}— Polls order status — pending → confirmed → shipped; used by client after purchase
Database & Storage
  • Redis — atomic inventory counter and session/token store; in-memory speed is mandatory for the critical purchase path
  • Schema (Redis keys): inventory:{sale_id} INTEGER, token:{token_id} HASH(user_id, sale_id, expires_at, used BOOL)
  • PostgreSQL — orders and product catalog; ACID guarantees (all-or-nothing transactions) needed for financial records
  • Schema: orders(order_id UUID PK, sale_id UUID, user_id UUID, item_id UUID, status VARCHAR, created_at TIMESTAMPTZ); sales(sale_id UUID PK, item_id UUID, total_qty INT, starts_at TIMESTAMPTZ)
  • Index strategy: orders(user_id, created_at DESC) for order history; sales(starts_at) for upcoming sale queries; partial index on orders WHERE status='pending' for consumer queue monitoring
  • Key tradeoff: splitting Redis (hot writes) from Postgres (durable writes) means reconciliation is async — a crash window exists where Redis says sold but Postgres hasn't written yet, mitigated by AOF and idempotent (safe-to-retry) order inserts keyed on order_id
