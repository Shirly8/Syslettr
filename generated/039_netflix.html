Netflix

Netflix looks like a video player bolted to a database, but the real challenge is delivering the right quality of video to 200M+ concurrent users across wildly different network conditions — without buffering. It's asked in interviews because it surfaces hard problems in CDN design, adaptive bitrate encoding, and global state at scale.

Interview

Interviewer
Design Netflix — specifically the video streaming system. Users should be able to browse a catalog, select a title, and watch it with minimal buffering. Where do you start?
You
Before diving in — what's the scale? Are we talking global, like 200M active users, or a regional slice? And should I cover the full pipeline including transcoding and CDN, or focus purely on the playback path? Also, is live streaming in scope or just on-demand?
Interviewer
Global scale — 200M subscribers, roughly 10-15% streaming concurrently at peak. On-demand only, no live. Cover the full pipeline from upload to playback.
You
So ~20-30M concurrent streams at peak. If each stream averages 5 Mbps, that's roughly 100-150 Tbps of egress — that's why a global CDN (content delivery network — a distributed network of edge servers close to users) is non-negotiable, not a nice-to-have. I'll also assume we have a studio ingest pipeline where masters are uploaded, and a separate consumer playback path. I'll design around three major concerns: transcoding at ingest, CDN delivery, and adaptive bitrate (ABR — dynamically switching video quality based on available bandwidth) during playback.

Core Components

Interviewer"Walk me through how you'd handle encoding — a single movie master file could be 100GB or more. How do you make that manageable?"
Transcoding Pipeline
  • WHY: Without transcoding into multiple resolutions and codecs, we can't serve the right quality to a 4K TV and a 3G phone from the same source file.
  • HOW: I'd chunk the master file into segments (typically 2-6 seconds each) and transcode each chunk in parallel across a fleet of workers — this is scene-parallel encoding. Each chunk gets encoded into multiple quality profiles (e.g., 240p through 4K) and multiple codecs (H.264 for compatibility, H.265/AV1 for efficiency). Workers pull chunks from a distributed queue and write outputs to object storage. A manifest file (a text index listing every chunk URL and its quality) is generated at the end and stored alongside the segments.
  • TRADEOFF: Parallel chunked encoding dramatically cuts wall-clock time but increases total CPU cost and requires a reassembly/validation step to ensure chunk boundaries are seamless.
Interviewer"How do you actually get video segments to users fast? What's your CDN strategy?"
CDN Layer & Edge Caching
  • WHY: Without edge caching, every segment request hits origin storage — at 30M concurrent streams that's instant origin overload and unacceptable latency.
  • HOW: I'd use a tiered CDN (content delivery network). The first tier is edge POPs (points of presence — servers co-located near ISPs), the second is regional mid-tier caches. A segment request hits the nearest edge; on a miss it goes to the mid-tier; only on a second miss does it reach origin. Popular content (top 10 shows) gets proactively pushed to edges before peak hours — this is cache warming. Each segment URL includes a content hash so edges can cache aggressively with no invalidation complexity.
  • TRADEOFF: Tiered CDN reduces origin load by 95%+ but adds one extra network hop on cold misses, slightly increasing first-chunk latency for unpopular content.
Interviewer"How does the player decide which quality to request at any given moment?"
Adaptive Bitrate (ABR) Player Logic
  • WHY: Without ABR, a user on a fluctuating connection either buffers constantly (if we pick too high a quality) or wastes bandwidth on a great connection (if we pick too low).
  • HOW: The player uses HLS (HTTP Live Streaming — Apple's segment-based streaming protocol) or DASH (Dynamic Adaptive Streaming over HTTP — the open standard equivalent). It maintains a buffer health metric (seconds of video pre-loaded). A throughput estimator measures download speed of recent segments using an EWMA (exponentially weighted moving average — weights recent samples more than old ones). Based on buffer level and estimated throughput, a bitrate-selection algorithm picks the highest quality profile that can be sustained without draining the buffer below a safety threshold (e.g., 5 seconds).
  • TRADEOFF: Conservative ABR (buffer-based) avoids rebuffering but may under-utilize bandwidth on sudden network improvements, causing the user to stay at lower quality longer than necessary.
Interviewer"How do you handle DRM — making sure only paying subscribers can decrypt and play content?"
Playback Session & License Service
  • WHY: Without DRM (digital rights management — encryption + license keys that control playback), anyone who intercepts a CDN URL can redistribute content freely.
  • HOW: Video segments are encrypted at ingest using AES-128. When a user starts playback, the player requests a license from a DRM license server (we support Widevine, FairPlay, PlayReady for different platforms). The license server validates the user's active subscription via the Auth service, then returns a decryption key scoped to that session and device. Keys are time-limited — typically 24 hours — so revocation is automatic on subscription lapse.
  • TRADEOFF: Every playback start requires a license round-trip — this adds 100-300ms latency to session startup; caching keys client-side reduces repeat overhead but extends the revocation window.
Interviewer"How do you serve the browse experience — the homepage, search, and recommendations at this scale?"
Catalog & Metadata Service
  • WHY: Without separating metadata reads from the streaming path, a browse spike (e.g., right after a big release) can starve CDN or auth resources.
  • HOW: Metadata (titles, descriptions, ratings, artwork URLs) lives in a read-optimized relational DB with a distributed cache (in-memory key-value store) in front of it. Cache TTL (time-to-live — how long a cached entry stays valid) is set to 5-10 minutes for catalog data. Recommendations come from a pre-computed ranked list per user stored in a fast key-value store — the ML pipeline that generates them runs offline and writes results asynchronously. The API layer assembles the homepage by stitching pre-ranked rows, making only a single cache lookup per shelf.
  • TRADEOFF: Pre-computed recommendations are slightly stale (up to hours old) but let us serve a homepage in under 100ms; real-time personalization at this scale would require much heavier infrastructure.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1At 30M concurrent streams, a single origin cluster handling cache misses becomes a bottleneck — even a 1% miss rate is 300K simultaneous origin requests.
Fix: I'd add a mid-tier CDN layer between edge POPs and origin — a regional cluster of cache servers that aggregates misses from many edges before they hit origin. This collapses the miss fanout by roughly 10-50x. For the most popular content (top 1% of titles), I'd proactively push segments to all edges during off-peak hours (cache warming) so those titles have near-zero misses even on new edge nodes joining the fleet.
Tradeoff: Mid-tier adds a network hop and infrastructure cost; cache warming requires predicting popularity in advance, which occasionally wastes bandwidth on content that underperforms.
2Transcoding a 2-hour movie naively as a single job can take hours — blocking new content from being available and wasting compute on retries if a worker fails.
Fix: I'd split the master file into independent chunks before any encoding begins and distribute those chunks across a stateless worker pool via a job queue. Each worker encodes only its assigned chunk across all quality levels, then writes output to object storage and marks the chunk done in a coordinator. The coordinator assembles the manifest only once all chunks are confirmed. This way a single worker failure means only one chunk needs re-encoding, not the whole file.
Tradeoff: Chunk-parallel encoding requires extra coordination logic and a validation step to ensure audio/video sync at chunk boundaries — if this is off, playback will stutter.
3The DRM license service becomes a hot synchronous bottleneck at peak because every new playback session requires a live auth check before the user sees any video.
Fix: I'd add a short-lived (24-hour) license cache keyed by user ID + device ID + title ID in a fast in-memory store at the license service layer. On a cache hit, we skip the auth service round-trip entirely and return the cached decryption key. On first-play or post-cache-expiry, the full auth check runs. This reduces license service load by ~80% for users who watch multiple episodes in a session.
Tradeoff: If a user's subscription is cancelled mid-session, their cached key remains valid until it expires — a 24-hour revocation lag. Shortening TTL tightens revocation but increases auth service load.

Reference

API
POST/api/v1/playback/session— Start a playback session — returns manifest URL, CDN edge host, and DRM license token for the requested title and device
GET/api/v1/playback/manifest/{titleId}/{quality}.m3u8— Fetch the HLS manifest listing all segment URLs for a given title and quality profile
GET/api/v1/catalog/browse— Returns personalized homepage shelves — query params: userId, region, limit; response includes pre-ranked title metadata and artwork URLs
GET/api/v1/catalog/title/{titleId}— Returns full metadata for a single title — synopsis, cast, available quality profiles, and content rating
POST/api/v1/drm/license— Exchanges a playback token for a decryption key — validates subscription, returns scoped AES key; called by player SDK automatically
POST/api/v1/events/playback— Client posts play/pause/seek/quality-switch events for analytics and resume-position tracking; fire-and-forget, async ingestion via queue
Database & Storage
  • PostgreSQL for catalog/metadata — structured, relational, supports complex queries (genre filtering, search ranking joins), read replicas handle browse load
  • Schema: titles(title_id UUID PK, title TEXT, type TEXT, release_year INT, rating TEXT, duration_s INT, created_at TIMESTAMP); title_profiles(profile_id UUID PK, title_id UUID FK, quality TEXT, codec TEXT, segment_count INT, manifest_path TEXT)
  • Redis (in-memory key-value store) for session state and license cache — O(1) lookup by session token, TTL-based expiry, no persistence needed
  • Schema: sessions:{session_id} → {user_id, title_id, device_id, edge_host, started_at, expires_at} with 6-hour TTL; licenses:{user_id}:{device_id}:{title_id} → {aes_key, expires_at} with 24-hour TTL
  • DynamoDB (wide-column NoSQL store — optimized for high-throughput key-value at scale) for per-user recommendation lists and resume positions — hash key: user_id, sort key: shelf_id or title_id; scales horizontally without schema changes
  • Index strategy: PostgreSQL full-text index on titles.title for search; composite index on (type, release_year DESC) for browse filtering; Redis keyspace notifications for session expiry cleanup
  • Key tradeoff: Using Redis for session/license caching trades durability (data lost on restart) for sub-millisecond latency — acceptable because sessions are re-creatable and we persist the source-of-truth in Postgres/Dynamo
