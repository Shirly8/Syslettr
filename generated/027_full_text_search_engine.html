Full-Text Search Engine

Building a full-text search engine is deceptively complex because relevance ranking, real-time index updates, and sub-100ms query latency must coexist at massive scale. Interviewers use it to probe your understanding of inverted indexes, distributed write paths, and the hard tradeoffs between freshness and performance.

Interview

Interviewer
We want to build a full-text search engine — think something like the search bar on an e-commerce platform or a document management system. Where do you start?
You
Before diving in — what corpus are we searching? Product listings, user-generated documents, or web pages? What's the scale: tens of millions of documents or hundreds of billions? And what's the freshness requirement — can index updates lag by minutes, or do we need near-real-time?
Interviewer
Think e-commerce: 500 million product listings, each with title, description, and attributes. Queries peak at 50,000 per second. New and updated products should appear in search within 30 seconds.
You
Got it. 500M documents at ~2KB average is roughly 1TB of raw text. At 50K queries/sec with a p99 latency (99th percentile — the slow tail, not the average) target of under 100ms, caching (keeping hot query results in memory) is essential. Index updates within 30 seconds means we need a streaming ingestion pipeline, not batch. I'll design around an inverted index (a map from each word to the list of documents containing it), with sharding (splitting the index across multiple machines) by document ID, and a separate query fan-out layer that merges per-shard results.

Core Components

Interviewer"How do you get 500 million documents — plus continuous updates — into the index without overwhelming it?"
Document Ingestion Pipeline
  • WHY: Without a decoupled ingestion layer, a spike in product updates would directly saturate the indexing nodes and cause query latency to spike.
  • HOW: Producers (upstream product services) publish document events to a distributed log (a durable, ordered, partitioned message queue). Indexing workers consume from the log, run text analysis (tokenization, lowercasing, stop-word removal, stemming — reducing words to root forms), and write posting list (the list of document IDs for a given term) updates to the index shards. Workers checkpoint their position in the log so restarts are safe.
  • TRADEOFF: The log introduces up to a few seconds of lag between a product update and index visibility, which is acceptable given the 30-second SLA.
Interviewer"Walk me through how the inverted index is actually structured on disk and how you keep it fast under concurrent reads and writes."
Inverted Index Storage
  • WHY: The inverted index is the core data structure — without efficient on-disk layout, every query degrades to a full scan, making low-latency impossible.
  • HOW: I use an LSM-tree (Log-Structured Merge tree — writes go to an in-memory buffer first, flushed to immutable sorted files, then merged in background) to handle high write throughput. Each entry maps a term to a posting list — a sorted array of (doc_id, term_frequency, position_list) tuples. I store posting lists in compressed blocks using delta encoding (storing differences between consecutive doc IDs rather than absolute values) to cut disk I/O. Merge operations compact and re-sort segments without blocking reads.
  • TRADEOFF: LSM-tree read amplification (a single lookup may touch multiple sorted files) means I need a bloom filter (a probabilistic structure that rules out missing keys) per segment to avoid unnecessary disk reads.
Interviewer"Once a query comes in, how do you go from raw text to a ranked list of products in under 100ms?"
Query Processing & Ranking
  • WHY: Without a structured query pipeline, merging posting lists from dozens of shards and ranking thousands of candidates becomes the bottleneck that blows the latency SLA.
  • HOW: The query coordinator parses and tokenizes the query, then fans out term lookups to the relevant index shards in parallel. Each shard returns its top-K (top K scoring documents) candidates scored by BM25 (a term-frequency/inverse-document-frequency ranking formula). The coordinator merges per-shard top-K lists, applies business logic boosts (e.g. promoted products, in-stock weight), and returns the final top-N. I cap per-shard candidate set to 200 to bound merge cost.
  • TRADEOFF: Capping per-shard candidates at 200 can miss high-scoring documents ranked below position 200 on a single shard, slightly reducing recall at the tail.
Interviewer"At 50K queries per second, how much does caching actually help, and what's your invalidation strategy?"
Query Result Cache
  • WHY: Without a result cache, every query hits the index fan-out path, and at 50K QPS the index shards would need enormous compute to keep up.
  • HOW: I cache the serialized top-N result list keyed by the normalized query string. Empirically, search query distributions follow a power law — the top 1% of queries account for ~50% of traffic — so even a modest cache with LRU eviction (drops least-recently-used entries when cache is full) gives high hit rates. TTL (time-to-live — automatic expiry after a set duration) is set to 60 seconds, which is safe given the 30-second index freshness SLA.
  • TRADEOFF: A 60-second TTL means a popular product update may not surface in cached results for up to 60 seconds, which is acceptable but must be communicated to product stakeholders.
Interviewer"Should autocomplete share the same index, or is that a separate system?"
Typeahead / Autocomplete Layer
  • WHY: Autocomplete requires sub-20ms response while the user is typing — waiting for full index fan-out is too slow.
  • HOW: I maintain a separate trie (a prefix tree data structure for fast prefix lookups) or a prefix-keyed sorted structure built from the top-N most frequent queries, updated hourly from query logs. This lives entirely in memory on a small cluster of nodes behind the API gateway. It doesn't need near-real-time freshness because query popularity patterns shift slowly.
  • TRADEOFF: Autocomplete suggestions lag behind actual inventory changes by up to an hour, so newly added product categories won't appear in suggestions immediately.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single coordinator merging 50 shard responses at 50K QPS becomes a CPU and network bottleneck, blowing the 100ms latency budget.
Fix: I horizontally scale the query coordinator tier behind the load balancer — each coordinator handles an independent slice of traffic. No shared state is needed between coordinators since each one independently fans out to all index shards and merges results. I also implement scatter-gather with a timeout: if a shard doesn't respond in 80ms, the coordinator returns partial results from the shards that did, degrading gracefully rather than failing.
Tradeoff: Returning partial results on slow shards means some queries miss documents on that shard until it recovers, reducing recall transiently.
2Hot-term posting lists (e.g. the word 'blue' in a clothing store) are massive and read on nearly every query, creating a hot-shard problem.
Fix: I replicate the index with read replicas (copies of an index shard that serve reads only) — the load balancer distributes reads across all replicas of the hot shard. For the hottest terms, I also cache the posting list itself (not just the final result) in the coordinator's local memory so the shard isn't hit at all for the most common terms.
Tradeoff: Per-coordinator posting list caches consume significant RAM and can serve slightly stale lists for up to their TTL if a product is updated.
3Re-indexing all 500M documents after a schema change (e.g. adding a new field) requires hours of batch processing that blocks or degrades live queries.
Fix: I maintain two index generations — the live (active) index and a shadow (being rebuilt) index. The ingestion pipeline writes to both simultaneously during the rebuild window. Once the shadow index passes validation, the query coordinator is atomically switched to use it via a configuration flag. The old index is kept for a short rollback window then deallocated.
Tradeoff: Running dual writes during the rebuild window doubles ingestion load and storage cost temporarily.

API
GET/api/v1/search?q={query}&page={n}&size={k}&filters={json}— Returns top-K ranked results for the query; supports facet filters (e.g. price range, category) and pagination cursor
GET/api/v1/suggest?q={prefix}&limit={n}— Returns up to N autocomplete suggestions from the in-memory trie; sub-20ms SLA
POST/api/v1/internal/documents— Ingests a single document or batch into the pipeline; returns an ack with estimated index-visible-by timestamp
DELETE/api/v1/internal/documents/{doc_id}— Tombstones (marks for removal) a document from the index; propagated via the same log to all shards
Database & Storage
  • Columnar object store for raw document snapshots — needed for re-indexing without re-fetching from upstream
  • Schema: documents(doc_id UUID PK, content TEXT, attributes JSONB, indexed_at TIMESTAMP, checksum CHAR(64))
  • Index strategy: primary key lookup only; no secondary indexes — the inverted index IS the query path
  • Key tradeoff: storing raw documents separately from the inverted index doubles storage but decouples schema evolution from index structure
