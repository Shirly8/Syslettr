Content Moderation System

Content moderation is deceptively hard because it must be both fast (users expect near-instant feedback) and accurate (false positives silence real users, false negatives cause harm). Interviewers use it to probe async pipeline design, ML integration, human-in-the-loop workflows, and how you handle adversarial actors at scale.

Interview

Interviewer
We want to build a content moderation system for a platform like Instagram — users upload images, videos, and text. Walk me through how you'd design it.
You
Before diving in — what content types are in scope, just UGC (user-generated content — text, images, video) or also ads and DMs? What's the upload volume — tens of millions per day or hundreds of millions? And what's the tolerance for latency: does content need to be held until reviewed, or do we publish optimistically and remove reactively?
Interviewer
All UGC — text, images, short videos. About 50 million uploads per day. Publish optimistically but flag and remove within minutes if harmful. Human review team is available 24/7 but can handle roughly 100K items per day.
You
So roughly 580 uploads/sec sustained, with spikes maybe 3x that. Humans can review ~100K/day, which is about 0.2% of volume — so the automated pipeline (ML classifiers making the first decision without humans) must handle the other 99.8%. I'll design a tiered system: auto-approve low-risk content, auto-reject high-confidence violations, and queue the ambiguous middle tier for human review. The human queue becomes a priority queue — worst-potential-harm content surfaces first. I'll assume p99 latency (99th percentile — the slow tail, not the average) for auto-moderation under 5 seconds.

Core Components

Interviewer"How does content actually enter the moderation pipeline — do you block the upload until moderation finishes?"
Ingestion & Async Dispatch
  • WHY: Blocking uploads on ML inference adds 2–10 seconds of latency to every post — users will abandon the product.
  • HOW: The upload service writes content to object storage (a blob store like S3 for raw files) and publishes a lightweight event message — content ID, type, user risk score, metadata — onto a durable message queue (a persistent broker that holds messages until consumed). Moderation consumers pull from that queue independently of the upload path. Content is published optimistically and a 'pending' flag is set in the content record.
  • TRADEOFF: Optimistic publishing means harmful content is briefly visible — typically under 30 seconds — before removal.
Interviewer"Walk me through the automated classification — how do you decide whether to approve, reject, or escalate?"
ML Classification Pipeline
  • WHY: A single binary classifier is too crude — different violation types (nudity, hate speech, spam, violence) have different risk levels and require different models.
  • HOW: I run a cascade of specialized classifiers in parallel — a text toxicity model, an image NSFW (Not Safe For Work) model, a spam/phishing detector. Each returns a confidence score 0–1. I then apply a decision matrix: confidence above 0.95 on any high-severity category auto-rejects; below 0.3 on all categories auto-approves; everything in between goes to the human review queue with the highest classifier score and violation category attached for context.
  • TRADEOFF: Parallel classifiers increase compute cost per item and require separate model training pipelines per category.
Interviewer"The human team can only handle 100K items a day but you said a lot of content will be ambiguous — how do you prevent the queue from blowing up?"
Human Review Queue
  • WHY: Without priority ordering, reviewers spend equal time on mildly questionable memes and potential CSAM (Child Sexual Abuse Material) — the highest-harm content gets delayed.
  • HOW: I model the queue as a priority queue ordered by a composite score: (classifier confidence × harm severity weight). Severity weights are configurable — CSAM and credible violence threats rank highest, spam lowest. I also apply a user risk score (computed from past violation history) to boost priority for repeat offenders. If queue depth exceeds 24-hour reviewer capacity, I lower the auto-approve threshold temporarily to shed low-risk items — this is a safety valve (a circuit breaker to prevent queue overflow).
  • TRADEOFF: Lowering the threshold dynamically means slightly more harmful content auto-approves during traffic spikes — you're trading false negatives for queue stability.
Interviewer"What happens when a user appeals a wrongful removal — and how does that improve the system over time?"
Appeals & Feedback Loop
  • WHY: Without a feedback loop, the ML models never improve and wrongful removals erode user trust with no recourse.
  • HOW: Appeals go to a senior reviewer queue separate from the first-pass queue. The outcome — overturned or upheld — is written back as a labeled training example (a data point pairing content with a confirmed human judgment). These labeled examples feed a weekly model retraining job. I also track per-reviewer agreement rate (how often a reviewer agrees with peers) to surface low-quality reviewers who might be noisy labels (unreliable training data sources).
  • TRADEOFF: Weekly retraining means the model lags behind new violation patterns by up to a week — adversarial actors can exploit that window.
Interviewer"Re-uploading known illegal content is a common evasion — how do you catch that without running the full ML pipeline every time?"
Hash-Based Perceptual Matching
  • WHY: Running full ML classifiers on every re-upload of known-bad content wastes compute and adds latency when you can match it in milliseconds.
  • HOW: I compute a perceptual hash (pHash — a fingerprint that stays similar even after cropping or recompression) on every image and video thumbnail at ingest time. I maintain a hash blocklist — a set of pHashes of confirmed violations — stored in a fast key-value store. Before hitting any ML model, I do a nearest-neighbor lookup (find hashes within a small Hamming distance — the number of differing bits). Exact and near-matches auto-reject immediately and skip the ML pipeline entirely.
  • TRADEOFF: Perceptual hashing only catches derivatives of known-bad content — novel violations always need ML.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1ML inference at 580 items/sec with video content causes GPU compute to become the throughput bottleneck — a single inference server can't keep up.
Fix: I horizontally scale (add more instances) the ML worker pool behind the message queue — the queue acts as a buffer (backpressure absorber) so producers never block on slow consumers. For video, I skip full-frame inference and run classifiers on sampled keyframes (one frame every 2 seconds) rather than every frame. I also cache classifier results keyed by pHash — if the same video is re-uploaded, I return the cached verdict in milliseconds without touching the GPU.
Tradeoff: Keyframe sampling means a violation that appears in a single non-sampled frame could be missed — you're trading recall for throughput.
2The human review queue accumulates faster than reviewers can drain it during events (breaking news, viral content waves), causing high-harm items to wait hours.
Fix: I implement dynamic load shedding: when queue depth exceeds a configurable watermark (the threshold triggering action), I automatically raise the auto-approve confidence threshold floor so more borderline items skip the queue entirely. Simultaneously, I trigger an on-call reviewer alert to bring in surge capacity. For structural relief, I partition the review queue by region and violation type — reviewers specialize, which increases throughput per reviewer.
Tradeoff: Dynamic threshold adjustment is a policy decision with legal and trust implications — it shouldn't be made automatically without human oversight in production.
3The content status database becomes a write hotspot as millions of moderation decisions update the same records concurrently.
Fix: I shard (split data across multiple DB machines) the content table by content_id using consistent hashing (a hashing scheme that minimizes reshuffling when nodes are added) so writes distribute evenly. For high-frequency status reads — e.g., the client polling whether their post was approved — I add a read replica (a copy of the DB that serves reads) with a short TTL (time-to-live — how long cached data stays valid) cache layer in front. The source-of-truth write path stays on the primary shard.
Tradeoff: Sharding by content_id makes per-user queries (all content by user X) expensive — you'd need a secondary index on user_id or a denormalized lookup table.

Reference

API
POST/api/v1/content/upload— Accepts multipart file + metadata; returns content_id and status=pending immediately
GET/api/v1/content/{content_id}/status— Returns current moderation status (pending/approved/rejected) and violation category if rejected
POST/api/v1/content/{content_id}/appeal— Submits a user appeal with optional context text; returns appeal_id and estimated review SLA
POST/api/v1/review/decision— Internal — reviewer submits approve/reject decision with violation category and confidence label
GET/api/v1/review/queue— Internal — returns next N items from prioritized review queue for the authenticated reviewer session
POST/api/v1/hashes/blocklist— Internal admin — adds a confirmed pHash to the blocklist after human review confirms violation
Database & Storage
  • PostgreSQL — relational model fits content records with status transitions, foreign keys to users, and append-only appeal history
  • content(content_id UUID PK, user_id UUID, type VARCHAR, storage_url TEXT, status VARCHAR, classifier_scores JSONB, harm_category VARCHAR, created_at TIMESTAMP, reviewed_at TIMESTAMP)
  • Index on (status, harm_category, created_at DESC) for the review queue query; index on (user_id, created_at) for per-user content history
  • JSONB for classifier_scores allows storing multi-model outputs without schema changes as new classifiers are added, at the cost of losing column-level query optimization on individual scores
  • Redis — stores pHash blocklist as a sorted set for O(1) lookup; also caches content status by content_id with 30s TTL to absorb polling traffic
  • Object Store (S3-compatible) — raw blobs stored with content_id as key; never stored in the relational DB to keep row sizes small and avoid BLOB (Binary Large Object) performance issues
