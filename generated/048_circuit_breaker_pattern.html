Circuit Breaker Pattern

The circuit breaker pattern looks simple on paper — stop calling a failing service — but implementing one correctly requires careful state management, threshold calibration, and coordination across multiple service instances. Interviewers use it to test whether candidates understand failure modes in distributed systems and can reason about resilience beyond basic retry logic.

Interview

Interviewer
We have a payment service that calls a third-party fraud detection API. Recently a slowdown in that API caused our entire checkout flow to hang, taking down the payment service entirely. How would you design around this?
You
Before designing — a few things. What's the acceptable p99 latency for checkout? And is the fraud detection call synchronous in the critical path, or could it be deferred? Also, are we running multiple instances of the payment service, or a single monolith?
Interviewer
Checkout must respond in under 2 seconds p99. The fraud check is synchronous and required before we authorize. We run 20+ instances of the payment service behind a load balancer.
You
Got it. So the core problem is: a slow dependency blocks threads, exhausts the connection pool (the fixed set of reusable connections to the fraud API), and causes cascading failure (one service's failure taking down its callers). I'll design a circuit breaker — a proxy that tracks failure rates and short-circuits calls to the fraud API when it's unhealthy, returning a fast fallback instead of hanging. The tricky part is coordinating state across 20 instances and tuning thresholds so we trip correctly without false positives.

Core Components

Interviewer"Walk me through the states and how transitions work."
Circuit Breaker State Machine
  • WHY: Without defined states, the breaker either never recovers or hammers a partially-recovered dependency immediately on reopening.
  • HOW: I implement three states — CLOSED (normal, all calls pass through), OPEN (breaker tripped, all calls short-circuit to fallback immediately), and HALF-OPEN (probe state, one call let through to test recovery). Transition from CLOSED to OPEN when the error rate (failures / total calls) exceeds a threshold — say 50% — over a rolling window of the last 20 calls. After a cooldown timer (e.g. 30 seconds), transition to HALF-OPEN and allow one probe request. If it succeeds, close the circuit; if it fails, go back to OPEN and reset the timer.
  • TRADEOFF: A single probe in HALF-OPEN means slow recovery — a dependency that's 80% healthy will stay OPEN roughly 20% of the time.
Interviewer"With 20 instances each running their own breaker, how do you prevent one instance from tripping while another stays open?"
Distributed State Coordination
  • WHY: If each instance tracks state locally, instance A may trip its breaker while instance B keeps hammering the fraud API — you lose the protection entirely.
  • HOW: I centralize breaker state in a shared cache (a fast in-memory data store like Redis). Each instance atomically increments a failure counter per time bucket using an atomic increment operation, and reads the aggregate error rate before each call. State transitions are written back with compare-and-swap (atomic update: only write if the value hasn't changed since you read it) to prevent race conditions. The cooldown timer is a TTL-keyed entry — when it expires, any instance can attempt the HALF-OPEN probe, using a distributed lock (a shared flag that only one process holds at a time) so only one instance probes at a time.
  • TRADEOFF: Every call now has a cache read in the hot path — adds ~1-2ms latency and introduces the cache as a new failure dependency.
Interviewer"When the circuit is OPEN and you short-circuit, what do you actually return to the caller?"
Fallback Strategy
  • WHY: Returning a 500 error immediately when the breaker trips is usually worse than a degraded but functional response — you've just moved the failure to the customer.
  • HOW: I define a fallback hierarchy. First option: return a cached fraud score from the last successful call for this user/card combination — fraud patterns don't change in 30 seconds. Second option: apply a rules-based lightweight local check (block known bad BINs, enforce velocity limits from local counters). Third option: allow the transaction and flag it for async fraud review post-authorization, accepting slightly higher fraud risk in exchange for availability.
  • TRADEOFF: Every fallback option accepts some risk — either stale data, lower fraud detection quality, or guaranteed chargebacks on fraudulent transactions that slip through.
Interviewer"How do you pick the right error rate threshold and window size to avoid false trips?"
Threshold Calibration & Observability
  • WHY: A threshold set too low trips on normal transient errors; too high and you don't protect against real degradation until the damage is done.
  • HOW: I use a sliding window (the N most recent calls, not a fixed time bucket) of at least 20 requests so low-traffic periods don't trip on a single failure. I track both error rate AND latency — a dependency that's slow but not erroring is just as dangerous, so p99 latency above 1 second counts as a failure. I emit metrics on circuit state, failure rate, and fallback invocations to a time-series store so I can review trip events and tune thresholds based on real traffic patterns.
  • TRADEOFF: Latency-based tripping requires careful calibration per dependency — a batch job endpoint has very different latency expectations than a real-time API.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Redis becomes a single point of failure — if the shared state store goes down, every instance either can't read circuit state or defaults to CLOSED, hammering an already-failing fraud API.
Fix: I layer a local in-process cache (a per-instance copy of the last-known breaker state, refreshed every 100ms) in front of Redis. If Redis is unreachable, each instance operates on its last cached state for up to 60 seconds before defaulting to OPEN (fail-safe, not fail-open). I also run Redis in clustered mode with replicas so a single node failure doesn't take down the whole state store.
Tradeoff: Local caching means instances can briefly diverge on state — one instance may still think the breaker is CLOSED for up to 100ms after another trips it.
2Thread pool exhaustion — even with a circuit breaker, slow calls before the breaker trips can fill the thread pool (the fixed set of threads serving requests) and cause the payment service itself to stop accepting new requests.
Fix: I wrap the fraud API call in a bulkhead (a separate, isolated thread pool dedicated only to fraud calls, sized independently from the main request pool). The fraud bulkhead gets 20 threads and a queue of 10. If those fill, I reject immediately with a fallback instead of queuing in the main thread pool. I also add a hard timeout of 500ms on the fraud API call — if it doesn't respond, I count it as a failure and invoke the fallback, never blocking a thread for the full 2-second checkout budget.
Tradeoff: A fixed bulkhead size means under a surge of legitimate requests, fraud checks queue and some callers get the fallback even when the fraud API is healthy.
3Half-open thundering herd — when the cooldown expires, all 20 instances simultaneously detect HALF-OPEN and send probe requests, potentially overwhelming a dependency that just recovered.
Fix: I use a distributed lock (a Redis SETNX operation — set if not exists — with a 5-second TTL) so only one instance can hold the probe token at a time. All other instances continue short-circuiting to the fallback until the lock is released and the successful probe is written back. The instance holding the lock sends one request; on success it writes CLOSED state to Redis and releases the lock.
Tradeoff: During the probe window, all non-lock-holding instances still use the fallback even though the dependency may be healthy — introduces up to 5 seconds of unnecessary fallback invocations.

Reference

API
POST/api/v1/payments/authorize— Submits a payment authorization; internally invokes circuit breaker before calling fraud API — returns 200 with auth token or 200 with fallback flag if breaker is OPEN
GET/api/v1/circuit-breaker/status— Returns current state (CLOSED/OPEN/HALF-OPEN), error rate, and failure count for each protected dependency — for ops dashboards
POST/api/v1/circuit-breaker/reset— Manually forces the breaker to CLOSED state — admin-only endpoint for incident recovery when automated recovery is too slow
GET/api/v1/circuit-breaker/metrics— Returns rolling window stats: request count, error rate, p99 latency, fallback invocation count per dependency
Database & Storage
  • Redis: low-latency shared state store for breaker state, counters, and distributed locks — all reads/writes in hot path must be sub-millisecond
  • Schema: circuit_state(service_id VARCHAR PK, state ENUM, failure_count INT, last_trip_at TIMESTAMP, cooldown_expires_at TIMESTAMP)
  • Index: primary key on service_id; failure counters stored as Redis hash fields with per-bucket TTL for sliding window expiry
  • Key tradeoff: Redis is in-memory only — breaker state is ephemeral; on Redis restart all breakers reset to CLOSED, potentially re-exposing a failing dependency until counters rebuild
