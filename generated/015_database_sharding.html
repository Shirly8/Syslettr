Database Sharding

Sharding looks simple — split data across machines — but the hard part is choosing a key that avoids hotspots while keeping queries fast and making rebalancing possible without downtime. Interviewers use it to probe whether you understand distributed data placement, consistency tradeoffs, and operational complexity at scale.

Interview

Interviewer
We're building the backend database layer for a social platform — think user posts, follows, and likes. It's growing fast and a single database can't handle the load anymore. Where do you start?
You
Before diving in — what's our current data volume and write rate? Are queries mostly by user ID, or do we have cross-user fan-out reads like timelines? And do we need strong consistency or is eventual consistency acceptable?
Interviewer
About 500TB of data, 50K writes/sec, 500K reads/sec. Most queries are by user ID. Eventual consistency is fine for feeds, but likes and follow counts should be accurate within a few seconds.
You
Got it — so roughly 50K writes/sec and 500K reads/sec, about 10:1 read-heavy. At 500TB we're well past vertical scaling. I'll shard (split data across multiple DB nodes) by user_id as the primary shard key since most queries are user-scoped. I'll assume ~200 logical shards mapped onto ~20 physical nodes to start, with room to grow. Eventual consistency (replicas may lag slightly behind the primary) is fine for reads, but I'll need synchronous replication for counters like likes to hit that seconds-accurate SLA.

Core Components

Interviewer"Why user_id as the shard key, and what hotspots does that create?"
Shard Key Selection
  • WHY: A bad shard key concentrates writes on one node, making sharding pointless — one hot node becomes the new bottleneck.
  • HOW: I hash user_id with consistent hashing (a ring-based scheme where each node owns a range, so adding nodes only moves a fraction of keys) to distribute writes evenly. Celebrity users who generate disproportionate write load get a dedicated shard suffix — e.g., user 999 maps to shard 999_0 through 999_N — so their fan-out doesn't overwhelm neighbors.
  • TRADEOFF: Range queries across users (e.g., 'all posts in a region') require scatter-gather across all shards, which is expensive.
Interviewer"How does the application know which shard to talk to for a given request?"
Shard Routing Layer
  • WHY: Without a routing layer, every app server needs to know the current shard topology — any rebalancing breaks all clients simultaneously.
  • HOW: I run a stateless router service that holds a shard map (a lookup table: logical shard ID → physical node address) cached in memory, refreshed from a config store like ZooKeeper (a distributed coordination service). App servers talk to the router; the router forwards the query to the correct node and returns the result. The shard map is small — 200 entries — so it fits in memory and stays fast.
  • TRADEOFF: The router adds one network hop per query; I mitigate this by having app servers cache the shard map locally and only hit the router on a cache miss or topology change.
Interviewer"What happens when a physical node fills up and you need to add capacity?"
Rebalancing / Resharding
  • WHY: Without a safe rebalancing strategy, adding nodes requires downtime or risks data loss as keys move between machines mid-traffic.
  • HOW: With consistent hashing, adding a new physical node only steals key ranges from its neighbors on the ring — I migrate that subset of data in the background using a copy-then-cutover approach: copy data to the new node, keep writes dual-writing to old and new, verify checksums, then atomically update the shard map in ZooKeeper to point reads at the new node, then drain the old.
  • TRADEOFF: Dual-writes during migration double the write load on affected shards temporarily and add operational complexity.
Interviewer"How do you handle queries that span multiple shards, like a user's global activity feed?"
Cross-Shard Query Handling
  • WHY: A scatter-gather query (fan out to all shards, merge results) at 500K reads/sec would saturate every node on every timeline request.
  • HOW: I pre-compute feeds using a write-time fan-out: when user A posts, a background worker writes a feed entry into each follower's feed shard. The read path hits only one shard — the requesting user's — rather than scattering. For low-follower users this is cheap; for celebrities I cap fan-out and fall back to a lazy merge of the celebrity's shard at read time.
  • TRADEOFF: Write amplification — a celebrity with 10M followers means 10M shard writes per post, so the hybrid approach (fan-out for normal users, pull for celebrities) is a necessary complexity.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single high-traffic user (celebrity) concentrates writes on one shard, overwhelming that node while others sit idle.
Fix: I detect hot shards using per-shard write rate metrics. For celebrity users I split their data across multiple sub-shards (e.g., user_999 → shards 999_0 through 999_3) and route writes round-robin across them. Reads merge results from all sub-shards. This is sometimes called shard splitting. For read load specifically, I add read replicas (copies that take read traffic but don't accept writes) to the hot shard group.
Tradeoff: Read merges across sub-shards add latency and application complexity; this is only worth it past a clear hotspot threshold.
2Cross-shard JOIN queries (e.g., 'find mutual friends') require scatter-gather across all shards, making them O(n) in shard count.
Fix: I eliminate cross-shard JOINs at the DB layer by pre-materializing (pre-computing and storing) relationship data. For mutual friends, I store an adjacency list (a stored list of connections per user) on the same shard as the user. Complex graph queries that genuinely need cross-shard access go through an async job that runs at non-peak hours and writes results to a separate aggregation store — they don't block the hot read path.
Tradeoff: Materialized data is stale by the job cadence — not suitable for real-time social graph queries where freshness matters.
3During rebalancing, the shard map update and data migration are not atomic — a window exists where some nodes have the old map and some have the new.
Fix: I use a two-phase cutover: first, direct all writes to both old and new shards (dual-write phase) while reads still go to the old shard. Once data is fully synced and verified via checksum comparison, I update ZooKeeper atomically (single write, linearizable — guaranteed to be seen as one instant update). Clients refresh their local shard map on the next request after a ZooKeeper watch fires.
Tradeoff: Dual-write doubles write load on the affected shard range during migration, which can last minutes to hours for large shards.

Reference

API
POST/api/v1/posts— Creates a post for authenticated user; routes write to user's shard; returns post_id and shard_id
GET/api/v1/users/{user_id}/feed— Returns pre-computed feed from user's shard; no scatter-gather; supports cursor-based pagination
POST/api/v1/users/{user_id}/likes— Increments like counter on post's shard; synchronous replication to meet seconds-accurate SLA
GET/api/v1/admin/shards— Returns current shard map — logical shard IDs, physical node addresses, and per-shard write rate metrics
POST/api/v1/admin/shards/rebalance— Triggers background migration job for a specified shard range; returns job_id for tracking
Database & Storage
  • PostgreSQL per shard — mature, strong consistency within a shard, well-understood replication
  • posts(post_id BIGINT PK, user_id BIGINT, content TEXT, created_at TIMESTAMP, shard_id SMALLINT)
  • Index on (user_id, created_at DESC) per shard for feed queries; partial index on hot users only to cap index size
  • Global sequences are impossible across shards — use snowflake IDs (a timestamp + shard_id + sequence combo) to generate globally unique post_ids without coordination
