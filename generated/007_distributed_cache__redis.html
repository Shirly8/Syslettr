Distributed Cache (Redis)

A distributed cache looks simple until you hit cache stampedes, hot-key skew, or split-brain during a network partition — any of which silently corrupts your latency SLA. Interviews use it to probe whether you understand data consistency, eviction semantics, and failure modes beyond 'just add Redis'.

Interview

Interviewer
We want to add a distributed cache layer to our e-commerce platform to reduce DB load. Walk me through how you'd design it.
You
Before I start — what's the read/write ratio and peak QPS (queries per second)? Are we caching full objects or just IDs? And what's the tolerance for serving stale data — is eventual consistency acceptable, or does a price change need to be reflected immediately?
Interviewer
Peak is 500K reads/sec, 20K writes/sec — mostly product catalog and session data. A few seconds of staleness is fine for catalog, but sessions must stay consistent. Budget for roughly 2TB of hot data.
You
Good. So 96% read-heavy with a 2TB working set (data actively accessed in a window). I'll size a Redis Cluster (horizontally sharded Redis with automatic failover) at ~20 nodes of 128GB each, giving us ~2.5TB usable after replication overhead. Sessions need strong consistency — I'll use synchronous replication with WAIT commands there. Catalog can tolerate TTL-based (time-to-live, auto-expire after N seconds) invalidation. My main concerns are hot-key skew, cache stampedes, and what happens when a primary node fails mid-write.

Core Components

Interviewer"How do you actually split data across nodes, and what happens when a node goes down?"
Redis Cluster Topology
  • WHY: Without sharding (splitting data across multiple nodes), a single Redis node becomes a memory and throughput ceiling — you can't scale past one machine.
  • HOW: Redis Cluster uses consistent hashing over 16,384 hash slots — each key is mapped to a slot via CRC16, and each primary node owns a range of slots. I deploy each primary with one replica; if a primary fails, the cluster promotes its replica automatically within ~10 seconds via Raft-like leader election. I spread primaries across availability zones so a single AZ failure doesn't take down the whole cluster.
  • TRADEOFF: Multi-key operations (MGET, transactions) must target keys in the same hash slot — you either use hash tags to force co-location or lose atomic multi-key semantics.
Interviewer"How do you keep the cache consistent when the underlying DB data changes?"
Cache Invalidation Strategy
  • WHY: Without a coherent invalidation strategy, clients read stale prices or inventory counts — the cache becomes a source of bugs, not just a performance layer.
  • HOW: I use write-through (write to DB and cache atomically) for session data — consistency is mandatory. For catalog data I use TTL-based expiry (keys auto-expire after 30 seconds) combined with cache-aside (read: check cache, miss → fetch DB → populate cache). On explicit product updates I publish an invalidation event to a message queue; consumers DELETE the key in Redis before the TTL fires. This avoids both stale reads and thundering herd on the queue consumer side.
  • TRADEOFF: Write-through doubles write latency on the critical path; TTL-based catalog invalidation means up to 30s of staleness between a DB update and cache eviction.
Interviewer"The cache fills up. What gets dropped, and how do you decide?"
Eviction Policy
  • WHY: Without a defined eviction policy (the rule for which keys Redis drops when memory is full), Redis either crashes on OOM or silently drops random data — both are worse than a controlled strategy.
  • HOW: I set allkeys-lru (LRU eviction — drops the least-recently-used key across all keys, not just those with TTL) for catalog data. For sessions I use a dedicated Redis instance with volatile-lru (only evict keys that have a TTL set) so session keys without TTL are never silently dropped. I also set maxmemory-policy at 80% of total RAM to leave headroom for replication buffers.
  • TRADEOFF: LRU is approximate in Redis — it samples a configurable number of keys (default 5) rather than tracking a true LRU list, so occasionally a hotter key gets evicted; increasing the sample size improves accuracy at CPU cost.
Interviewer"A popular product key expires at the same time and you get 10,000 concurrent requests — how do you handle that?"
Cache Stampede Prevention
  • WHY: A cache stampede (thundering herd — all cache-miss requests hit DB simultaneously) can overload the DB and cause cascading failures, especially for high-traffic keys.
  • HOW: I use probabilistic early reactivation — as a key approaches its TTL, a small random fraction of reads proactively refresh it before it expires, spreading the refresh load. For the hardest hot keys I also use mutex locking: the first cache-miss thread acquires a Redis distributed lock (SET key NX PX 200 — atomic set-if-not-exists with 200ms expiry) and populates the cache; all other threads either wait or serve slightly stale data via a background-refresh pattern. I never block the read path.
  • TRADEOFF: The mutex approach adds ~10ms latency for the lock-holding request; probabilistic reactivation can cause redundant DB reads slightly before expiry.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single product (e.g., a viral item) generates 200K reads/sec against one hash slot on one Redis primary — that node becomes a hot-key (a disproportionately accessed key that overwhelms a single shard) bottleneck regardless of cluster size.
Fix: I add a local in-process cache on each app server (e.g., a small LRU map with 1-second TTL) as an L1 cache layer. Requests that hit the same host don't reach Redis at all for that 1-second window. For the most extreme keys I also use key replication — store copies under product:123:replica:0 through :N and have clients randomly select a replica suffix, spreading the load across N Redis nodes for that logical key.
Tradeoff: Local in-process caches add per-host memory pressure and introduce up to 1 second of staleness beyond the Redis TTL; key replication means invalidation must target all N replica keys, increasing write fan-out (sending one write to multiple destinations).
2Redis is single-threaded for command execution, so a slow KEYS scan or a LRANGE over a massive list on one node blocks all other commands queued behind it.
Fix: I prohibit KEYS in production — replace with SCAN (cursor-based iteration that yields small batches, non-blocking). For large sorted sets or lists I paginate reads with LRANGE start end using a page size of 100–500. I also set a per-command latency threshold in Redis config and monitor p99 latency (99th percentile — the slow tail, not the average) per node; any command exceeding 1ms triggers an alert.
Tradeoff: SCAN is not atomic — the keyspace can change between cursor pages, so it may miss recently-added keys or return duplicates; it's safe for cache warming but not for correctness-critical enumeration.
3A Redis primary fails mid-write during async replication — the replica promoted to primary is missing the last N writes, causing silent data loss.
Fix: For session data where consistency is mandatory, I use the WAIT command (blocks client until N replicas acknowledge the write, e.g., WAIT 1 100 waits for 1 replica or 100ms timeout). This converts async to semi-synchronous replication on the write path. For catalog data I accept the loss window (at most a few commands) since TTL-based refresh will self-heal within 30 seconds.
Tradeoff: WAIT adds round-trip latency to every write — roughly the replica lag (~1-5ms in same datacenter) — and degrades to fire-and-forget if the replica is down, so it's a soft guarantee not a hard one.

Reference

API
GET/api/v1/cache/{key}— Returns cached value for key; 404 if miss — caller handles DB fallback
PUT/api/v1/cache/{key}— Sets key with value and TTL (seconds) in body; used by write-through path
DELETE/api/v1/cache/{key}— Explicit invalidation; used by event consumer after DB update
POST/api/v1/cache/bulk-delete— Accepts list of keys in body; pipeline-deletes to minimize round trips
GET/api/v1/cache/_health— Returns per-node memory usage, hit rate, and p99 latency for monitoring
Database & Storage
  • Redis: primary cache store — in-memory, O(1) reads/writes, TTL-native, cluster-native
  • Schema (Redis key patterns): session:{user_id} → Hash{token, expires_at, user_agent}; product:{id} → Hash{name, price, inventory}; lock:{resource} → String (NX PX 200)
  • Index strategy: no secondary indexes needed — keys are the index; hash tags ({product}:123) force co-location for multi-key atomicity on related fields
  • Key tradeoff: storing full serialized objects (JSON blobs) vs. Redis Hashes — blobs are simpler but overwrite entire object on any field change; Hashes allow HSET on single fields but cost extra memory per entry due to per-field overhead
