Systems Design · Tier 2

Payment Gateway

Payment gateways are deceptively hard because money movement demands exactly-once execution — a bug that double-charges or drops a transaction destroys trust instantly. Interviewers use this problem to stress-test your understanding of distributed consistency, failure recovery, and security under real-world constraints.

Interview

Interviewer
Design a payment gateway — think something like Stripe or Braintree. Where do you start?
You
Before diving in — what's the transaction volume? Thousands per second or tens of thousands? Are we handling card networks (Visa/Mastercard) directly, or routing to third-party processors? And what's our SLA on payment confirmation latency?
Interviewer
Target 10,000 transactions per second at peak. Route to external processors — don't implement card network settlement. P99 latency (99th percentile — the slow tail, not the average) under 2 seconds for payment confirmation.
You
So 10K TPS peak — I'll design for 3x headroom, call it ~30K TPS capacity. Each transaction touches auth, fraud check, processor call, and a write — so I need async decoupling (breaking the flow into independent steps via queues) on non-critical paths. Assuming ~500 bytes per transaction record plus audit logs, we're looking at roughly 15TB of raw data per year. Idempotency (guaranteeing an operation produces the same result if retried) is the central concern — the system must never double-charge even if a client retries or a node crashes mid-flight.

Core Components

Interviewer"How do you actually prevent double charges if a client retries after a timeout?"
Idempotency Layer
  • WHY: Without this, a network timeout causes the client to retry and the user gets charged twice — catastrophic and nearly unrecoverable from a trust standpoint.
  • HOW: Every payment request carries a client-generated idempotency key (a unique token the caller creates, like a UUID). On receipt, I write that key to a distributed store — Redis works well — with a short TTL (time-to-live, how long the key lives before expiring), say 24 hours. If a duplicate key arrives while the first is in-flight, I return a 202 Accepted and poll for the result. If the first already completed, I return the cached response immediately without re-executing.
  • TRADEOFF: Clients must generate and store keys reliably — if they lose the key, they can't safely retry and need a manual reconciliation path.
Interviewer"How do you run fraud checks without blowing your 2-second p99 budget?"
Fraud Detection Service
  • WHY: Without fraud checks inline, the system approves fraudulent transactions; without latency control, the fraud check becomes the bottleneck that violates SLA.
  • HOW: I split fraud scoring into two tiers. Synchronous pre-auth checks — velocity rules (rate limits per card/IP), blocklists — run in-process with a hard 200ms timeout using precomputed feature flags from Redis. A heavier async ML scoring job consumes a transaction event from a queue after auth and flags transactions for human review or automated reversal within seconds. This way, clear fraud is blocked instantly and edge cases are caught asynchronously.
  • TRADEOFF: The async path means a small window exists where a borderline transaction is approved before the ML model flags it — requiring a refund flow rather than a block.
Interviewer"What happens when your external processor is down or slow?"
Payment Processor Router
  • WHY: A single processor integration makes the entire payment system dependent on one third-party's uptime — a 99.5% processor SLA means 43 hours of downtime per year.
  • HOW: I maintain integrations with at least two processors (primary and fallback). A router service checks processor health via a circuit breaker (a state machine that stops calling a failing dependency to let it recover) — if the primary's error rate exceeds 5% in a 30-second window, the circuit opens and traffic shifts to the fallback automatically. Each processor adapter normalizes the response into a common internal schema so the rest of the system is decoupled from processor-specific quirks.
  • TRADEOFF: Multi-processor contracts, fee structures, and feature parity (e.g. not all processors support the same card types) add operational complexity.
Interviewer"How do you store transaction state reliably and support reconciliation?"
Transaction Ledger (Append-Only)
  • WHY: Mutable transaction records create audit gaps and make it impossible to reconstruct exactly what happened when a dispute or reconciliation failure occurs.
  • HOW: I use an append-only ledger (a write-once log where state changes are new rows, never updates) in a relational DB. Every state transition — INITIATED, AUTHORIZED, CAPTURED, FAILED, REFUNDED — is a new row with a timestamp and the actor that triggered it. Current state is derived by reading the latest event for a transaction ID. This is event sourcing (storing state as a sequence of events rather than current value) at the data layer.
  • TRADEOFF: Querying current state requires reading and folding event history — I mitigate this with a materialized view (a precomputed read-optimized projection) updated asynchronously.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1External processor calls are synchronous and can take 800ms–1.5s, blocking threads and pushing p99 over SLA during traffic spikes.
Fix: I decouple the processor call using a request queue (a buffer that holds work items so producers and consumers operate independently). The payment service writes the transaction intent to the queue and returns a 202 Accepted immediately. A pool of processor workers consumes from the queue, calls the external processor, and writes the result back to the ledger. The client polls a /status endpoint or receives a webhook (an HTTP callback the server pushes to the client) when complete. This limits thread exhaustion — I size the worker pool to the processor's concurrency limit rather than incoming request rate.
Tradeoff: Payment confirmation becomes asynchronous — merchants must handle the async pattern in their integration, which increases SDK complexity.
2The ledger DB becomes a write bottleneck at 10K TPS — all transaction state changes funnel through one primary node.
Fix: I shard (split data across multiple DB machines) the ledger by merchant ID using consistent hashing (a sharding strategy where keys map to nodes in a ring, minimizing reshuffling when nodes are added). Each shard handles a subset of merchants, distributing write load horizontally. For read-heavy reconciliation queries, I add read replicas (copies of the DB that handle reads only) per shard. The application layer routes writes to the correct shard via a thin routing layer that maps merchant IDs to shard addresses.
Tradeoff: Cross-shard queries — like global reconciliation reports — require scatter-gather (fan-out reads across all shards then merge) which is expensive and must be run offline.
3Fraud ML model inference is slow (200–500ms) and can't run synchronously without violating the 2-second p99 budget during high load.
Fix: I pre-compute risk feature vectors (numeric summaries of user behavior) for known cards and merchants in a background job, storing them in Redis with a short TTL. At transaction time, the sync fraud check reads the precomputed vector and applies lightweight rule scoring in under 20ms. Full ML inference runs asynchronously via the event queue and can trigger automated reversal within 5 seconds if the score exceeds a threshold.
Tradeoff: Precomputed features are stale by their TTL — a card compromised in the last few minutes may not yet show elevated risk scores.

Reference

API
POST/api/v1/payments— Initiates a payment; requires Idempotency-Key header; returns 202 Accepted with transaction_id and status=PENDING
GET/api/v1/payments/{transaction_id}— Returns current payment status and full event history for polling or dispute lookup
POST/api/v1/payments/{transaction_id}/refund— Initiates a full or partial refund; idempotent; appends REFUND_INITIATED event to ledger
POST/api/v1/webhooks— Registers a merchant webhook URL for async payment status push notifications
GET/api/v1/merchants/{merchant_id}/transactions— Paginated transaction history for a merchant; supports date range and status filters
Database & Storage
  • PostgreSQL for the transaction ledger — ACID guarantees (atomic, consistent, isolated, durable — all-or-nothing writes) are non-negotiable for financial records
  • Schema: transactions(id UUID PK, merchant_id UUID, amount BIGINT, currency CHAR(3), status VARCHAR(20), created_at TIMESTAMPTZ, idempotency_key VARCHAR(128) UNIQUE); transaction_events(id UUID PK, transaction_id UUID FK, event_type VARCHAR(30), payload JSONB, occurred_at TIMESTAMPTZ)
  • Index on (merchant_id, created_at DESC) for merchant history queries; index on idempotency_key for dedup lookups; partial index on status WHERE status IN ('PENDING','AUTHORIZED') for active transaction sweeps
  • Storing amounts as BIGINT in smallest currency unit (cents) avoids floating-point rounding errors — never store money as FLOAT
