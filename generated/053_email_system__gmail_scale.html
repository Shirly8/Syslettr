Email System (Gmail-scale)

An email system looks simple until you realize a single send can fan out to millions of recipients, each needing their own durable, searchable, queryable mailbox copy. Interviewers use it to probe distributed storage, fan-out write amplification, and full-text search — all in one problem.

Interview

Interviewer
Design an email system at Gmail scale — sending, receiving, storing, and searching messages. Where do you start?
You
Before diving in — are we building the full stack including SMTP (Simple Mail Transfer Protocol, the standard for routing email between servers) handling, or just the internal storage and delivery pipeline? And what's the DAU (daily active users) target — are we talking 1 billion users or something smaller? Finally, do we need real-time search or is eventual consistency on the index acceptable?
Interviewer
Full stack — inbound SMTP, delivery to mailboxes, storage, and search. 1.5 billion users, roughly 5 billion emails per day. Search results can lag by a few seconds.
You
So about 58K emails per second sustained, with spikes probably 3-5x that — call it 300K/sec peak. Each email averages maybe 75KB with attachments stored separately, so raw message throughput is around 4GB/sec at peak. I'll plan for roughly 1.5PB of new email storage per year. Search lag of a few seconds means I can build an async index pipeline rather than synchronous writes, which removes a nasty bottleneck. I'll assume multi-device access, so IMAP-style (Internet Message Access Protocol — sync state across devices) semantics, not POP3.

Core Components

Interviewer"How do you handle inbound email from the public internet without getting crushed by spam or being an open relay?"
SMTP Inbound Gateway
  • WHY: Without a hardened entry layer, every spam flood, spoofed sender, or malformed message reaches your internal pipeline and corrupts or overwhelms it.
  • HOW: I run a fleet of stateless SMTP gateway servers behind Anycast IPs (routing that sends traffic to the nearest server automatically) that handle the raw TCP connections. They apply rate limiting per sending IP, check SPF/DKIM/DMARC (sender authentication standards that verify the email isn't forged), and do a first-pass spam score. Messages that pass go onto an inbound queue; rejected ones get a 5xx SMTP response so the sender knows it's permanent. I keep these stateless so I can scale horizontally without coordination.
  • TRADEOFF: Running full spam analysis at the gateway adds 100-200ms to acceptance — legitimate senders with slow retry logic may see delays.
Interviewer"If one email goes to a mailing list with 10 million recipients, how do you write it to all those mailboxes without killing your storage layer?"
Fan-out Delivery Service
  • WHY: Naive per-recipient writes at 10M copies per message would saturate storage I/O and cause head-of-line blocking (one huge job stalls everything behind it in the queue).
  • HOW: I use a two-tier approach: store exactly one copy of the message body in a blob store (object storage for large unstructured data) keyed by content hash. Each recipient gets only a lightweight metadata record — message ID, folder, flags, timestamp — written to their mailbox shard. The fan-out worker reads from the inbound queue, writes the body blob once, then publishes N small mailbox pointer records. For truly massive lists I fan out in parallel batches of 10K per worker so no single worker blocks.
  • TRADEOFF: This complicates reads — fetching a message requires joining the mailbox pointer with the blob store — adding one network hop per read.
Interviewer"How do you shard (split data across machines) a billion mailboxes and keep reads fast?"
Mailbox Storage Layer
  • WHY: A single database cannot hold 1.5PB of email metadata and serve low-latency folder views for 1.5B users.
  • HOW: I shard by user ID using consistent hashing (a technique that maps keys to nodes so adding/removing nodes only remaps a fraction of data). Each shard owns a contiguous range of user IDs, so all folder and thread queries for a user hit a single shard — no cross-shard joins. Within a shard I use a wide-column store (a database that organizes data by row key then column families, optimized for range scans) with the row key as (user_id + folder_id + reverse_timestamp) so inbox reads are a sequential prefix scan, which is fast.
  • TRADEOFF: If a celebrity account receives billions of emails, that single shard becomes a hot spot — I'd need a secondary sharding layer or dedicated shard for such accounts.
Interviewer"How do you make 15 years of email searchable in under a second for each user?"
Full-Text Search Index
  • WHY: Without per-user search indexes, every query would require a full table scan of hundreds of billions of rows — completely infeasible.
  • HOW: When a message is delivered, a search indexer worker consumes from the same inbound queue and builds an inverted index (a map from each word to the list of message IDs containing it) scoped per user. I partition the search cluster by user ID so a user's query hits exactly one search node holding their index. The index stores term → list of (message_id, field, position) so I can rank by recency and field weight (subject matches rank higher than body). With a few-second lag allowed, I can batch index updates every 2 seconds instead of per-message, which dramatically reduces write amplification.
  • TRADEOFF: Per-user index partitioning means index nodes can't easily share work — a user with 20 years of email has a large index that must fit on one node.
Interviewer"How do you reliably send email to external domains without getting your IPs blacklisted?"
Outbound SMTP Delivery
  • WHY: Without IP reputation management, a single spam campaign from one user will get the entire sending IP range blacklisted, breaking delivery for everyone.
  • HOW: I maintain pools of sending IPs segmented by reputation tier — bulk marketing email and transactional confirmations use separate IP pools so they can't poison each other. Outbound workers pull from a priority queue (high-priority: direct user sends; low-priority: bulk) and apply per-domain throttling because large ISPs like Yahoo rate-limit by sending IP. I track bounce rates and spam complaints per IP via feedback loop integrations (ISP programs that report spam clicks back to the sender) and automatically rotate an IP out of the pool if its bounce rate exceeds 2%.
  • TRADEOFF: Segmented IP pools mean bulk emails get a separate queue with lower priority, so marketing sends can be delayed during traffic spikes.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Fan-out to a 10M-member mailing list creates a write storm that saturates mailbox shard I/O for minutes.
Fix: I decouple the fan-out into two stages: a 'list exploder' service writes to a secondary expansion queue partitioned by user ID shard, and each shard's writer consumes only its own partition at a rate it can sustain. This turns one thundering herd into N independent, back-pressured (slowing producers when consumers fall behind) streams. Delivery SLA for large lists becomes best-effort with a time cap (say, 30 minutes) rather than a hard real-time guarantee.
Tradeoff: Recipients on a large list can see the email arrive at different times — some immediately, some minutes later.
2Full-text search on 15 years of email per user causes index nodes to run out of memory and serve slow queries.
Fix: I tier the search index: the last 90 days (hot tier) stays in memory on fast nodes; older email is in a compressed disk-based index (cold tier). The query router sends the query to both tiers in parallel and merges results, returning the top-N most relevant. Cold tier nodes can be much cheaper (high-density disk) since query latency there is bounded by result count, not user SLA.
Tradeoff: Cold-tier queries take 2-5x longer — acceptable for archive search but bad if users expect uniform latency across all time ranges.
3A single Blob Store cluster becomes a hotspot when large attachments are fetched by millions of users.
Fix: I put a CDN (Content Delivery Network — edge servers that cache content close to users) layer in front of the blob store for read requests. Attachment URLs are pre-signed (short-lived authenticated URLs) with a 1-hour TTL (time-to-live — how long a cached response is considered fresh) and cache at the CDN edge. Only cache misses hit the origin blob store. For attachments over 25MB I use ranged byte requests so clients can resume interrupted downloads without re-fetching the whole file.
Tradeoff: Pre-signed URLs mean that if you share an attachment link with someone outside your org, it expires after one hour — usability issue for external sharing use cases.

API
POST/api/v1/messages— Compose and send; body includes to/cc/bcc/subject/body/attachment_ids; returns message_id and queued status
GET/api/v1/mailbox/{folder}?page_token={tok}&limit=50— List messages in folder, keyed by cursor for pagination; returns message summaries and next_page_token
GET/api/v1/messages/{message_id}— Fetch full message including headers and body; attachment URLs are pre-signed blob store links
PATCH/api/v1/messages/{message_id}— Update flags (read, starred, archived, label); returns updated message state
DELETE/api/v1/messages/{message_id}— Soft-delete to Trash with 30-day expiry; returns 204 on success
POST/api/v1/attachments— Upload attachment before send; returns attachment_id and pre-signed upload URL for direct-to-blob-store upload
GET/api/v1/search?q={query}&limit=20&offset=0— Full-text search scoped to authenticated user; returns ranked message summaries with snippet highlights
Database & Storage
  • Wide-column store (e.g., Bigtable-style) for mailbox metadata — row-key prefix scans give fast inbox reads without full table scans
  • Schema: mailbox_messages(row_key=user_id+folder_id+~timestamp STRING PK, message_id STRING, thread_id STRING, from_addr STRING, subject STRING, snippet STRING, flags BYTES, blob_key STRING)
  • Index: row key is the primary index — reverse timestamp in key means newest messages sort first on range scan; secondary index on thread_id per user for conversation view
  • Object/blob store for message bodies — content-addressed by SHA-256 hash enables deduplication; bodies are immutable so no update path needed
  • Schema: message_blobs(blob_key STRING PK, body BYTES, size_bytes INT, created_at TIMESTAMP)
  • Search index stored in inverted index nodes partitioned by user_id — term maps to posting list of (message_id, field_weight, timestamp); tiered hot/cold by message age
  • Key tradeoff: denormalizing snippet and flags into the mailbox row avoids a blob fetch for inbox list view, but means flags updates require two writes (mailbox row + no blob update needed)
