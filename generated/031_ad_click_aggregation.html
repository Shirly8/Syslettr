Ad Click Aggregation

Ad click aggregation is deceptively hard because you need both low-latency raw event ingestion and accurate, queryable aggregate counts — two workloads with completely different access patterns that fight each other. Interviewers use it to probe your understanding of stream processing, eventual consistency, and the precision-vs-throughput tradeoff under extreme write pressure.

Interview

Interviewer
We need to build a system that tracks ad clicks and lets advertisers query aggregated metrics — things like clicks per ad per minute. Where do you start?
You
Before diving in — what's the click volume we're targeting, hundreds of millions per day or more? Do advertisers need real-time dashboards or is a few minutes of lag acceptable? And are we aggregating only clicks, or also impressions and conversions?
Interviewer
One billion clicks per day. Advertisers can tolerate up to one minute of staleness. Focus on clicks only for now, but the design should be extensible.
You
One billion clicks per day is roughly 11,500 clicks per second at peak, and realistically 2x that at peak hours — call it ~25,000 writes/sec. Read queries (advertisers pulling aggregates) are far fewer, maybe 1,000/sec. The core tension is that the write path needs to be near-instant acknowledgment while the aggregation (rolling up raw events into counts by ad_id and time bucket) can be slightly delayed. I'll separate the hot write path from the aggregation pipeline entirely.

Core Components

Interviewer"How does the ingestion layer handle 25,000 writes per second without becoming a bottleneck?"
Click Ingestion API
  • WHY: If ingestion is synchronous all the way to the DB, a slow aggregation query or DB spike kills write throughput and drops clicks — which is lost revenue data.
  • HOW: The ingestion service is stateless and horizontally scalable behind a load balancer. It validates the click event (ad_id, user_id, timestamp, IP), deduplicates obvious duplicates in a short-window bloom filter (a probabilistic data structure that quickly checks if an item was recently seen), then immediately publishes to a durable message queue. It returns 200 to the client as soon as the event is enqueued — not after it's aggregated.
  • TRADEOFF: Fire-and-forget after enqueue means if the queue has an outage, events can be lost unless the queue itself has replication and disk persistence enabled.
Interviewer"How do you compute accurate per-minute click counts from that queue without double-counting or missing events?"
Stream Aggregation Layer
  • WHY: If you try to aggregate at query time by scanning raw events, you're doing full scans over billions of rows per query — completely unacceptable latency.
  • HOW: Consumer workers pull batches of click events from the queue and maintain in-memory counters keyed by (ad_id, minute_bucket). Every 60 seconds, each worker flushes its partial counts to a time-series store using an atomic increment (add-and-return operation, not read-then-write). The aggregation is idempotent if the queue delivers each event exactly-once or at-least-once with deduplication — I use the event's UUID to skip reprocessing.
  • TRADEOFF: In-memory accumulation means a worker crash within the flush window can lose up to 60 seconds of counts — acceptable given the stated one-minute staleness SLA.
Interviewer"What does the read path look like when an advertiser queries clicks for their ad over the last 24 hours?"
Aggregate Query Service
  • WHY: Without a dedicated read layer, raw time-series scans at query time are slow and compete with the write path.
  • HOW: The query service fetches pre-aggregated minute-level buckets from the time-series store for the requested (ad_id, time_range), sums them in-process, and returns the result. For popular ads queried repeatedly, I cache the response at the query service layer with a TTL (time-to-live — expiry after N seconds) of 60 seconds, matching the staleness SLA.
  • TRADEOFF: Caching at the query layer means two advertisers querying the same ad within the same 60-second window get the same stale number — usually fine, but makes real-time dashboards feel slightly laggy.
Interviewer"Users double-click ads, bots replay events — how do you prevent inflated counts?"
Deduplication Store
  • WHY: Without dedup, a single accidental double-click or a bot replay inflates an advertiser's bill — that's a direct financial and trust issue.
  • HOW: At ingestion, I check a short-window dedup store (a key-value store keyed by event UUID with a 10-minute TTL) before enqueuing. If the UUID already exists, I drop the event and still return 200 to the client. The bloom filter handles the fast path for obviously new events; the key-value store handles the slow path for actual UUID lookups.
  • TRADEOFF: The 10-minute TTL window means replayed events older than 10 minutes can slip through — acceptable for accidental duplicates, and a longer TTL would require significantly more memory.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single hot ad (viral campaign) concentrates millions of clicks per second onto one queue partition and one aggregation worker, creating a write hotspot that delays counts for that ad.
Fix: I split hot ad partitions further using a compound partition key: (ad_id + shard_suffix), where shard_suffix is a random integer 0–9. This distributes one ad's traffic across 10 workers. Each worker writes partial counts, and a combiner step sums the 10 shards before writing the final bucket to the time-series store. The combiner runs every flush cycle — it's just 10 reads and one write, cheap.
Tradeoff: Adding the combiner step introduces one extra hop of latency (~1–2 seconds) before counts are visible, and the combiner itself becomes a coordination point that needs its own fault tolerance.
2The time-series store becomes a write bottleneck when all aggregation workers flush simultaneously at the top of every minute, creating a thundering herd (all clients hitting the server at once).
Fix: I add jitter (random delay, 0–10 seconds) to each worker's flush schedule so flushes are spread across the minute rather than synchronized. This turns a spike of 500 simultaneous writes into a steady stream of ~8 writes/second, which the time-series store handles trivially.
Tradeoff: Jitter means any individual ad's count can be up to 10 seconds more stale than the 60-second SLA — still within the one-minute bound, but worth flagging.
3The dedup key-value store becomes a write hotspot because every click event requires both a read (does this UUID exist?) and a write (mark it seen) before enqueuing.
Fix: I move the primary dedup check to an in-process bloom filter (probabilistic — fast but has a small false-positive rate where a new event is wrongly flagged as a duplicate). The key-value store is only hit when the bloom filter says 'maybe seen' — roughly 1% of traffic. The bloom filter is reset every 10 minutes to match the TTL window.
Tradeoff: Bloom filter false positives (~0.1% at tuned size) mean a tiny fraction of legitimate clicks are dropped — acceptable for ad counting, but would be unacceptable for billing-grade precision.

Reference

API
POST/api/v1/clicks— Receives a click event (ad_id, user_id, timestamp, UUID); validates, deduplicates, and enqueues; returns 200 immediately — does not wait for aggregation
GET/api/v1/clicks/aggregate?ad_id={id}&start={ts}&end={ts}&granularity={minute|hour}— Returns pre-aggregated click counts for the given ad and time range, bucketed at the requested granularity; served from cache when available
GET/api/v1/clicks/raw?ad_id={id}&start={ts}&end={ts}&limit={n}— Returns paginated raw click events for audit or debugging; bypasses the aggregation layer and reads from raw event store directly
Database & Storage
  • Time-Series DB (e.g., column-oriented, append-optimized) — pre-aggregated counts have a fixed write pattern (ad_id + minute bucket) that maps naturally to time-series storage's compression and range-scan strengths
  • Schema: click_counts(ad_id VARCHAR PK, bucket_ts TIMESTAMP PK, click_count BIGINT) — composite primary key on (ad_id, bucket_ts) enables fast range scans per ad
  • Index strategy: primary key IS the index — data is stored sorted by (ad_id, bucket_ts) so range queries like 'all buckets for ad_42 in the last hour' are sequential reads, no secondary index needed
  • Key tradeoff: pre-aggregating at minute granularity means you can't drill below one minute without also keeping raw events in a separate cold store — raw event storage costs ~500GB/day at 1B clicks, so retention needs a TTL policy (e.g., 7 days raw, 2 years aggregated)
