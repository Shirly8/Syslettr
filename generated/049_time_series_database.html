Time Series Database

Time series data looks simple — just timestamps and values — but the write volume, compression requirements, and time-range query patterns make naive relational or document stores collapse under load. Interviewers use this to test whether you understand columnar storage, LSM trees, and the specific tradeoffs that make generic databases fail at this problem.

Interview

Interviewer
We want to build a time series database to store and query metrics from a large fleet of servers — think CPU, memory, disk I/O. Walk me through how you'd design it.
You
Before I start — what's the ingestion rate? Thousands of metrics/sec or millions? And what's the primary query pattern — real-time dashboards, alerting, or long-term analytics with aggregations over months? Also, what retention window do we need?
Interviewer
Ten million data points per second at peak. Queries are mostly real-time dashboards and alerting — sub-second p99 for the last hour, slower is fine for multi-month aggregations. Keep data for two years.
You
So 10M writes/sec sustained, let's plan for 15M at burst. Each data point is a tuple: (metric name, tags, timestamp, float64 value) — roughly 100 bytes uncompressed, so ~1.5 GB/sec raw ingest. At two years that's about 90 PB uncompressed — compression (encoding repeated patterns to reduce bytes on disk) is non-negotiable; delta-of-delta encoding (storing differences between consecutive timestamps rather than absolute values) plus XOR compression on floats typically gives 10-20x, landing around 5-9 PB on disk. For the query SLA I'll separate the hot path (last 24 hours, in-memory or SSD) from the cold path (older data, compressed on object storage). I'll design around an LSM-tree (Log-Structured Merge-tree — append-only writes flushed to disk in sorted runs) write path and columnar (data stored column-by-column, not row-by-row) storage for reads.

Core Components

Interviewer"Ten million writes per second is a lot — how do you actually absorb that without dropping data or overwhelming the storage layer?"
Ingestion Layer
  • WHY: Without a buffer in front of storage, bursty metric spikes overwhelm the write path and cause back-pressure that drops data points.
  • HOW: I put a distributed write-ahead log (WAL — an ordered, append-only log that survives crashes) in front of storage. Producers batch data points into ~100ms micro-batches and publish to the WAL partitioned by metric name hash. Downstream, storage workers consume from the WAL, accumulate points in an in-memory write buffer (memtable — the in-RAM sorted data structure before flush), and flush to immutable SSTable files (Sorted String Tables — sorted, compressed on-disk files) when the buffer hits a size threshold or time limit. This decouples ingest rate from storage I/O.
  • TRADEOFF: The WAL adds up to 100-200ms of end-to-end latency for a data point to become queryable, which is acceptable for dashboards but rules out sub-millisecond alerting directly on ingested data.
Interviewer"Walk me through how you'd actually compress the data — what techniques apply specifically to time series?"
Compression & Storage Engine
  • WHY: Without time-series-specific compression, raw float64 data at 10M points/sec produces petabytes we can't afford to store or scan quickly.
  • HOW: I apply two-stage compression. For timestamps: delta-of-delta encoding — store the difference between consecutive deltas (e.g., if samples are 10s apart, store 0 instead of the full epoch). For values: Gorilla XOR compression (Facebook's algorithm — XOR consecutive float64 values and encode only the meaningful bits that changed). Together these achieve 10-20x compression. Data is then written columnar: timestamps in one column, values in another, tags in a separate dictionary-encoded column, all within an SSTable. Columnar layout means a range scan reads only the timestamp and value columns — skipping tags entirely.
  • TRADEOFF: Compressed columnar files are write-once and immutable, so updates or late-arriving data require a compaction (background merge of overlapping SSTables) pass, adding CPU overhead.
Interviewer"How do you serve sub-second queries over the last hour while also handling queries that span two years?"
Query Engine
  • WHY: Treating hot and cold data the same way forces a tradeoff — either you waste RAM on cold data or you page-fault on hot queries.
  • HOW: I tier storage into three layers. Hot tier: last 24 hours in-memory memtables and SSD-resident SSTables — queries hit this directly with no decompression overhead. Warm tier: last 30 days on local NVMe, compressed SSTables — queries decompress on the fly, still fast enough for dashboards. Cold tier: data beyond 30 days on object storage (e.g., distributed blob store), queries run with pre-aggregated rollup tables (downsampled summaries — e.g., one point per minute instead of per second) so we don't scan raw data. The query planner routes by time range to the appropriate tier automatically.
  • TRADEOFF: Rollups lose raw resolution — a two-year query can't return per-second granularity, only per-minute or per-hour aggregates.
Interviewer"With petabytes of data across potentially thousands of metrics, how do you decide which node holds what data?"
Sharding & Routing
  • WHY: If all writes for a popular metric land on one node, that node becomes a hot shard (single overloaded machine) and saturates while others idle.
  • HOW: I shard by (metric_name, time_window) — consistent hashing (a ring-based scheme where adding/removing nodes rebalances minimally) maps each metric to a primary storage node, and I keep one week of data per shard boundary. This keeps time-range scans local to one or a few nodes since consecutive weeks hash nearby. For tag-based queries (e.g., 'all CPU metrics for host=web-01'), I maintain a separate inverted index (mapping from tag value → list of metric shards) on a small metadata cluster.
  • TRADEOFF: Metric-based sharding means a 'GROUP BY host' query fans out to all shards — it's expensive and requires scatter-gather.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Compaction (merging overlapping SSTables) is CPU and I/O intensive and competes directly with live read/write traffic on the same node.
Fix: I separate compaction onto dedicated compaction nodes that pull SSTables from storage, merge and re-compress them, and write back — the primary storage nodes never run compaction. I also throttle compaction I/O using a token bucket (rate limiter — allows bursts but caps sustained throughput) so it can't saturate the disk during peak write hours. Compaction runs aggressively during off-peak windows.
Tradeoff: Adding compaction nodes increases hardware cost and adds network round-trips for SSTable transfer, which extends the time between compaction runs.
2High-cardinality tag queries (e.g., filter by one tag value across millions of unique tag combinations) require scanning all shards and produce massive fan-out.
Fix: I pre-build a posting list index (an inverted index mapping each tag key-value pair to a list of matching series IDs) stored separately from the time series data. When a query comes in like 'host=web-01, metric=cpu', I look up both tag values in the posting list, intersect the series ID lists in memory, then fetch only those series from storage. This reduces shard fan-out from 'all shards' to only the shards holding matched series.
Tradeoff: The posting list must be updated on every new series ingestion and grows proportionally to cardinality — at billions of unique series, the index itself needs sharding and becomes a consistency challenge.
3A single popular metric (e.g., 'cluster-wide CPU average') receives disproportionate write volume, hot-spotting one shard.
Fix: I detect hot metrics at the ingest gateway using a count-min sketch (a probabilistic data structure that estimates item frequency with low memory). When a metric exceeds a write-rate threshold, I add a shard suffix (e.g., cpu_total_0, cpu_total_1) and round-robin writes across N virtual shards. Reads merge results from all N shards. The gateway maintains the shard map in a small consistent metadata store.
Tradeoff: Scatter-gather reads across N shards for a hot metric adds latency proportional to N and increases query complexity.

API
POST/api/v1/write— Accepts batch of data points [{metric, tags, timestamp, value}]; returns 204 on success, 207 on partial failure with error detail per point
GET/api/v1/query?metric=cpu&tags=host:web01&start=1700000000&end=1700003600&step=60— Returns time-range aggregated series; step param controls rollup granularity in seconds
GET/api/v1/series?metric=cpu&tags=host:web01— Returns all matching series IDs and their tag sets — used by dashboards for label discovery
DELETE/api/v1/series/{series_id}?older_than=1680000000— Marks series data before given timestamp for deletion during next compaction cycle
GET/api/v1/metadata/tags?metric=cpu— Returns all tag keys and their distinct values for a given metric — powers autocomplete UIs
Database & Storage
  • Primary storage: custom LSM-tree SSTable engine — time series write patterns (append-only, ordered by time) match LSM perfectly; random-update stores like B-tree would cause excessive write amplification (one logical write causing many physical writes).
  • Schema (conceptual columnar block): series_id UINT64 PK, timestamp_col BYTES (delta-of-delta encoded), value_col BYTES (Gorilla XOR encoded), min_ts INT64, max_ts INT64, block_size INT32
  • Index strategy: bloom filter per SSTable block for fast series-miss detection; min/max timestamp index per block for time-range pruning; separate posting-list index store (tag_key STRING, tag_value STRING, series_ids BYTES) with tag pair as PK.
  • Key tradeoff: columnar block layout optimizes range scans and compression but makes point lookups (fetch exactly one timestamp) expensive — they require decompressing an entire block even to read one value.
