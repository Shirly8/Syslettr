Systems Design · Tier 2

A/B Testing Platform

An A/B testing platform looks like a feature flag system until you realize it must guarantee the same user always sees the same variant, aggregate statistical metrics correctly at scale, and avoid assignment bias — all without adding meaningful latency to every request. Interviewers use it to probe distributed consistency, event pipelines, and statistical rigor simultaneously.

Interview

Interviewer
We want to build an internal A/B testing platform so product teams can run experiments on our web and mobile surfaces. Where would you start?
You
Before diving in — what's the traffic scale? Are we assigning variants to millions of users or hundreds of millions? And do we need real-time results, or is a few-hour lag on metric aggregation acceptable? Also, are experiments purely on the backend or do we need client-side SDKs too?
Interviewer
Assume 500 million monthly active users, up to 100 concurrent experiments. Metric lag of a few hours is fine. We need both server-side and client-side SDK support.
You
So roughly 500M users, 100 live experiments — that's up to 50 billion experiment-user assignment combinations in the worst case, though most users touch only a handful of experiments. Assignment reads need to be sub-10ms since they're in the request hot path; I'll treat them as a cache read. Event ingestion for metric collection I'd design for ~50K events/sec at peak, fanned into a stream processing pipeline (a queue-based system where consumers compute metrics in near-real-time). I'll assume statistical significance is computed offline on a batch cadence, not streamed. I'll plan for assignment data stored in a fast key-value store and raw event data in a columnar warehouse.

Core Components

Interviewer"How do experiment configs get to your assignment service without adding a database call to every request?"
Experiment Configuration Service
  • WHY: If assignment logic queries a database on every API request, you've added a synchronous DB round-trip to every user-facing call — that breaks latency SLAs.
  • HOW: I store experiment configs (rules defining which users are eligible, traffic split percentages, variant definitions) in a persistent store like a relational DB for durability. On startup, each assignment service node pulls the full config into memory. I use a pub/sub channel (a broadcast mechanism where config changes are pushed to all subscribers) so any config update propagates to all nodes within seconds — no polling. Nodes serve assignments entirely from in-memory state.
  • TRADEOFF: There's a brief window where nodes can have stale configs during propagation — acceptable for experiments but would need a stricter approach for kill-switches.
Interviewer"How do you guarantee the same user always gets the same variant, even across different servers or sessions?"
Variant Assignment Engine
  • WHY: If assignment is random per-request, the same user can flip between variants — that contaminates the experiment and produces meaningless metrics.
  • HOW: I use deterministic hashing (a function that always maps the same input to the same output): hash(user_id + experiment_id) mod 10000 gives a bucket from 0–9999. Each variant owns a contiguous range of buckets, e.g. control gets 0–4999, treatment gets 5000–9999 for a 50/50 split. No DB lookup needed — the assignment is computed inline from the config already in memory. For user eligibility (e.g. only logged-in users, only iOS), I evaluate rules against the request context before hashing.
  • TRADEOFF: If you change bucket ranges mid-experiment to adjust traffic split, users already assigned can switch variants — so I treat traffic splits as immutable after launch.
Interviewer"How do you collect metric events like clicks and conversions without overwhelming your analysis store?"
Event Ingestion Pipeline
  • WHY: Writing 50K events/sec directly to an analytical database creates write contention and can drop events under spike load.
  • HOW: Client SDKs and backend services emit events to a message queue (a durable buffer that decouples producers from consumers). Consumers read from the queue in micro-batches and write to a columnar store (a database that stores data column-by-column, optimized for aggregation queries) designed for append-heavy workloads. I keep the event schema minimal: experiment_id, variant_id, user_id, event_type, timestamp, and an optional numeric value (for revenue-type metrics).
  • TRADEOFF: Micro-batching adds a few minutes of ingestion lag — acceptable for our hours-level SLA but rules out real-time dashboards.
Interviewer"How do you compute whether a result is statistically significant at scale?"
Metric Aggregation & Significance Engine
  • WHY: Naive per-query aggregation over billions of raw events is too slow and too expensive to run on demand.
  • HOW: I run a periodic batch job (every 1–4 hours) that reads from the columnar store, computes per-variant means and variances for each metric, then runs a t-test (a statistical test comparing two group means accounting for variance). Results — including p-value (the probability the observed difference is due to chance), confidence intervals, and sample sizes — are written to a results table. The UI reads only from this pre-aggregated results table, never the raw events.
  • TRADEOFF: Significance is computed on a lag, so experimenters can't watch results update in real-time — but this also reduces the temptation to stop experiments early (peeking problem).
Interviewer"Do you need to log every assignment, and how do you avoid double-counting users in your metrics?"
Assignment Logging & Deduplication
  • WHY: If a user is exposed to a variant 100 times in a session, counting each exposure as a separate observation inflates sample size and distorts variance calculations.
  • HOW: I log the first exposure per user per experiment to a deduplicated assignments table, keyed on (user_id, experiment_id). On the client SDK side, I use a local flag to avoid re-emitting exposure events within a session. On the ingestion side, I deduplicate at batch-write time using an upsert (insert-or-ignore) pattern before metrics are aggregated.
  • TRADEOFF: First-exposure deduplication means a user who sees the experiment on day 1 and returns on day 10 is still counted once — which is typically the right behavior but requires careful definition per experiment type.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Assignment API becomes a hot path bottleneck if every request requires a network call to a central service.
Fix: I move assignment logic into an SDK that runs in-process (directly inside the calling service or browser, no network hop). The SDK holds a local copy of experiment configs, refreshed via the pub/sub channel. For server-side SDKs, I embed the library into the application binary; for client-side, it's a lightweight JS bundle. This eliminates the network round-trip entirely for the common case.
Tradeoff: Config updates now propagate asynchronously to each SDK instance, so there's a window of a few seconds where nodes may run on stale configs — acceptable for experiments but not for emergency kill-switches, which need a faster override path.
2Naive hashing produces correlated assignments when two experiments share the same user segments, biasing results.
Fix: I use experiment-specific salting: the hash input is hash(user_id + experiment_id), not just hash(user_id). This ensures each experiment independently randomizes users. Additionally, I maintain a mutual exclusion layer where experiments that share the same surface are grouped into namespaces, and namespace bucket ranges are non-overlapping — users in one experiment are excluded from others in the same namespace.
Tradeoff: Mutual exclusion reduces the available traffic pool per experiment, meaning experiments take longer to reach statistical significance.
3Event queue consumers fall behind under spike load, causing hours-long delays in metric computation.
Fix: I partition (split) the event queue by experiment_id so consumers scale horizontally — adding more consumers handles more partitions. I also apply back-pressure (a signal from consumers to producers to slow emission rate) at the SDK level so bursts are absorbed by the queue depth rather than lost. For large-scale spikes I pre-scale consumers based on experiment launch schedules known in advance.
Tradeoff: Partitioning by experiment_id means a single very high-volume experiment can still saturate its partition — I'd need sub-partitioning by user_id hash for those edge cases.

Reference

API
POST/api/v1/experiments— Creates a new experiment; body includes name, hypothesis, eligible segments, traffic split, metric definitions; returns experiment_id
GET/api/v1/assignments?user_id={id}&experiment_ids={ids}— Returns variant assignments for a user across one or more experiments; response is a map of experiment_id → variant_id; SDK calls this on bootstrap or uses local hash
POST/api/v1/events— Batch ingest endpoint for metric events; body is array of {experiment_id, variant_id, user_id, event_type, value, timestamp}; returns 202 Accepted
GET/api/v1/experiments/{id}/results— Returns pre-aggregated stats per variant: mean, variance, sample_size, p_value, confidence_interval; reads from results table, not raw events
POST/api/v1/experiments/{id}/stop— Stops an experiment and locks variant assignments; records a winner or inconclusive decision
Database & Storage
  • Relational DB (Postgres) for experiment config — structured, low volume, needs ACID (all-or-nothing writes) for safe config updates
  • Schema: experiments(id UUID PK, name TEXT, status TEXT, traffic_split JSONB, segments JSONB, created_at TIMESTAMPTZ); variants(id UUID PK, experiment_id UUID FK, name TEXT, bucket_start INT, bucket_end INT)
  • Columnar store (e.g. Parquet on object storage + query engine) for raw events — append-only, optimized for aggregation over experiment_id and variant_id columns
  • Schema: events(experiment_id UUID, variant_id UUID, user_id UUID, event_type TEXT, value FLOAT, ts TIMESTAMPTZ) partitioned by date and experiment_id
  • Results table in Postgres: results(experiment_id UUID, variant_id UUID, metric TEXT, mean FLOAT, variance FLOAT, sample_size BIGINT, p_value FLOAT, computed_at TIMESTAMPTZ) — UI reads only here
  • Index on events is unnecessary for the columnar store — partition pruning by experiment_id + date handles query performance; for Postgres results table, index on (experiment_id, computed_at DESC) for fast latest-results lookup
  • Key tradeoff: storing raw events in a columnar warehouse is cheap and flexible but requires a batch job to populate the results table — there's no path to sub-minute metric freshness without a streaming aggregation layer
