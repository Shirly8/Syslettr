Chat System

A chat system looks deceptively simple but requires solving bidirectional real-time communication, message ordering, and fan-out (delivering one message to many recipients) simultaneously — all under strict latency budgets. Interviewers use it to probe whether candidates understand long-lived connections, delivery guarantees, and the sharp tradeoffs between different persistence and fan-out strategies.

Interview

Interviewer
Design a chat system like WhatsApp or Slack. Where would you start?
You
Before diving in — are we targeting 1:1 DMs, group chats, or both? What's the DAU (daily active users) target — tens of millions or hundreds of millions? And do we need read receipts, message history search, or just delivery and storage?
Interviewer
Support both 1:1 and group chats, groups capped at 500 members. 500 million DAU. Focus on sending, delivery, and history — no full-text search for now. Messages must be delivered within 500ms p99 under normal load.
You
Okay — 500M DAU, assume each user sends 10 messages/day: that's roughly 58K writes/sec and likely 10x that in reads, so ~580K reads/sec. For group chats at 500 members, worst-case fan-out (pushing one message to all recipients) is 500 deliveries per write — I'll plan for a write-amplification spike around that. Messages average 1KB, so ~58MB/sec write throughput to storage, ~50TB/year. I'll target WebSockets (persistent bidirectional TCP connections) for real-time delivery and a hybrid push/pull model for group fan-out.

Core Components

Interviewer"How do you manage hundreds of millions of concurrent WebSocket connections across your servers?"
Connection Service (WebSocket Gateway)
  • WHY: HTTP is request-response — without persistent connections, clients must poll, which either melts servers or introduces unacceptable latency.
  • HOW: I run a fleet of stateless connection servers that each maintain ~100K WebSocket connections. Each server registers a mapping of user_id → server_id in Redis (an in-memory key-value store) so any other service can look up which server holds a user's live connection. When a message needs to be delivered, the routing layer reads that mapping and pushes directly to the right server.
  • TRADEOFF: Redis becomes a dependency — if it's unavailable, new connections can't register and in-flight deliveries fail to route.
Interviewer"How do you store messages and guarantee ordering, especially across distributed servers?"
Message Service & Storage
  • WHY: Without a total ordering guarantee, clients see messages out of sequence — in group chats this is a product-breaking bug.
  • HOW: Each message gets a globally unique, time-ordered ID using a Snowflake ID (a 64-bit ID encoding timestamp + machine ID + sequence, pioneered by Twitter). Within a conversation, messages are partitioned by conversation_id in Cassandra (a distributed wide-column store built for high write throughput), and the Snowflake ID serves as the clustering key so rows are stored in time order natively.
  • TRADEOFF: Cassandra provides eventual consistency (replicas converge asynchronously, not instantly) — in rare cases two clients may briefly see different message orderings before convergence.
Interviewer"A message sent to a 500-member group needs to reach every member — how do you handle that without blowing up write latency?"
Fan-Out Service (Group Message Delivery)
  • WHY: Synchronously writing 500 delivery records and pushing 500 WebSocket notifications in the request path would make send latency proportional to group size — unacceptable.
  • HOW: The send() API writes the message once to Cassandra, then publishes a single event to a Kafka topic (a durable, partitioned message queue) keyed by conversation_id. A pool of fan-out workers consumes that event and asynchronously handles per-member delivery — writing unread counts to Redis and pushing to the relevant WebSocket gateways. Online users get pushed; offline users get pulled when they reconnect.
  • TRADEOFF: Delivery becomes asynchronous, so there's a small window where the sender's message shows as sent before all recipients have received it — we handle this with a client-side optimistic update.
Interviewer"How do you track which users are online without hammering your database on every heartbeat?"
Presence & Last Seen
  • WHY: If presence state is stored in a DB, 500M users sending a heartbeat every 5 seconds generates 100M writes/sec — that will collapse any relational database.
  • HOW: I store presence in Redis with a TTL (time-to-live — automatic expiry after a set duration) of 30 seconds. Each client sends a heartbeat every 10 seconds; the gateway does a Redis SET with TTL refresh. No TTL refresh means the key expires and the user is marked offline automatically — no explicit logout needed.
  • TRADEOFF: Presence is eventually consistent — there's a up-to-30s window where a user appears online after they've actually disconnected.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single hot group chat (e.g. a celebrity broadcast room) sends thousands of messages/sec, overwhelming a single Kafka partition and fan-out worker pool.
Fix: I shard (split across multiple partitions) Kafka not just by conversation_id but by a composite key of conversation_id + message_id bucket. For celebrity/broadcast use cases I introduce a tiered fan-out: the first tier delivers to 'super-nodes' (regional aggregators), and each super-node delivers to its local shard of subscribers — reducing the per-worker fan-out from 500K to ~1K.
Tradeoff: Tiered fan-out adds a delivery hop, slightly increasing p99 latency for large broadcast groups.
2WebSocket servers are stateful — if a server crashes, all its connections drop and re-establish, causing a thundering herd (mass simultaneous reconnection) that cascades across the fleet.
Fix: I add exponential backoff with jitter (randomized delay so reconnections spread out over time rather than all hitting at once) on the client side. On the server side, I use a consistent hash ring (a ring structure where each server owns a range of hash space, minimizing re-distribution when nodes change) so reconnecting clients route to the same server where possible, and the session registry in Redis is the source of truth — not the server itself.
Tradeoff: Consistent hashing adds complexity to the load balancer and means uneven load distribution if hash ring segments aren't well-balanced.

Reference

API
POST/api/v1/messages— Send a message; body: {conversation_id, content, media_url?}; returns message_id, timestamp
GET/api/v1/conversations/{conv_id}/messages— Paginate message history; query params: before_id, limit; returns ordered message list
POST/api/v1/conversations— Create 1:1 or group conversation; body: {type, participant_ids[], name?}; returns conv_id
GET/api/v1/users/{user_id}/presence— Returns online status and last_seen timestamp from Redis
POST/api/v1/users/me/heartbeat— Refresh presence TTL; called every 10s by connected clients; returns 204
GET/api/v1/conversations/{conv_id}/members— Returns paginated member list with roles and join timestamps
Database & Storage
  • Cassandra — primary message store; optimized for high write throughput and time-series range reads by conversation
  • Schema: messages(conversation_id UUID PK, message_id BIGINT CLUSTERING KEY ASC, sender_id UUID, content TEXT, media_url TEXT, created_at TIMESTAMP)
  • Index: partition key is conversation_id (all messages in one conv collocated); clustering on message_id gives time-ordered retrieval for free
  • Tradeoff: no joins or transactions — consistency within a partition is strong, but cross-partition aggregations require application-level logic
  • MySQL — stores users, conversations, and group membership; chosen for ACID transactions and relational integrity (e.g. cascading deletes on group membership)
  • Schema: conversations(conv_id BIGINT PK, type ENUM('dm','group'), name VARCHAR, created_at TIMESTAMP); memberships(conv_id BIGINT FK, user_id BIGINT FK, joined_at TIMESTAMP, role ENUM) — composite PK on (conv_id, user_id)
  • Index: memberships(user_id) so fetching all conversations for a user is O(log n); conversations(conv_id) primary key lookup
  • Tradeoff: MySQL doesn't scale writes horizontally as easily as Cassandra — shard by user_id for the memberships table at scale
