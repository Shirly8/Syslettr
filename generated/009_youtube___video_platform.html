Systems Design · Tier 1

YouTube / Video Platform

Video platforms look like file storage until you realize a single upload triggers a multi-stage processing pipeline that must produce a dozen encoded variants before a single user can watch. Interviewers use it to test whether you understand bandwidth-heavy distributed systems, async fan-out, and CDN-aware delivery — all at once.

Interview

Interviewer
Design a video platform like YouTube. Users can upload videos, which others can then search and watch. Where do you start?
You
Before diving in — what's the scale? How many uploads per day and concurrent viewers? Are we building the full product or focusing on a core flow like upload-to-playback? And do we need live streaming, or just on-demand?
Interviewer
500K uploads per day, 5 billion views per day. Focus on upload, transcoding, and playback. On-demand only, no live streaming.
You
That's roughly 6 uploads/sec and about 58K view requests/sec. Videos average 300MB raw — so ~150TB of raw upload data daily. I'll assume we store multiple encoded variants per video, targeting 10x storage expansion, so ~1.5PB of processed video added per day and a cold storage tail measured in exabytes over years. Reads dwarf writes, so CDN (content delivery network — a globally distributed cache of static files) offloads nearly all playback bandwidth. The hard part is the async transcoding (re-encoding video into multiple resolutions/codecs) pipeline between upload and watchability.

Core Components

Interviewer"How does the upload actually get from the user's browser to your system reliably at that scale?"
Upload Service & Raw Storage
  • WHY: A 300MB upload over a slow connection will time out or corrupt if handled naively through a single HTTP endpoint — we need resumable, chunked transfers.
  • HOW: I'd use a resumable upload protocol where the client splits the file into 5–10MB chunks and uploads each with a byte-range header to an upload service. The upload service writes chunks to a staging object store (like S3) under a temp key, then stitches them into a final raw object once all chunks arrive and a checksum validates. I issue the client a session token at upload start so it can resume after network interruption without restarting.
  • TRADEOFF: Chunking adds client complexity and requires the server to track partial upload state, usually in a small metadata table.
Interviewer"Once the raw video is uploaded, how do you produce all the different quality variants efficiently?"
Transcoding Pipeline
  • WHY: A raw 4K upload can't be streamed directly — browsers need multiple bitrate/resolution variants (e.g., 360p, 720p, 1080p, 4K) so the player can adapt to the viewer's bandwidth, which is the core of ABR (adaptive bitrate streaming).
  • HOW: When the raw video lands in object storage, the upload service publishes a message to a transcoding job queue. A pool of worker nodes pulls jobs, and each worker splits the video into parallel segment transcoding tasks — one task per resolution per ~10-second segment. This parallelism cuts a 60-minute video's transcode wall time from hours to minutes. Each finished segment is written to object storage, and a manifest file (an index listing all segments and their URLs) is generated when all segments complete.
  • TRADEOFF: Parallel segmented transcoding requires re-stitching and manifest generation logic, and a failed segment must be retried without re-transcoding the whole video — so you need idempotent (safe to re-run) job tracking.
Interviewer"Where do you store video metadata — title, uploader, view count, status — and how do you query it at scale?"
Metadata Service
  • WHY: Video metadata is read on every page load, search result, and recommendation card — without a fast metadata layer, every player page would need a slow object store lookup.
  • HOW: I'd store structured metadata (video ID, title, uploader ID, upload timestamp, status enum, duration, thumbnail URL) in a relational DB sharded (split across multiple DB machines) by video ID. A write-through cache (updates cache and DB together on write) in front of the DB serves the hot read path — most metadata reads are for recently uploaded or trending videos, which fit comfortably in cache. View counts are eventually consistent — I'd use a counter service that batches increments and flushes to the DB every few seconds rather than a direct increment per view.
  • TRADEOFF: Batched view count updates mean the displayed count can lag real views by a few seconds, which is acceptable for YouTube-class products.
Interviewer"Walk me through what happens when a user hits play — how does the video actually get to them?"
Playback & CDN Delivery
  • WHY: At 58K view requests/sec, we can't serve video bytes from origin object storage — bandwidth costs and latency would be catastrophic.
  • HOW: The player fetches the HLS (HTTP Live Streaming — a protocol that breaks video into small .ts segments described by a .m3u8 manifest) manifest from a playback API, which resolves to the CDN edge node nearest the viewer. The CDN caches both the manifest and the video segments. On a cache miss, the CDN pulls from origin object storage and caches for the TTL (time-to-live — how long before a cached item expires). The player's ABR algorithm reads available bandwidth and switches between 360p, 720p, and 1080p segment playlists mid-stream seamlessly.
  • TRADEOFF: CDN caching means a re-encoded segment replacement (e.g., DMCA takedown) requires an active CDN cache purge — not just a storage delete — or viewers will still see stale content until TTL expires.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Transcoding workers become a bottleneck on viral uploads — a single 4K video submitted at peak can queue behind thousands of jobs, delaying playability by hours.
Fix: I'd introduce priority lanes in the job queue: newly uploaded videos get a fast-lane queue that's processed by a dedicated autoscaling (automatically adding/removing worker instances based on queue depth) worker pool. Background re-encoding jobs (e.g., adding a new codec variant to old videos) use a separate low-priority queue that only consumes spare capacity. I'd scale workers based on queue depth metrics, targeting sub-5-minute transcode time for the fast lane.
Tradeoff: Priority lanes require tuning — if the fast lane is sized too generously, you overprovision compute; too small and you still miss SLA on upload spikes.
2Metadata DB hot-spots form for viral videos — every page load reads the same video row, overwhelming a single DB shard.
Fix: I'd put a read-through cache (cache is populated on first miss, subsequent reads served from memory) in front of the metadata DB. Hot video metadata is tiny (< 1KB) so a modest cache cluster can hold tens of millions of entries. I'd set a short TTL on mutable fields like view count and a long TTL on immutable fields like title and duration.
Tradeoff: Stale reads on mutable metadata (view count, description edits) are possible within the TTL window — acceptable for YouTube-class freshness requirements.
3CDN cache miss rate spikes for long-tail (rarely watched) videos, forcing frequent origin pulls that burn bandwidth and add latency.
Fix: I'd configure a tiered CDN (regional CDN nodes pull from a smaller set of continental origin shields rather than directly from object storage) so a cache miss hits a regional shield before going all the way to object storage. This reduces origin load by ~80% for long-tail content while keeping latency acceptable. I'd also set long TTLs on immutable video segments — once transcoded, a segment never changes.
Tradeoff: An extra hop through the shield adds ~20–40ms of latency on a cold miss compared to a direct origin pull.

Reference

API
POST/api/v1/uploads— Initiates a resumable upload session; returns session_id and per-chunk upload URLs
PUT/api/v1/uploads/{session_id}/chunks/{chunk_index}— Uploads a single chunk; returns 200 on success or 409 if already received
POST/api/v1/uploads/{session_id}/complete— Signals all chunks sent; triggers checksum validation and enqueues transcode job
GET/api/v1/videos/{video_id}— Returns video metadata and transcoding status (pending/processing/ready)
GET/api/v1/videos/{video_id}/manifest.m3u8— Returns HLS master manifest listing available quality-level playlist URLs
DELETE/api/v1/videos/{video_id}— Soft-deletes metadata and enqueues CDN purge + storage cleanup job
GET/api/v1/search?q={query}&page={n}— Full-text search over video title/description; returns paginated metadata list
Database & Storage
  • Relational DB (sharded by video_id) — structured metadata with transactional status updates during upload/transcode lifecycle
  • Schema: videos(video_id UUID PK, uploader_id UUID, title VARCHAR(200), description TEXT, status ENUM, duration_s INT, thumbnail_url TEXT, created_at TIMESTAMP)
  • Schema: upload_sessions(session_id UUID PK, video_id UUID, total_chunks INT, received_chunks JSONB, checksum VARCHAR, expires_at TIMESTAMP)
  • Index: videos(uploader_id, created_at DESC) for channel page queries; videos(status, created_at) for transcode queue drain monitoring
  • Object storage (separate) for raw uploads and transcoded segments — relational DB holds only URLs pointing to those objects, not binary data
  • Tradeoff: sharding by video_id gives even distribution but makes uploader-based range queries (fetch all videos by user) cross-shard — mitigated by a secondary index table keyed by uploader_id
