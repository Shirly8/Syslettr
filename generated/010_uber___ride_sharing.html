Systems Design · Tier 1

Uber / Ride Sharing

Ride sharing is deceptively hard because it requires sub-second geospatial matching across millions of moving entities while maintaining consistency between driver supply and rider demand. Interviewers use it to probe location indexing, real-time messaging, and how you handle state that changes every few seconds at global scale.

Interview

Interviewer
Design the core Uber ride-sharing backend — a rider requests a trip, a driver gets matched and accepts, and the ride completes. Where do you start?
You
Before diving in — what's the geographic scale? One city, global? And are we building the full lifecycle or focusing on matching and dispatch? Also, what's the SLA on match time — is sub-10 seconds acceptable?
Interviewer
Global scale, 5 million active drivers and 3 million concurrent ride requests at peak. Full lifecycle — request, match, track, complete. Match must happen in under 5 seconds.
You
So drivers ping location every 4 seconds — that's roughly 1.25 million location writes/sec globally. Rider requests come in bursts; assume 50K requests/sec at peak. The hardest part is geospatial indexing (efficiently querying which drivers are near a given point) on a data set that's changing every few seconds. I'll shard (split data across machines) by geographic region using a geohash grid (encoding lat/lng into a hierarchical string prefix), keep driver locations in memory, and use a dedicated matching service to avoid coupling the location pipeline to the ride state machine.

Core Components

Interviewer"Drivers are pinging every 4 seconds — how do you ingest 1.25 million writes per second without falling over?"
Location Ingestion Service
  • WHY: If location writes hit the DB directly, write amplification kills throughput and reads for matching stall waiting on stale data.
  • HOW: Drivers connect via persistent WebSocket (long-lived bidirectional TCP connection) to a fleet of stateless ingestion nodes behind a load balancer. Each node fans writes into a partitioned message queue (a durable log of events, ordered by key) by geohash prefix. A location consumer service reads the queue, updates an in-memory geospatial store (Redis with geospatial sorted sets — latitude/longitude stored as a scored value), and writes a coarser snapshot to a time-series DB for audit. The in-memory store is the source of truth for matching; the DB is for analytics only.
  • TRADEOFF: In-memory location data is lost on a Redis node failure — I accept up to 4-second staleness on failover since drivers re-ping anyway.
Interviewer"How do you actually find the best driver near a rider in under 5 seconds across 5 million moving drivers?"
Geospatial Matching Engine
  • WHY: A naive DB query for 'drivers within 2km' at 50K requests/sec with a changing dataset would lock up any relational store.
  • HOW: I query the Redis geospatial index with GEORADIUS (a Redis command that returns members within a radius from a lat/lng) against the driver's pickup geohash cell and its neighbors — this gives candidates in O(log N). The matching service then scores candidates by ETA (estimated arrival time) using a lightweight road-network estimate (straight-line distance adjusted by a city density factor), driver rating, and current surge zone. Top candidate gets an offer pushed via WebSocket with a 10-second accept window. If declined or timeout, the service moves to the next candidate without re-querying — it holds a ranked list.
  • TRADEOFF: Holding a pre-ranked candidate list means a driver's position could shift in the 10 seconds between ranking and offer delivery — I accept this small staleness to avoid round-trip latency.
Interviewer"What manages the lifecycle of a ride — requested, matched, en route, completed — and how do you keep that consistent?"
Ride State Machine
  • WHY: Without explicit state ownership, race conditions occur — two drivers can accept the same ride, or a ride transitions to 'completed' before payment processes.
  • HOW: A dedicated Ride Service owns the state machine with transitions: REQUESTED → MATCHED → PICKUP → IN_PROGRESS → COMPLETED. Each transition is a conditional update (compare-and-swap — update only if current state equals expected) against a relational DB row, preventing double-accepts. The row holds ride_id, rider_id, driver_id, status, and timestamps. On COMPLETED, the service publishes an event to a queue; downstream services (billing, rating) consume independently.
  • TRADEOFF: Synchronous DB writes on every state transition add ~5ms latency per hop — acceptable given correctness requirements.
Interviewer"How does the rider see the driver moving on the map during the trip without polling every second?"
Real-Time Trip Tracking
  • WHY: Polling at 1-second intervals from millions of riders simultaneously would create massive unnecessary load — most polls return no change.
  • HOW: The rider's app holds a WebSocket connection to a trip-tracking service. When the driver's location update arrives through the ingestion queue, the consumer checks if the driver has an active ride and, if so, pushes the new coordinates directly to the rider's open socket. The tracking service is stateful (it maps driver_id → rider WebSocket session) but horizontally scalable — consistent hashing (routing the same driver_id always to the same node) ensures each driver's updates go to the right node without cross-node lookup.
  • TRADEOFF: Consistent hashing means node failure causes brief reconnects for all sessions on that node — I mitigate with fast rebalancing and client-side reconnect logic.
Interviewer"How do you compute and apply surge pricing in real time without it becoming a bottleneck?"
Surge Pricing Service
  • WHY: If surge multipliers are computed per-request by querying raw supply/demand data, latency spikes and the pricing calculation becomes the critical path for every ride request.
  • HOW: A background Surge Service aggregates supply (available drivers) and demand (open requests) per geohash cell every 30 seconds, computes a surge multiplier using a simple supply-demand ratio formula, and writes the result to a Redis hash keyed by geohash. The Matching Service reads surge from Redis on every ride request — this is a single O(1) cache read, not a compute operation. Multipliers expire after 60 seconds, forcing a fresh compute cycle.
  • TRADEOFF: 30-second aggregation windows mean surge lags actual demand spikes by up to 30 seconds — acceptable for pricing but not for real-time inventory.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Location queue consumers can't keep up during a sudden demand surge — the queue depth grows and matching reads stale 30-second-old driver positions.
Fix: I partition the location queue by geohash prefix at finer granularity — instead of 12 partitions I scale to 128, aligned to city-level geohash cells. Consumers are stateless and auto-scaled horizontally; each consumer owns a partition range and writes only to its Redis geo-shard. This eliminates cross-consumer contention. I also add a lag monitor: if consumer lag (difference between latest message offset and consumer's current offset) exceeds 5 seconds, it pages on-call and auto-scales consumer count.
Tradeoff: Finer partitioning increases coordination overhead for matching queries that span partition boundaries — I accept one extra Redis GEORADIUS call per boundary cell.
2The Ride DB becomes a write hotspot on the rides table when thousands of rides complete simultaneously in the same city, all updating the same index.
Fix: I shard (partition data horizontally across DB machines) the rides table by hashed city_id + timestamp bucket, so completions in the same city during the same minute land on the same shard but different shards handle different cities. For high-cardinality cities like NYC, I add a sub-shard suffix derived from ride_id mod 8. The completed-ride event also goes to the event queue immediately so billing doesn't block on the DB write path.
Tradeoff: Cross-shard queries for analytics (e.g. total rides per driver globally) require scatter-gather (fan out to all shards and merge) — I push those to a read replica or data warehouse.
3The matching service builds a ranked candidate list synchronously, so if 50K ride requests arrive simultaneously, matching latency blows through the 5-second SLA.
Fix: I add a match request queue between the API gateway and the matching service, sized per geohash region. Each matching service instance consumes from one regional partition and maintains a local hot cache of available drivers for that region pulled from Redis. This decouples ingest rate from processing rate — requests queue briefly rather than all hitting the matcher concurrently. I set a TTL (time-to-live — max age before discarding) of 8 seconds on queued match requests so stale requests drop before they breach SLA.
Tradeoff: Queuing adds up to a few hundred milliseconds of p99 latency (99th percentile — the slow tail) under normal load, which is the cost of backpressure protection.

Reference

API
POST/api/v1/rides— Rider submits ride request with pickup lat/lng, dropoff lat/lng, ride_type; returns ride_id and status=REQUESTED
GET/api/v1/rides/{ride_id}— Returns current ride state, driver info, and ETA — polled by client or pushed via WebSocket
POST/api/v1/rides/{ride_id}/accept— Driver accepts offer; conditional update sets status=MATCHED, returns rider pickup details
POST/api/v1/rides/{ride_id}/complete— Driver marks ride complete; triggers billing and rating events, returns fare breakdown
POST/api/v1/drivers/location— Driver pings current lat/lng and availability; returns surge multiplier for their cell
GET/api/v1/drivers/{driver_id}/status— Returns driver availability, current ride assignment, and last-known location
Database & Storage
  • PostgreSQL (relational, ACID-compliant) for ride and driver state — correctness on state transitions requires row-level locking
  • Schema rides(ride_id UUID PK, rider_id UUID, driver_id UUID, status VARCHAR, pickup_geohash CHAR(7), fare_cents INT, created_at TIMESTAMPTZ, updated_at TIMESTAMPTZ)
  • Schema drivers(driver_id UUID PK, status VARCHAR, current_geohash CHAR(7), rating NUMERIC, vehicle_type VARCHAR, updated_at TIMESTAMPTZ)
  • Index: rides(rider_id, created_at DESC) for rider history; rides(driver_id, status) for active-ride lookup; drivers(current_geohash, status) for fallback geo query
  • Shard rides by hash(city_id || date_bucket) — avoids hotspots on city-level timestamp ranges; driver table replicated per region since it's small (~5M rows)
  • Redis for all location and surge data — eviction policy is volatile-ttl (expire keys by TTL) so stale driver entries self-clean after 30 seconds of no pings
  • Tradeoff: Keeping rides in relational DB and locations in Redis means no single transaction spans both — compensating logic in the matching service handles partial failures
