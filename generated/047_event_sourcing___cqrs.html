Systems Design · Tier 2

Event Sourcing & CQRS

The hard part isn't storing events — it's keeping the read model consistent with the event log without losing data or serving stale state under failure. Interviewers ask this to test whether candidates understand eventual consistency tradeoffs and can reason about systems where the past is immutable but the present is derived.

Interview

Interviewer
We're building a financial transaction ledger for a payment platform — think account balances, transfers, refunds. Walk me through how you'd design this, and where do you start?
You
Before I commit to an architecture — what's the write volume? Are we talking thousands of transactions per second or tens of thousands? And is the primary read pattern account balance lookups, or do we also need historical audit trails and reporting? Also, do we need strict consistency on reads, or is eventual consistency acceptable on the query side?
Interviewer
Roughly 10,000 transactions per second at peak, 500 million accounts total. Reads are mostly balance lookups — sub-100ms SLA — but we need a full immutable audit trail. Eventual consistency on reads is fine as long as lag stays under 2 seconds.
You
Got it. So 10K writes/sec sustained, which means about 864 million events per day — I'll plan for ~50TB of event storage in year one. CQRS (Command Query Responsibility Segregation — splitting write and read paths into separate services and data stores) gives us the right separation here. The write side uses Event Sourcing (storing every state change as an immutable append-only event, never updating in place) so the ledger is inherently auditable. The read side materializes current balances into a fast query store. Under 2-second lag is achievable with an async projection pipeline. I'll design around that split.

Core Components

Interviewer"How do you prevent duplicate transactions — say a client retries a transfer because they got a timeout?"
Command Service (Write Side)
  • WHY: Without idempotency on the write side, a retry storm causes double-charges — the worst possible failure mode in a payments system.
  • HOW: Every command carries a client-generated idempotency key (a unique token the client creates per logical operation). Before appending the event, I check a short-lived idempotency store — a fast key-value store with a 24-hour TTL — keyed on that token. If it already exists, I return the original result without writing a new event. If not, I append the event atomically and record the key. The event append itself uses optimistic concurrency control (OCC — reject the write if the stream's expected version doesn't match) to prevent concurrent commands corrupting the same account stream.
  • TRADEOFF: OCC causes retries under high contention on hot accounts — a celebrity account with thousands of concurrent transfers will see elevated write latency.
Interviewer"What database backs the event store, and how do you model the data?"
Event Store
  • WHY: The event store is the system of record — if events are lost or reordered, every derived view is permanently corrupted and there's no way to recover.
  • HOW: I'd use an append-only table partitioned by account_id. Each row is an event with a stream-scoped sequence number (a monotonically increasing integer per account). The sequence number enforces ordering and enables OCC — I reject appends where the incoming expected_version doesn't match MAX(sequence) for that account. For global ordering across accounts (needed for the projection pipeline), I include a global_offset backed by a database sequence or a Kafka partition offset. Events are stored as structured JSON blobs with a type field so the projection can deserialize them correctly.
  • TRADEOFF: Partitioning by account_id means cross-account queries — like 'all events in the last hour' — are expensive full scans; I'd push those to the read side.
Interviewer"How does the read model stay in sync with the event store, and what happens if the projection consumer crashes mid-way?"
Projection Engine (Read Model Builder)
  • WHY: Without a reliable projection pipeline, the read model drifts from reality — balances go stale or become inconsistent, breaking every downstream query.
  • HOW: I tail the event store's change feed (a stream of new writes in commit order — most event stores expose this natively) and publish events to a durable queue. Projection workers consume from that queue, apply the event to the read model (e.g. increment balance by transfer amount), and commit their queue offset only after the read model write succeeds. This gives at-least-once delivery — if a worker crashes before committing the offset, it replays from the last committed position. I make each projection handler idempotent by checking the last applied sequence number per account before writing.
  • TRADEOFF: At-least-once delivery means I need idempotent projections everywhere — any handler that isn't idempotent will double-count on replay.
Interviewer"How do you serve balance reads under 100ms if the read model is a database?"
Query Service (Read Side)
  • WHY: Without a caching layer, every balance lookup hits the database — at 500 million accounts and high read QPS, that saturates the DB and blows the 100ms SLA.
  • HOW: I put a read-through cache (a cache that fetches from DB on miss and populates itself automatically) in front of the read model DB, keyed on account_id. Hot accounts — high-frequency traders, payroll accounts — stay warm. TTL is set to 2 seconds to match the acceptable staleness budget, so the cache never serves data older than the SLA allows. For cache invalidation, the projection worker writes through the cache on every update, keeping it warm rather than relying on expiry alone.
  • TRADEOFF: Write-through cache (updating cache on every projection write) increases projection write latency slightly — I'm doing two writes per event instead of one.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Replaying millions of events to rebuild account state from scratch makes cold reads and projection restarts prohibitively slow — a 5-year-old account might have 50,000 events.
Fix: I introduce periodic snapshots (a saved copy of the materialized state at a known event sequence number). Every N events — say every 500 — I write a snapshot of the account balance alongside the sequence number it represents. On replay, I load the most recent snapshot and apply only the delta events on top. For the projection engine restart case, I can also store the last committed read model state as a snapshot so the worker resumes from a recent offset rather than event zero.
Tradeoff: Snapshots add write amplification (extra writes per N events) and require a snapshot eviction policy — storing unlimited snapshots costs storage proportional to the number of accounts times snapshot frequency.
2Hot accounts — high-volume merchants or payroll accounts — become a contention bottleneck because all writes serialize on the same account stream under OCC.
Fix: I use a virtual account pattern: split a hot account into N sub-accounts (shards), each holding a fraction of the balance. Writes are distributed across shards using a hash of the transaction ID. The true balance is the sum of all shard balances, computed by the query service at read time by aggregating shard snapshots. This turns a serialized single-stream write into N parallel streams. For accounts below a contention threshold, I keep them on a single stream — the fan-out is only applied dynamically when OCC retry rates breach an alert threshold.
Tradeoff: Balance reads for hot accounts become a scatter-gather (fan-out read across N shards), adding latency and complexity to the query service.
3Event store grows unboundedly — at 10K events/sec, raw event storage hits ~50TB in year one and querying old events becomes expensive.
Fix: I implement tiered storage: recent events (last 90 days) stay in the primary high-performance DB. Older events are compacted (merged into summary records where individual event granularity isn't needed) and archived to a cold object store. The event store layer handles routing transparently — queries for recent events hit the hot tier, historical audit queries hit the cold tier. I never delete raw events from the cold store; compacted summaries are additive, not destructive.
Tradeoff: Cold-tier audit queries are significantly slower — seconds not milliseconds — which is usually acceptable for compliance reads but needs to be explicitly communicated to audit tooling consumers.

API
POST/api/v1/accounts/{account_id}/commands/transfer— Submits a transfer command with idempotency-key header; returns 202 Accepted with event_id on success, 409 on duplicate key
POST/api/v1/accounts/{account_id}/commands/deposit— Submits a deposit command; same idempotency contract as transfer; returns 202 with event_id
GET/api/v1/accounts/{account_id}/balance— Returns current balance from read model cache; includes as_of_sequence to indicate staleness
GET/api/v1/accounts/{account_id}/events— Returns paginated event log for audit; supports from_sequence and to_sequence query params for range queries
GET/api/v1/accounts/{account_id}/events/{sequence}— Returns a single event by sequence number; used for point-in-time state reconstruction
Database & Storage
  • Event Store — append-only relational DB with native sequence support; guarantees ordering and OCC via per-stream version checks
  • Schema: events(id UUID PK, account_id UUID, sequence BIGINT, global_offset BIGINT, event_type VARCHAR, payload JSONB, occurred_at TIMESTAMPTZ)
  • Unique index on (account_id, sequence) enforces per-stream ordering and OCC; global_offset index supports projection tailing
  • Read Model DB — wide-column store for balance lookups; keyed on account_id for O(1) point reads without full table scans
  • Schema: balances(account_id UUID PK, balance_cents BIGINT, currency CHAR(3), last_applied_sequence BIGINT, updated_at TIMESTAMPTZ)
  • last_applied_sequence enables idempotent projection writes — skip the update if incoming sequence is already applied
  • Tradeoff: JSONB event payloads are flexible but slower to query than typed columns — acceptable since events are written once and queried by sequence, not by payload content
