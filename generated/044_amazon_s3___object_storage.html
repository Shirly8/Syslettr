Amazon S3 / Object Storage

Object storage hides enormous complexity behind a deceptively simple PUT/GET interface — durability at 11 nines requires erasure coding, consistent hashing, and careful failure isolation across racks and AZs. Interviewers use it to probe whether you can reason about distributed consistency, large-scale data placement, and the gap between file systems and object stores.

Interview

Interviewer
Design an object storage system like Amazon S3. Users should be able to upload arbitrary blobs and retrieve them reliably. Where do you start?
You
Before diving in — what's our target scale? Are we talking petabytes with millions of objects or exabytes with trillions? And what's the durability SLA — S3-level 11 nines, or something looser? Also, are we supporting versioning and multi-part uploads out of the gate, or just basic PUT/GET first?
Interviewer
Assume 1 billion objects, averaging 1MB each — so roughly 1PB total. Target 11 nines durability and 99.9% availability. Support multi-part uploads and basic versioning. Latency SLA is p99 under 200ms for reads.
You
So ~1PB stored, and if objects average 1MB, metadata for 1B objects is roughly 200GB assuming ~200 bytes per record — that fits in a distributed key-value store but not a single Postgres. For write throughput, if 1% of objects are written daily that's ~116 writes/sec, but bursty peaks probably 10x that so I'll design for ~1,200 writes/sec. Reads are typically 10:1, so ~12,000 reads/sec. Durability at 11 nines means I need erasure coding (breaking data into chunks with redundant parity shards so any k-of-n shards can reconstruct the object) across at least 3 availability zones. I'll separate the data path from the metadata path — metadata lives in a strongly consistent store, raw bytes go to distributed chunk servers.

Core Components

Interviewer"How do you store and look up metadata for a billion objects without a single-node bottleneck?"
Metadata Service
  • WHY: Without a scalable metadata layer, every GET requires scanning storage nodes to find where an object's chunks live — that doesn't scale past millions of objects.
  • HOW: I'd use a sharded (data split across multiple DB machines by key range or hash) key-value store keyed on bucket+object_key hash. Each record stores object size, checksum, creation time, version ID, and a list of chunk location references. Reads are point lookups so p99 (99th percentile — slowest 1% of requests) stays low. I'd keep a read replica per AZ to serve reads locally without cross-AZ hops.
  • TRADEOFF: Sharding by hash gives even distribution but makes range scans (e.g., list all objects in a bucket) expensive — I'd need a secondary index on bucket_id for listing operations.
Interviewer"Walk me through how you'd actually store bytes durably across nodes. What happens when a disk fails?"
Chunk Storage & Erasure Coding
  • WHY: Replicating full objects 3x costs 3x storage — erasure coding achieves the same durability at roughly 1.5x overhead, which at petabyte scale saves hundreds of terabytes.
  • HOW: I split each object into k data shards and compute m parity shards using Reed-Solomon coding (a math technique where any k-of-(k+m) shards reconstruct the original). A common config is 6+3: 6 data, 3 parity, placed across 3 AZs so we survive a full AZ loss. Chunk servers are grouped into failure domains (rack, AZ) and a placement service ensures no two shards of the same stripe land on the same rack. On disk failure, a background reconstruction job reads k surviving shards and rebuilds the missing one to a healthy node.
  • TRADEOFF: Reconstruction under failure increases read amplification (reading more shards than needed for a single object) and reconstruction is CPU-intensive — you need spare capacity headroom.
Interviewer"How do you handle large file uploads — say a 5GB video — without holding a single TCP connection open for minutes?"
Write Path & Multi-Part Upload
  • WHY: A single TCP stream for a 5GB upload over a flaky connection means a failure at byte 4.9GB restarts the entire transfer — unacceptable for users and wastes bandwidth.
  • HOW: I expose a multi-part upload API: client calls InitiateUpload to get an upload_id, then sends parts of 5–100MB each in parallel with UploadPart — each returns an ETag (a hash fingerprint of that chunk). Finally, CompleteMultipartUpload sends the ordered list of ETags; the server assembles the object, verifies checksums, writes metadata, and commits. Parts live in a temporary staging area until completion. If the session expires or client calls AbortUpload, a garbage collection job cleans up orphaned parts.
  • TRADEOFF: Staging parts before commit means you need roughly 2x transient storage during an active large upload, and GC lag can tie up that space for hours.
Interviewer"How do you decide which storage nodes get which chunks, and what happens when you add capacity?"
Consistent Hashing for Chunk Placement
  • WHY: Without a deterministic placement strategy, either you need a centralized lookup for every chunk (bottleneck) or adding nodes causes a full data reshuffle (prohibitive at petabyte scale).
  • HOW: I use consistent hashing (a ring-based scheme where each node owns a hash range — adding a node only migrates ~1/N of data). Each chunk server is placed at multiple virtual nodes (vnodes) on the ring to smooth out load. The placement service maps a chunk's ID to the ring position and picks the next k nodes that span required failure domains. When a new node joins, only its neighboring vnodes' data migrates to it.
  • TRADEOFF: Hot key skew (one object getting hammered) can still overload one ring segment — I'd mitigate this by spreading popular objects' shards across many vnodes, but it adds placement complexity.
Interviewer"Reads are 10:1 versus writes — how do you keep p99 latency under 200ms?"
Read Path & Caching
  • WHY: At 12,000 reads/sec hitting raw chunk servers across AZs, without a caching layer the p99 blows past 200ms just from network RTT plus disk seek.
  • HOW: I put a read-through cache (serves from memory, fetches from storage on miss) in front of chunk servers, keyed on object_id+version. Hot objects — profile pictures, popular static assets — stay in memory with LRU eviction (drops least-recently-used entries when cache is full). Metadata is separately cached since it's accessed on every request. For very hot objects I'd also allow a CDN (Content Delivery Network — edge servers close to users) layer for publicly accessible blobs, with cache-control headers driving TTLs.
  • TRADEOFF: Caching works great for read-heavy hot objects but doesn't help unique large files (like personal video exports) — those always hit storage.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single metadata shard becomes a hot spot when millions of objects in one bucket are listed or written rapidly, saturating that shard's CPU and I/O.
Fix: I'd split the metadata shard further using a composite shard key of bucket_id + object_key_prefix rather than just object_key hash. This spreads list operations across shards instead of funneling them to one. Additionally, I'd front the metadata layer with a dedicated metadata cache — most GET requests hit the same popular objects repeatedly, so a cache hit rate above 80% dramatically reduces shard load.
Tradeoff: Prefix-based sharding makes it harder to rebalance if one prefix (like a date-stamped prefix) becomes disproportionately hot — you'd need dynamic shard splitting logic.
2During peak write throughput (~1,200 writes/sec), the erasure coding step (CPU-bound math) on the write service nodes becomes the bottleneck — p99 write latency spikes above SLA.
Fix: I'd offload erasure coding to a dedicated encoding tier that the write service calls asynchronously via a queue (a message buffer that decouples producer speed from consumer speed). The write service accepts the upload, writes raw data to a fast temporary store, and immediately returns an upload_id to the client. The encoding tier drains the queue, computes parity shards, and moves the result to final chunk servers. Once committed, the metadata record is updated to 'durable' state.
Tradeoff: The object isn't immediately durable after the upload acknowledges — there's a brief window where only raw unencoded bytes exist, so you need to make sure clients don't treat the upload_id as a guaranteed durable reference until the metadata shows 'durable'.
3Large object downloads (e.g., 1GB files) tie up read service workers for seconds, reducing throughput for small object reads.
Fix: I'd use byte-range serving: the read service supports HTTP Range requests (client specifies a byte window) and streams shard data directly to the client without buffering the full object in worker memory. For very large public objects I'd also issue a pre-signed URL (a time-limited direct URL) that lets the client pull bytes directly from edge chunk servers, bypassing the read service entirely.
Tradeoff: Direct-to-chunk serving bypasses the application layer auth check on each range request — you have to bake auth into the pre-signed token and ensure tokens can't be reused past expiry.

Reference

API
POST/api/v1/buckets/{bucket}/objects/initiate— initiates multipart upload; returns upload_id
PUT/api/v1/buckets/{bucket}/objects/parts?upload_id={id}&part={n}— uploads one part (5-100MB); returns ETag (chunk hash)
POST/api/v1/buckets/{bucket}/objects/complete— body: ordered ETag list; commits object, returns object_key and version_id
DELETE/api/v1/buckets/{bucket}/objects/abort?upload_id={id}— aborts multipart session; triggers GC of staged parts
GET/api/v1/buckets/{bucket}/objects/{key}— fetches object bytes; supports Range header for partial reads
GET/api/v1/buckets/{bucket}/objects/{key}?version={id}— fetches specific version of an object by version_id
DELETE/api/v1/buckets/{bucket}/objects/{key}— soft-deletes object (inserts delete marker for versioned buckets)
GET/api/v1/buckets/{bucket}/objects?prefix={p}&limit={n}— lists objects by prefix; cursor-paginated for large buckets
Database & Storage
  • Primary metadata store: distributed key-value store (e.g., Cassandra-style) — scales horizontally, handles wide rows for version history naturally
  • Schema: objects(object_id UUID PK, bucket_id UUID, object_key TEXT, version_id UUID, size_bytes BIGINT, checksum TEXT, state ENUM('staging','durable','deleted'), shard_refs JSONB, created_at TIMESTAMP)
  • Schema: buckets(bucket_id UUID PK, owner_id UUID, region TEXT, versioning_enabled BOOL, created_at TIMESTAMP)
  • Schema: parts(upload_id UUID, part_number INT, etag TEXT, size_bytes BIGINT, staged_path TEXT, PRIMARY KEY(upload_id, part_number))
  • Index: (bucket_id, object_key) compound index for O(log n) key lookup; secondary (bucket_id, created_at) for sorted listing queries
  • Shard key on hash(bucket_id + object_key) for write distribution — avoids hot shards on sequential keys but requires scatter-gather for prefix listing across shards
