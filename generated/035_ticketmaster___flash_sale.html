Systems Design · Tier 2

Ticketmaster / Flash Sale

The core trap is that millions of users simultaneously try to claim a finite, non-replenishable resource — making overselling and race conditions (two requests winning the same seat) the primary failure modes. Interviewers use this to test whether you can reason about distributed locking, optimistic concurrency, and queue-based demand shaping under extreme write pressure.

Interview

Interviewer
We want to build a ticket-purchasing system like Ticketmaster, but with a flash-sale constraint — tickets go on sale at a fixed moment and sell out in seconds. Where do you start?
You
Before diving in — what's the peak concurrency we're planning for? Ten thousand users or ten million hitting 'buy' simultaneously? And are we selling general-admission inventory (just a count) or reserved seating (specific seat IDs)? Also, is there a hold/checkout window where a ticket is locked for a user before payment?
Interviewer
Assume a major artist: up to 5 million concurrent users at sale open, reserved seating with specific seat IDs, and a 10-minute hold window before payment must complete. Tickets total around 50,000 per event.
You
Got it. So we have 5M users racing for 50K seats — a 100:1 demand-to-supply ratio, meaning the vast majority of requests must be gracefully rejected. A 10-minute hold means we need a TTL-based lock (a time-to-live record that expires and releases the seat automatically). The critical numbers: at peak, even if we queue requests, the reservation write path must handle ~5M concurrent sessions. The actual inventory mutation rate is bounded by seat count — at most 50K successful reservations — but the read and queue pressure is the real challenge. I'll treat oversell prevention and thundering herd (a massive simultaneous spike that overwhelms backend services) as the two primary constraints to design around.

Core Components

Interviewer"With 5 million users hitting the system simultaneously, how do you keep the backend from collapsing the moment sale opens?"
Virtual Waiting Queue
  • WHY: Without demand shaping, all 5M requests hit reservation services in parallel, crashing the DB and producing a thundering herd that kills availability for everyone.
  • HOW: I put a virtual queue in front of checkout — when the sale opens, users are issued a queue position token and held in a waiting room UI. A queue processor drains at a controlled rate, say 2,000 users/second, admitting them to the actual seat-selection flow. The queue is backed by a fast in-memory store with persistence so positions survive restarts.
  • TRADEOFF: Adds perceived latency — legitimate users may wait minutes — but it's a far better UX than a crash or a sold-out page appearing before anyone gets a chance.
Interviewer"Once a user gets through the queue to seat selection, how do you prevent two users from claiming the same seat?"
Seat Reservation & Lock Service
  • WHY: Without an atomic lock, concurrent requests for the same seat ID will both succeed at the application layer before the DB write, causing overselling.
  • HOW: I use optimistic locking (attach a version number to each seat row; reject the write if the version changed since the read) for the common case — no contention. For the reservation hold, I write a TTL-keyed entry in Redis (a fast in-memory store) with the seat ID as the key and user ID as the value, using a SET NX (set if not exists — atomic, no race) command. If SET NX succeeds, the seat is held for 10 minutes; if it fails, the seat is already held and the user gets redirected to pick another.
  • TRADEOFF: Redis is the single source of truth for holds, so a Redis failure before the DB write completes can leave seats in limbo — I'd mitigate with a reconciliation job that checks expired holds against DB state.
Interviewer"Seat availability is read constantly as users browse — how do you serve that without hammering the database?"
Inventory Cache Layer
  • WHY: With 5M users browsing seat maps simultaneously, read traffic to the DB would be catastrophically high and most reads return the same availability snapshot.
  • HOW: I cache the seat availability map per event in Redis with a short TTL (2–5 seconds) — stale by design, since exact real-time accuracy on a map view isn't required. Writes to the cache are write-through (update cache at the same time as the DB) on reservation commit, and invalidated on hold expiry. For the seat map UI specifically, I'd serve a pre-generated static snapshot via CDN (content delivery network — servers geographically close to users) that refreshes every few seconds.
  • TRADEOFF: Users may see a seat as available, attempt to select it, and then find it's held — I handle this with a clear 'seat no longer available' error and prompt to reselect.
Interviewer"Once the hold is placed and the user pays, what does the write path look like to make the reservation permanent?"
Payment & Confirmation Service
  • WHY: Payment introduces a third-party dependency that can fail or time out — if we mark a seat as sold before payment confirms, we risk giving away the seat for free; if we wait too long, the hold expires.
  • HOW: On payment success callback from the payment processor, I publish an event to a durable message queue (a persistent buffer ensuring messages aren't lost if consumers crash). A consumer service atomically updates the seat status from 'held' to 'sold' in the DB and removes the Redis TTL lock. If payment fails or times out within the 10-minute window, the Redis TTL expiry automatically frees the seat and a background job marks it available again.
  • TRADEOFF: Using a queue means the final status update is slightly async — there's a brief window where payment has succeeded but the seat isn't yet marked sold in the DB, requiring idempotency (safe to process the same event twice without double-selling) on the consumer.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1At sale open, all 5M users hit the reservation service simultaneously, creating a thundering herd that overwhelms the DB write path even with caching.
Fix: The virtual waiting queue absorbs the spike before it reaches any stateful service. I pre-assign queue positions at the edge layer (API Gateway) using an atomic counter in Redis — no DB touch at all during the initial surge. The queue processor drains at a controlled, tunable rate (e.g., 2,000 admissions/second) that the reservation service and DB can sustain. Users in the waiting room poll a lightweight status endpoint that returns their position from cache, not the DB.
Tradeoff: The queue adds perceived wait time and requires careful drain-rate tuning — too slow and users abandon, too fast and you recreate the original problem.
2The Seat DB becomes a write bottleneck when many hold confirmations and releases hit the same event's rows at once.
Fix: I shard (split data across multiple DB machines) the Seat DB by event_id — all seats for one event live on one shard, which keeps transactions local and avoids cross-shard coordination. Within a shard, I use row-level locking with short transactions (read seat, check status, write hold, commit — under 5ms) to maximize throughput. For events with extremely high demand, I can also batch-release expired holds in a background job rather than doing individual deletes on the hot path.
Tradeoff: Sharding by event_id means a viral event creates a hot shard — I'd mitigate by over-provisioning per-event capacity and, for true mega-events, splitting a single event across multiple shards by seat section.
3Static seat map images served from the origin on every page load would generate millions of identical requests at sale open.
Fix: I pre-generate the seat map as a versioned static asset and push it to CDN edge nodes globally before the sale opens. Availability updates (seats going held/sold) are applied as lightweight JSON deltas (small diff payloads — just changed seat IDs and their new status) fetched by the client every 3 seconds, not full map reloads. The delta endpoint is cached at the CDN with a 3-second TTL, meaning at most one origin request per 3 seconds per edge node regardless of user count.
Tradeoff: Users see a seat as available up to 3 seconds after it was held, leading to failed selection attempts — this is acceptable and explicitly communicated in the UI.

Reference

API
POST/api/v1/queue/join— Issues a queue position token for the given event_id; returns position and estimated wait time
GET/api/v1/queue/status/{token}— Returns current queue position and whether user is admitted; cached response, lightweight
GET/api/v1/events/{event_id}/seats— Returns seat availability snapshot (full map on first load, delta endpoint for updates)
POST/api/v1/reservations— Attempts to hold a specific seat_id for authenticated user; returns hold_id and expiry or conflict error
POST/api/v1/reservations/{hold_id}/confirm— Finalizes reservation after payment; idempotent — safe to retry on timeout
DELETE/api/v1/reservations/{hold_id}— Releases a hold early (user abandons checkout); frees seat immediately
Database & Storage
  • PostgreSQL — ACID transactions (all-or-nothing guarantees) required for seat status changes; row-level locking fits the access pattern
  • seats(seat_id UUID PK, event_id UUID, section VARCHAR, row VARCHAR, number INT, status ENUM('available','held','sold'), version INT, held_by UUID, held_until TIMESTAMP)
  • Index on (event_id, status) for availability queries; index on held_until for the reconciler's expired-hold scans
  • Sharding by event_id keeps all seats for one event co-located, avoiding distributed transactions, but creates hot-shard risk for blockbuster events
  • Redis — sub-millisecond SET NX for hold locks and queue position counters; persistence via AOF (append-only file — logs every write to disk) to survive restarts
  • Redis key schema: lock:seat:{seat_id} → user_id (TTL 600s), queue:{event_id}:counter → INT (atomic INCR), avail:{event_id} → serialized availability map (TTL 5s)
