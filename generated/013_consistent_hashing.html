Consistent Hashing

The deceptively simple question of 'which server handles this key?' becomes a catastrophic reshuffling problem the moment you add or remove a node — naive modulo hashing reassigns nearly every key. Interviewers use it to probe whether you understand distributed systems fundamentals: data locality, hotspots, and the real cost of rebalancing at scale.

Interview

Interviewer
We're building a distributed cache layer that needs to scale horizontally — nodes get added and removed frequently. Walk me through how you'd route keys to the right node.
You
Before diving in — are we talking read-heavy or write-heavy workloads? And when nodes are added or removed, what's the acceptable window for key unavailability, if any? Also, are all keys roughly the same size, or do we have large hot keys?
Interviewer
Mostly read-heavy, 95/5 ratio. We tolerate brief inconsistency during rebalancing but not full unavailability. Keys vary — some are much hotter than others.
You
Got it. So naive modulo hashing (assigning a key to node index = hash(key) % N) is out — adding one node changes N and remaps ~(N-1)/N of all keys, which causes a thundering herd (sudden flood of cache misses hitting the DB). I'll use consistent hashing (mapping both nodes and keys onto a fixed ring so only ~1/N keys move on membership changes). For the hot-key problem I'll layer on virtual nodes (vnodes — multiple ring positions per physical node) to spread load more evenly.

Core Components

Interviewer"How does the ring actually work, and how do you map a key to a specific node?"
The Hash Ring
  • WHY: Without a fixed address space, any change to node count forces a global key remap — essentially a full cache flush.
  • HOW: I hash the ring to a fixed integer space, typically 0 to 2^32-1. Each node gets hashed to a position on that ring. To look up a key, I hash it and walk clockwise until I hit the first node — that node owns the key. Adding a node only affects the keys between it and its counterclockwise neighbor.
  • TRADEOFF: The ring lookup requires a sorted data structure (like a balanced BST or sorted array) — O(log N) per lookup, which adds a small overhead over O(1) modulo hashing.
Interviewer"You mentioned hot keys — how do virtual nodes actually fix the uneven load problem?"
Virtual Nodes (Vnodes)
  • WHY: With only one ring position per physical node, uneven hashing naturally gives some nodes 2-3x the key space of others — those nodes become hotspots.
  • HOW: I assign each physical node multiple positions on the ring — typically 100-150 vnodes per node. Each vnode is hashed using a different seed (e.g. node_id + replica_index). This spreads each node's ownership across the full ring rather than one contiguous arc, so load distributes more uniformly across all nodes. When a node is added, it claims a small slice from many neighbors, not a large slice from one.
  • TRADEOFF: More vnodes means a larger routing table (the sorted structure that maps ring positions to nodes) and higher memory overhead on the coordinator that does lookups.
Interviewer"How do you handle node failure — if a node goes down, are those keys just gone?"
Replication with Preference Lists
  • WHY: A single-owner ring means one node failure causes data loss or unavailability for all its keys.
  • HOW: For each key, I replicate to the next N physical nodes clockwise (skipping duplicate vnodes of the same physical machine). This is called the preference list — the ordered set of nodes responsible for a key. Typically N=3. Reads and writes can use quorum (requiring acknowledgment from a majority of replicas — e.g. 2 of 3) to balance consistency and availability.
  • TRADEOFF: Replication amplifies write traffic by N and complicates coordination — you need a strategy for handling replica divergence (e.g. vector clocks or last-write-wins).
Interviewer"Which component actually decides which node gets the request — does the client know about the ring?"
Coordinator / Routing Layer
  • WHY: Clients can't be trusted to maintain an accurate, up-to-date view of the ring topology — membership changes would require updating every client.
  • HOW: A coordinator node (or a client-side library embedded in the app server) holds the ring state. It intercepts every read/write, hashes the key, does a binary search on the sorted vnode table (O(log V) where V = total vnodes), and forwards the request to the correct node. Membership changes propagate via gossip protocol (nodes periodically exchange state with random peers) — the coordinator refreshes its ring view when it receives an update.
  • TRADEOFF: Adding a coordinator hop adds latency (~1ms) and makes the coordinator a potential bottleneck unless it's stateless and horizontally scalable.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single extremely popular key maps to one vnode, so one cache node absorbs disproportionate traffic regardless of how many vnodes exist.
Fix: I detect hot keys by tracking request frequency at the coordinator using a count-min sketch (a probabilistic structure that estimates item frequency with low memory). When a key exceeds a threshold, I replicate it to K additional random nodes beyond the preference list and route reads to any of those K+N nodes using random selection. This spreads the hot key's read load across many nodes without requiring a ring topology change.
Tradeoff: Writes to hot keys now fan out to more nodes, increasing write latency and the risk of stale reads if replicas diverge briefly.
2When a new node joins, it must receive data migrated from its successor — this migration causes a temporary spike in network and disk I/O on both nodes.
Fix: I use a lazy migration strategy: the new node starts serving requests immediately but fetches key-value pairs on demand as cache misses occur, using the old owner as a fallback. I also cap the background migration rate (bandwidth throttling) so the transferring node isn't saturated. In practice this means brief staleness on migrating keys but never a complete unavailability window.
Tradeoff: During migration, some reads are slower because they require a cross-node fetch from the old owner before the new node has warmed up.
3With few physical nodes, even 150 vnodes per node can produce arcs of unequal length, causing some nodes to own 20-30% more key space than others.
Fix: I use consistent hashing with bounded loads (a variant that caps how many keys any single node can hold relative to the average). Concretely, the coordinator tracks current load per node and, when a node is over its cap (e.g. 1.25x average), it routes the incoming key to the next eligible node clockwise that's under its cap. This is a soft redirect — it doesn't change ring ownership permanently.
Tradeoff: Routing logic becomes stateful — the coordinator must track real-time load per node, adding coordination overhead and a stale-load-data risk.

Reference

API
GET/api/v1/cache/{key}— Returns value for key; coordinator resolves node, falls back to DB on miss
PUT/api/v1/cache/{key}— Writes value to primary + N-1 replicas; returns 200 on quorum ack
DELETE/api/v1/cache/{key}— Invalidates key across all replicas in preference list
GET/api/v1/ring/topology— Returns current vnode-to-node mapping; used by coordinators to sync ring state
POST/api/v1/ring/nodes— Registers a new node joining the ring; triggers vnode assignment and migration
Database & Storage
  • In-memory store (e.g. any key-value engine with O(1) get/set) per cache node — the ring determines which node holds which keys, so each node only stores its slice
  • Schema: cache_entry(key VARCHAR(512) PK, value BLOB, ttl_expires_at TIMESTAMP, version INT)
  • No secondary indexes needed — all lookups are by primary key; TTL enforced by a background sweeper thread per node
  • Storing version (logical counter) per entry enables last-write-wins conflict resolution when replicas diverge during a partition
