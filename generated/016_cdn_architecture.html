CDN Architecture

A CDN looks like 'just caching at the edge' until you realize cache invalidation across hundreds of global nodes, origin shield design, and tail latency (the slow requests at the 99th percentile) are all deeply interconnected. Interviewers use it to probe whether you can reason about distributed consistency, geographic routing, and failure modes at planetary scale.

Interview

Interviewer
We want to build a CDN to serve static and semi-static content globally. Where do you start?
You
Before diving in — what's the content mix? Mostly large media files, small JS/CSS assets, or API responses? What's our target p99 latency (99th percentile — the worst-case slow tail, not the average) and what geographic footprint do we need to cover? And do we own the edge infrastructure or are we designing the software layer on top of bare metal we control?
Interviewer
Primarily static assets — images, video segments, JS/CSS. 50ms p99 latency globally, 100 points of presence (PoPs — edge data centers close to users) across six continents. We own the hardware. Expect 10 million requests per second at peak, 60% cache hit rate target.
You
So at 10M RPS with 60% edge hit rate, 4M RPS miss-traffic needs to be absorbed somewhere before hitting origin. I'll design a two-tier cache hierarchy: L1 edge PoPs absorb local traffic, L2 regional shields (mid-tier aggregation nodes) absorb cross-PoP misses, and origin only sees the remaining cold-miss traffic — roughly 400K–800K RPS. Anycast routing (advertising the same IP from multiple PoPs so BGP routes users to the nearest one) handles geographic steering. I'll assume content is immutable-versioned by default — URL changes on update — so invalidation is rare and purge-by-tag covers the exception.

Core Components

Interviewer"How do users end up at the right PoP? Walk me through the routing path."
Anycast + DNS Steering
  • WHY: Without geographic steering, all users hit the same servers regardless of proximity, blowing the 50ms p99 budget for users on the wrong continent.
  • HOW: I advertise the same /24 IP block from every PoP via BGP (Border Gateway Protocol — the internet's routing protocol that lets us announce reachability). The internet's routers naturally route each user to the topologically closest PoP. For fine-grained control, DNS-based steering supplements this: our authoritative DNS server returns PoP-specific IPs based on the resolver's geolocation, letting us steer by latency measurements or load rather than pure BGP topology.
  • TRADEOFF: Anycast gives fast failover but BGP convergence (the time for routing tables to stabilize after a change) can take 30–90 seconds, so briefly some users hit a degraded PoP during failover.
Interviewer"Walk me through exactly what happens on a cache miss at an edge PoP."
Two-Tier Cache Hierarchy
  • WHY: Without a mid-tier shield, every edge PoP independently misses to origin — 100 PoPs each requesting the same cold asset at nearly the same time creates a thundering herd (hundreds of simultaneous duplicate requests) that overwhelms origin.
  • HOW: Each L1 edge PoP holds a local in-memory + NVMe (fast solid-state storage) cache. On a miss, instead of going directly to origin, the PoP routes to the L2 regional shield — one of ~8 regional aggregation clusters. The shield uses request coalescing (collapsing duplicate in-flight requests for the same key into one upstream request) so origin only gets one request regardless of how many PoPs miss simultaneously. The shield's cache is larger and slower than L1 but still dramatically faster than origin round-trip.
  • TRADEOFF: Adding a tier increases complexity and adds ~5–15ms of latency on a shield hit versus a direct origin fetch, but that's acceptable since shield hits avoid the 100–300ms origin RTT (round-trip time).
Interviewer"How do you invalidate content across 100 PoPs without a thundering herd or stale data window?"
Cache Invalidation & Purge
  • WHY: Serving stale content after a deployment or security patch is a hard SLA violation — users get outdated JS or, worse, cached sensitive responses.
  • HOW: The primary strategy is URL versioning — content URLs include a hash of the content (e.g. /app.a3f9b2.js), so new deployments naturally get new cache keys and old content ages out via TTL (time-to-live — max seconds a cached object is considered fresh). For imperative purges, I fan out a purge RPC (remote procedure call — a request from one service to another over the network) from a central Purge Coordinator to all PoPs concurrently; each PoP marks the object stale. I use cache tags (metadata grouping multiple URLs under a logical label) so a single tag-based purge can invalidate thousands of URLs atomically without enumerating each one.
  • TRADEOFF: Tag-based purge requires maintaining an inverted index (tag → list of cached URLs) at each PoP, which adds memory overhead proportional to tag cardinality.
Interviewer"Where does TLS terminate, and how does that interact with your caching?"
TLS Termination & HTTP/2 Push at Edge
  • WHY: Terminating TLS (Transport Layer Security — the encryption layer in HTTPS) at origin means every byte travels encrypted over the public internet to origin, destroying the latency benefit of edge caching.
  • HOW: TLS terminates at the L1 PoP. Each PoP holds a wildcard or multi-SAN (Subject Alternative Name — a cert field listing multiple valid hostnames) certificate, rotated centrally via a certificate management service that pushes new certs to all PoPs before expiry. After termination, traffic between PoPs and origin travels over our private backbone (a dedicated inter-datacenter fiber network) so re-encryption overhead is controllable and the backbone is trusted.
  • TRADEOFF: Terminating TLS at the edge means the edge infrastructure must be treated as fully trusted — a PoP compromise exposes plaintext content.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A viral content event (e.g. a major product launch video) causes 100 PoPs to simultaneously miss and all fan out to origin — the thundering herd crushes origin even with L2 shields if the content isn't in the shield yet.
Fix: I add request coalescing at the L2 shield so only one upstream request leaves per unique cache key while it's in-flight, holding other requesters in a wait queue. I also add a circuit breaker (a mechanism that stops sending requests to a failing backend and returns errors temporarily) at the shield to prevent cascade when origin degrades. For predictable viral events, I implement content pre-warming: pushing content to shields and PoPs via a fan-out job before the event goes live.
Tradeoff: Pre-warming requires content to be ready before the event and adds operational complexity — you need a reliable push pipeline and tracking of warm state per PoP.
2Long-tail content — assets requested once every few days — has near-zero cache hit rates at small PoPs, forcing nearly all requests to miss through to origin and wasting expensive SSD capacity on cold objects.
Fix: I implement a two-phase admission policy: objects only get written to the L1 NVMe cache on their second or third request (using a small Bloom filter — a probabilistic data structure that tests whether a key has been seen before — per PoP). First-time requests fetch directly from the shield without polluting L1 cache. Combined with LRU eviction (drops least-recently-used entries when cache is full), this keeps hot working-set objects resident and long-tail objects from crowding them out.
Tradeoff: First-time requests always miss to L2, adding ~10–20ms latency for genuinely new one-off requests, and Bloom filters have a small false-positive rate requiring occasional resets.
3Certificate rotation across 100 PoPs takes too long manually, and an expired cert causes immediate HTTPS failures for all users hitting that PoP.
Fix: I build a central Certificate Manager that watches expiry dates and triggers rotation 30 days before expiry. It pushes new certs to PoPs via an authenticated internal API, and each PoP performs a hot reload (replacing the cert in memory without dropping connections) so there's zero downtime. I run a continuous prober that hits each PoP's HTTPS endpoint from a monitoring host and alerts if the cert expiry drops below 14 days.
Tradeoff: Hot reload requires the TLS library to support in-place cert swapping — not all runtimes do this cleanly, which may constrain the edge software stack.

Reference

API
POST/api/v1/purge— Accepts { urls: [], tags: [] } — invalidates matching cached objects across all PoPs, returns a purge job ID and estimated propagation time
GET/api/v1/cache-status?url={url}— Returns cache state (HIT/MISS/STALE), TTL remaining, and which PoP tiers hold the object
POST/api/v1/prewarm— Accepts { urls: [], pops: ['all'|list] } — triggers background fetch-and-store of specified content to specified PoPs before traffic arrives
GET/api/v1/analytics?pop={pop}&window=1h— Returns hit rate, bandwidth, p99 latency, and top miss URLs for the specified PoP and time window
PUT/api/v1/cache-rules/{hostname}— Updates cache behavior rules (TTL overrides, bypass conditions, Vary headers) for a given origin hostname
Database & Storage
  • Distributed key-value store (e.g. consistent-hashing ring over commodity nodes) — maps cache keys to metadata: TTL, tags, ETag, content-length; query pattern is pure point lookups at high throughput
  • Schema: cache_objects(cache_key VARCHAR(512) PK, etag CHAR(64), ttl_expires_at TIMESTAMP, size_bytes BIGINT, tags TEXT[], origin_url TEXT, last_accessed_at TIMESTAMP)
  • Primary index on cache_key (hash-partitioned); secondary index on tags array for O(1) tag-to-keys lookup using an inverted index table: tag_index(tag VARCHAR(256), cache_key VARCHAR(512))
  • Tradeoff: keeping tag_index consistent with cache_objects during concurrent purges requires compare-and-swap (atomic read-modify-write) operations, which add ~2ms per purge write but prevent stale tag mappings
