Load Balancer Design

A load balancer sounds simple — split traffic across servers — but the hard part is handling server failures in real time without dropping requests, choosing the right routing algorithm for your workload, and maintaining session affinity without creating hotspots. Interviewers ask this because it tests your understanding of distributed systems fundamentals: consensus, failure detection, and the tradeoffs between stateless and stateful routing.

Interview

Interviewer
We need to design a load balancer for a large-scale web service. Walk me through how you'd approach this.
You
Before diving in — what's the traffic scale, requests per second? Are we building a general-purpose Layer 7 load balancer (routes based on HTTP content) or Layer 4 (routes based on TCP/IP headers only)? And do we need session stickiness (routing the same user to the same backend server consistently)?
Interviewer
Target is 1 million requests per second at peak. Layer 7 HTTP load balancing. Sessions matter — users have cart state on backend servers. Availability SLA is 99.99% uptime.
You
So roughly 1M RPS (requests per second) with sticky sessions required and four-nines availability — that means less than 52 minutes of downtime per year. I'll assume backend servers are stateful, so I need a session mapping layer. I'll also assume the LB itself must be horizontally scalable and not a single point of failure. Key decisions will be: routing algorithm, health check design, session persistence strategy, and LB redundancy. Let me walk through each.

Core Components

Interviewer"What routing algorithm would you use, and does that change under different load patterns?"
Routing Algorithm Engine
  • WHY: Without a smart routing algorithm, some backends get overloaded while others sit idle — increasing p99 latency (99th percentile response time, the slow tail not the average) and causing cascading failures.
  • HOW: I'd default to Least Connections (routes each new request to the backend with the fewest active connections) for stateless endpoints — it naturally handles servers with variable processing times. For sticky-session endpoints I'd layer Consistent Hashing (maps requests to backends via a hash ring, minimizing remapping when servers join or leave) on top, keyed on a session cookie or user ID. Round Robin is a fallback only when all backends are homogeneous and processing time is uniform.
  • TRADEOFF: Least Connections requires the LB to track live connection counts per backend, adding state and coordination overhead compared to stateless round-robin.
Interviewer"How does the load balancer know when a backend server has gone down, and how quickly can it stop sending traffic there?"
Health Check System
  • WHY: Without active health checking, the LB continues routing requests to dead servers, causing timeouts and failed transactions for users.
  • HOW: I'd run two tiers of health checks. First, passive checks: the LB monitors live traffic — if a backend returns 5xx errors above a threshold (say 50% error rate over 10 seconds), it's marked unhealthy immediately. Second, active checks: a dedicated health-check goroutine polls each backend every 2 seconds on a /health endpoint; a backend must fail 3 consecutive checks before removal (prevents flapping on transient blips). Reinstatement requires 2 consecutive passes. This two-tier approach catches both hard failures (passive, instant) and degraded servers (active, sustained).
  • TRADEOFF: Active polling adds load to backends and the check interval (2s) means up to 6 seconds before a failed server is fully removed — some requests will hit it during that window.
Interviewer"If a user's session is tied to Backend Server 3 and that server goes down, what happens?"
Session Persistence Layer
  • WHY: Without session persistence, a user's cart or auth state — stored on one backend — is inaccessible when routed to a different server, causing data loss or forced re-login.
  • HOW: I'd use two strategies in parallel. First, cookie-based affinity: the LB inserts an SERVERID cookie mapping the user to a backend; this is stateless on the LB side. Second, a distributed session store (Redis cluster) where backends sync session state asynchronously — this is the real safety net. If Backend 3 dies, the LB routes the user elsewhere and the new backend reads session state from Redis. The cookie strategy is a performance optimization to reduce Redis reads under normal operation.
  • TRADEOFF: Adding Redis as a session store introduces a dependency — if Redis has an outage, session reads fail across all backends, making it a shared failure point.
Interviewer"The load balancer itself is now a single point of failure. How do you handle that?"
LB Redundancy & Failover
  • WHY: A single LB means one hardware failure or process crash takes down all traffic — violating the 99.99% SLA.
  • HOW: I'd run LBs in an active-passive pair behind a Virtual IP (VIP — a floating IP address that can move between machines). Both LBs share state via a heartbeat protocol (VRRP — sends keepalive packets every second to detect peer failure). If the active LB misses 3 heartbeats, the passive one claims the VIP within ~3 seconds. At higher scale, I'd move to active-active with DNS-based load balancing (Anycast routing — multiple machines share one IP, network routes to nearest) in front of the LB tier.
  • TRADEOFF: Active-passive wastes 50% of capacity on standby; active-active requires synchronizing connection tables between LB nodes, adding latency overhead.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1At 1M RPS, a single LB node becomes a CPU bottleneck processing L7 HTTP headers, TLS termination (decrypting SSL/TLS before forwarding), and routing logic simultaneously.
Fix: I'd split the work into two tiers. First, an L4 layer (hardware or kernel-bypass networking like DPDK — bypasses OS network stack for raw speed) handles raw TCP connection distribution across a pool of L7 LB nodes. Each L7 LB node only sees a fraction of total traffic. TLS termination is offloaded to dedicated TLS termination boxes or handled at the L7 nodes using session ticket resumption (avoids full handshake on reconnect) to reduce CPU cost per connection.
Tradeoff: Adding an L4 tier in front of L7 nodes increases infrastructure complexity and adds one more hop of latency (~0.5-1ms) on every request.
2The session persistence mapping (user → backend assignment) stored only in LB memory is lost when the LB restarts or fails over, routing all users to wrong backends and invalidating sessions.
Fix: I'd externalize the session mapping to a shared Redis cluster with TTLs (time-to-live — automatic expiry) matching session length. On failover, the new active LB reads session assignments from Redis instead of rebuilding from memory. For extremely hot mappings, I'd add a local LRU cache (drops least-recently-used entries when full) on each LB node with a short TTL (5 seconds) to reduce Redis read pressure under normal operation.
Tradeoff: Local LRU cache creates a 5-second window where a mapping update (server removed from pool) may not be reflected on an LB node, briefly routing stale sessions.
3Slow backends drag down overall throughput — with Least Connections, a backend that's alive but processing requests slowly still accumulates connections and receives new ones.
Fix: I'd add a circuit breaker (stops sending requests to a backend after failure rate exceeds threshold, then probes with occasional test requests to check recovery) in front of each backend slot in the routing table. Additionally, I'd track weighted response time per backend and use a Weighted Least Response Time algorithm — backends with higher rolling average response times get a lower weight and receive fewer new connections.
Tradeoff: Weighted routing requires the LB to maintain rolling latency statistics per backend, adding memory and computation overhead proportional to backend count.

Reference

API
GET/api/v1/lb/backends— Returns current backend pool with health status, connection counts, and weights for each server
POST/api/v1/lb/backends— Registers a new backend server into the pool with optional weight parameter; returns backend ID
DELETE/api/v1/lb/backends/{backend_id}— Gracefully drains and removes a backend — stops new connections, waits for active ones to close
PUT/api/v1/lb/backends/{backend_id}/weight— Adjusts routing weight for a backend (0 = remove from rotation, 100 = full weight)
GET/api/v1/lb/config— Returns active routing algorithm, health check intervals, and circuit breaker thresholds
PUT/api/v1/lb/config— Updates LB config (algorithm, timeouts) with live reload — no restart required
Database & Storage
  • Redis: In-memory key-value store used for session-to-backend mappings and health check state — sub-millisecond reads required at 1M RPS
  • Schema: session_map(session_id VARCHAR PK, backend_id VARCHAR, created_at TIMESTAMP, ttl_seconds INT) — TTL enforced by Redis EXPIRE command
  • Index strategy: session_id is the only access pattern — Redis key lookup is O(1), no secondary indexes needed; backend_id reverse index kept as a Redis Set for drain operations
  • Key tradeoff: Redis is in-memory so session map size is bounded by RAM — at 1M active sessions × ~100 bytes per entry that's ~100MB, well within limits, but Redis must be clustered to survive node failure
