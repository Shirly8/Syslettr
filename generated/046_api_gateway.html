Systems Design · Tier 2

API Gateway

An API Gateway looks like a simple reverse proxy until you realize it must enforce rate limits, authenticate tokens, route traffic, and transform requests — all in a single network hop at massive scale. Interviewers use it to test whether you understand cross-cutting concerns (shared logic applied to every request) and can reason about latency budgets under load.

Interview

Interviewer
We want to build an API Gateway that sits in front of all our backend microservices. Walk me through how you'd design it.
You
Before diving in — what's the request volume we're targeting, and do we own the client contracts or is this a public third-party API platform? Also, is rate limiting per-user, per-API-key, or per-service?
Interviewer
Public platform, 500K requests per second at peak. Rate limiting is per API key with configurable quotas. p99 latency (99th percentile — the worst-case tail, not average) added by the gateway must stay under 10ms.
You
Got it. So 500K RPS (requests per second) across potentially millions of API keys. At 10ms p99 budget, the gateway itself can't do any synchronous DB calls on the hot path — everything has to come from local memory or a co-located fast store. I'll plan for horizontal scaling (adding more identical gateway nodes) behind a load balancer, with a distributed in-memory store for rate limit counters and a local token cache (storing validated auth tokens in memory on each node). I'll assume API keys map to tenants with quota configs that change rarely — cache-friendly.

Core Components

Interviewer"How do you enforce rate limits at 500K RPS without a centralized DB becoming a bottleneck?"
Rate Limiter
  • WHY: Without rate limiting, a single noisy tenant can starve every other tenant's requests and take down backend services.
  • HOW: I use the token bucket algorithm (each API key gets a 'bucket' that refills at a fixed rate; requests consume tokens) stored in a Redis cluster (a distributed in-memory key-value store). Each gateway node does a Lua script atomic increment on the key's counter per time window — Lua keeps the check-and-decrement atomic so there's no race condition. For extreme throughput, each node also maintains a local counter and syncs to Redis every 100ms, accepting slight over-admission in exchange for near-zero added latency.
  • TRADEOFF: Local counter sync means a key can briefly exceed its quota by up to (number of gateway nodes × local buffer) requests before the global counter corrects — acceptable for most use cases but not for strict financial quotas.
Interviewer"JWT validation on every request — how do you keep that fast and handle token revocation?"
Auth & Token Validation
  • WHY: Without auth on every request at the gateway, a single compromised token can hit any downstream service with no central enforcement point.
  • HOW: I validate JWTs (JSON Web Tokens — self-contained signed auth credentials) locally on each gateway node using the public key — no network call needed for valid, non-revoked tokens. I keep a local blocklist cache (a set of revoked token JTI claims — unique token IDs) with a TTL matching the max token lifetime. The blocklist is pushed to all nodes via a pub/sub channel whenever a token is revoked, so revocation propagates in under a second. For API key auth (non-JWT), I cache the key-to-tenant mapping in a local LRU cache (drops least-recently-used entries when full) with a 60-second TTL.
  • TRADEOFF: If a node misses a pub/sub revocation event due to a network blip, it can accept a revoked token for up to 60 seconds until the next TTL-based refresh.
Interviewer"How does the gateway know which backend service to send a request to, and how do you handle versioning?"
Request Router
  • WHY: Without intelligent routing, every backend team must expose their own public IP, breaking encapsulation and making API versioning impossible to manage centrally.
  • HOW: I maintain a routing table (path prefix → backend service cluster mapping) loaded from a config store like etcd (a distributed key-value store for config data). The table is cached locally on each gateway node and watched for changes via a long-poll (keeping an open connection to detect updates). Routes are matched in order: exact path first, then prefix, then wildcard. Version routing (/v1/, /v2/) maps to different backend clusters — allowing blue/green deployments (running old and new versions simultaneously to shift traffic gradually) by adjusting the routing weights.
  • TRADEOFF: Path-based routing means breaking URL structure changes in backends propagate immediately to clients — teams must treat path contracts as a public API.
Interviewer"Some clients send legacy XML payloads but backends only speak JSON — where does that translation live?"
Request/Response Transformer
  • WHY: Without a transform layer at the gateway, every backend service must implement its own protocol translation, duplicating logic and coupling backend teams to client contracts.
  • HOW: I apply a middleware pipeline (a chain of composable steps each request and response passes through) on the gateway node itself. Each step is configured per-route: header injection, payload schema mapping, response field masking. Transforms are defined as declarative configs (not code) stored in the config store so they can be updated without deploying a new binary. For expensive transforms like XML→JSON parsing, I benchmark to ensure they fit in the 10ms latency budget — if they don't, I push that logic to a dedicated sidecar process (a lightweight helper process co-deployed next to the gateway).
  • TRADEOFF: Putting transform logic in the gateway creates a coupling point — when a backend changes its schema, the gateway transform config must also change.
Interviewer"How do you debug a request that failed across three hops in the gateway pipeline?"
Observability Pipeline
  • WHY: Without distributed tracing (linking logs across all services using a shared request ID), a failure in a multi-step pipeline looks like a single error with no path to the root cause.
  • HOW: Every request gets a trace ID injected as a header at the gateway entry point if one isn't already present. Each middleware step appends a span (a timed unit of work within a trace) with timing and status before passing the request along. I emit structured logs (machine-parseable JSON log lines, not free text) and metrics per route per status code to a time-series store. I sample 100% of error traces and 1% of success traces to control volume — a technique called head-based sampling (the decision is made at trace start).
  • TRADEOFF: 1% sampling of success traces means rare intermittent errors may fall outside sampled traffic and go undetected until they spike enough to hit the error trace bucket.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Redis rate limit counters become a hot bottleneck at 500K RPS because every request does a round-trip to increment a shared key.
Fix: I switch to a local sliding window counter on each gateway node, synchronized to Redis every 100ms in a background goroutine rather than per-request. Each node claims a share of the quota proportional to 1/N (where N is node count, updated via service discovery). The Redis sync corrects for drift. For keys that need strict enforcement (financial APIs), I reserve a small synchronous Redis call budget — but that's the exception, not the default.
Tradeoff: Burst traffic on a single node can temporarily over-admit by up to (node quota share × sync interval) requests before Redis corrects the distributed counters.
2A single global routing table reload blocks all in-flight requests when a backend service config changes.
Fix: I use a copy-on-write (a pattern where readers see the old version while a new version is being built) approach for the routing table. The gateway node holds a pointer to the current immutable table. On a config change event from etcd, a background goroutine builds the new table and atomically swaps the pointer. In-flight requests finish against the old table; new requests instantly see the new one — no lock contention.
Tradeoff: During the swap window (typically under 1ms), there's a brief period where some requests hit the old config — acceptable for route changes but could cause a momentary 404 spike during a service removal.
3TLS termination (decrypting HTTPS traffic) at 500K RPS is CPU-intensive and can saturate gateway nodes before they hit any other limit.
Fix: I offload TLS termination to a dedicated layer — either hardware load balancers or a TLS proxy tier — upstream of the gateway nodes. The gateway then receives plain HTTP internally over a trusted private network (using mTLS — mutual TLS, where both sides present certificates — for internal hop security without full public TLS overhead). This lets gateway nodes spend CPU on routing logic, not cryptography.
Tradeoff: Adding a TLS termination layer increases hop count by one and adds ~1-2ms to end-to-end latency, which must fit within the overall latency budget.

Reference

API
POST/api/v1/keys— Create API key for a tenant; returns key_id, secret, and quota config
GET/api/v1/keys/{key_id}— Fetch API key metadata and current quota usage for a key
PUT/api/v1/keys/{key_id}/quota— Update rate limit quota for a key; propagates to gateway nodes via pub/sub
DELETE/api/v1/keys/{key_id}— Revoke an API key; pushes JTI to blocklist and removes key from route cache
POST/api/v1/routes— Register a new route rule (path prefix → backend cluster); triggers routing table reload
GET/api/v1/routes— List all active route configs with current backend health status
GET/api/v1/metrics/{key_id}— Return per-key request counts, error rates, and p99 latency for a time window
Database & Storage
  • PostgreSQL — for API key metadata and route configs; relational integrity matters for tenant→key→quota relationships
  • Schema: api_keys(key_id UUID PK, tenant_id UUID, hashed_secret TEXT, quota_rpm INT, created_at TIMESTAMP, revoked_at TIMESTAMP)
  • Schema: routes(route_id UUID PK, path_prefix TEXT UNIQUE, backend_cluster TEXT, priority INT, transform_config JSONB, updated_at TIMESTAMP)
  • Index: api_keys(hashed_secret) for fast key lookup on auth; routes(path_prefix, priority) for ordered prefix matching
  • Redis Cluster — for rate limit counters and blocklist; TTL-keyed per time window, never persisted to disk
  • Redis key pattern: ratelimit:{key_id}:{window_epoch} with INCR and EXPIREAT; blocklist:{jti} with TTL = token max lifetime
  • Tradeoff: Postgres is source of truth but never on the hot request path — all hot reads come from local cache or Redis; a cache miss on a cold key adds ~5ms latency for the first request only
