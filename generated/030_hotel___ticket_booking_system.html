Hotel / Ticket Booking System

The deceptively hard part isn't search or display — it's the race condition where two users book the last room or seat simultaneously and both succeed. Interviewers use this system to probe inventory locking strategies, idempotency, and distributed coordination under real-time pressure.

Interview

Interviewer
Design a hotel booking system — think something like Hotels.com or Booking.com. Where do you start?
You
A few quick questions first. Are we designing the full platform — search, inventory management, and checkout — or focusing on the reservation and inventory path specifically? What's the scale: tens of thousands of hotels globally, or more like a regional product? And what's the SLA on booking confirmation — does it need to be synchronous and instant, or can we accept a short async delay?
Interviewer
Full platform but focus on search and booking. 500,000 hotels globally, ~10 million bookings per day. Booking confirmation must be synchronous — users need an immediate yes or no.
You
10 million bookings per day is roughly 115 writes/sec average, but with spikes — flash sales or popular events — I'd plan for 10x, so ~1,150 writes/sec peak. Search will dwarf that; assuming 50 searches per booking, that's 5,750 search reads/sec baseline, 50K+ at peak. Synchronous confirmation means I can't defer inventory deduction — I need to hold a lock or use optimistic concurrency (checking a version number before committing, retrying on conflict) at checkout. I'll assume each hotel has up to 500 room types, each with daily availability records. Core tables will be hot and small enough to cache aggressively, but the booking write path is the design's heart.

Core Components

Interviewer"How do you actually prevent two users from booking the same room on the same night simultaneously?"
Inventory & Availability Service
  • WHY: Without a coordination mechanism, two concurrent checkout requests both read availability as 1, both decrement, and both succeed — the classic double-booking race condition.
  • HOW: I use optimistic locking with a version column on the inventory row. When a user reaches checkout, the server reads the row and its version. On commit, the UPDATE includes a WHERE version = clause — if another transaction already changed it, the row count comes back 0 and I return a conflict error to the user. For high-contention inventory (last seat at a concert), I add a short-lived reservation hold: atomically decrement a Redis counter (Redis is an in-memory key-value store) for the room+date key. The hold expires in 10 minutes via TTL (time-to-live, an automatic expiry). If payment fails, the hold evaporates without a manual rollback.
  • TRADEOFF: Optimistic locking causes user-facing retries under high contention; the Redis hold adds a distributed dependency that must be made resilient with replication.
Interviewer"With 500,000 hotels and date-range queries, how do you make search fast without hitting the database on every request?"
Search & Availability Query Service
  • WHY: Querying raw availability rows per hotel per night for every search request would kill the database — searches outnumber bookings 50:1.
  • HOW: I precompute a rolled-up availability summary (min available rooms across dates in a range) and cache it in Redis with a short TTL of 60 seconds. The cache key is hotel_id:checkin:checkout:room_type. On a cache miss, the query service reads from a read replica (a DB copy that only receives replicated writes, never direct user writes) of the inventory DB. I accept that search results can be 60 seconds stale — a final authoritative check happens only at checkout when the Redis hold is attempted.
  • TRADEOFF: 60-second stale availability means a user might reach checkout to find the room gone — the hold step catches this but creates friction.
Interviewer"What happens if payment succeeds but the final DB write fails? How do you avoid charging users twice on retry?"
Booking & Payment Orchestrator
  • WHY: Without idempotency (the property that retrying an operation produces the same result as doing it once), a network hiccup between payment success and DB commit could cause a double charge or a ghost booking.
  • HOW: The client generates a UUID idempotency key before calling checkout. The orchestrator stores this key with status PENDING in a bookings table before calling the payment processor. On retry with the same key, it detects the existing record and returns the prior result without re-charging. If payment succeeds but the DB write fails, a background reconciliation job matches payment processor receipts against booking records and completes any orphaned PENDING entries.
  • TRADEOFF: The reconciliation job introduces a short inconsistency window — a confirmed payment might briefly show as PENDING to the user.
Interviewer"How do you handle sending confirmation emails and SMS without slowing down the booking response?"
Notification Service
  • WHY: Blocking the booking API response on email/SMS delivery introduces latency from external providers and creates failure coupling — a flaky email vendor should never fail a booking.
  • HOW: After the booking is committed, the orchestrator publishes a BookingConfirmed event to a message queue (a durable buffer that decouples producers from consumers). A separate notification consumer reads from the queue and calls email and SMS providers asynchronously. The queue persists messages, so if a provider is down, messages accumulate and drain when service resumes. I use dead-letter queues (a secondary queue for messages that fail after N retries) to catch persistent failures.
  • TRADEOFF: Notifications arrive slightly after booking confirmation — seconds to minutes depending on queue backpressure.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Hot inventory rows for popular hotels or events get hammered by concurrent checkout attempts, causing lock contention on the primary DB that serializes requests and spikes latency.
Fix: I front the inventory check with a Redis counter per room+date. The Redis DECR operation is atomic and runs in microseconds — only the request that successfully decrements to ≥ 0 proceeds to the DB write. This reduces DB write contention by only letting one 'winner' per available slot reach the primary DB. I shard (split) the Redis keyspace by hotel_id so no single Redis node becomes the bottleneck for all hotels simultaneously.
Tradeoff: Redis is now in the critical path for every booking — if it goes down, bookings fail. I mitigate with Redis replication and sentinel (automatic failover manager), but adding a dependency always adds failure surface.
2Search queries scanning availability across 500K hotels for flexible date ranges are too slow for a single relational DB — full table scans on date-range joins don't scale.
Fix: I offload hotel metadata search to a dedicated search index (like Elasticsearch — a distributed inverted-index engine optimized for complex queries). The search index stores pre-aggregated availability windows, amenities, and pricing. It's kept eventually consistent with the primary DB via a change-data-capture pipeline (CDC — streams row-level DB changes in real time). The relational DB stays as the source of truth for booking writes; the search index is purely for discovery.
Tradeoff: CDC adds operational complexity and the search index lags the DB by seconds — a room sold a moment ago might still appear available in search results until the next CDC flush.
3A single booking service instance becomes a bottleneck during high-traffic events (concert on-sale, holiday hotel rush), exhausting connection pools to the DB.
Fix: I horizontally scale booking service instances behind the load balancer and introduce a connection pool proxy (a middleware layer that multiplexes many app-side connections onto fewer real DB connections). Each booking service instance is stateless — session state lives in Redis, not in memory. I also add a queue in front of the inventory write path during flash sale events as a demand buffer, accepting that confirmation might take a few seconds instead of being instant.
Tradeoff: Queuing inventory writes during peak load breaks the synchronous confirmation SLA — users see 'processing' instead of instant confirmation.

Reference

API
GET/api/v1/hotels?checkin=DATE&checkout=DATE&guests=N&city=STR&page=N— Returns paginated list of available hotels with min price and availability summary; reads from search index via cache
GET/api/v1/hotels/{hotel_id}/rooms?checkin=DATE&checkout=DATE— Returns room types and per-night pricing for specific hotel and date range; reads from read replica
POST/api/v1/bookings— Creates a booking; body includes hotel_id, room_type_id, dates, guest info, idempotency_key; returns booking_id and status PENDING or CONFIRMED
GET/api/v1/bookings/{booking_id}— Returns booking status, confirmation number, and payment state; used for polling after async confirmation
DELETE/api/v1/bookings/{booking_id}— Cancels a booking if within cancellation window; triggers refund via payment provider and releases inventory hold
Database & Storage
  • PostgreSQL — relational integrity for bookings, ACID transactions for optimistic locking, row-level versioning
  • hotels(hotel_id UUID PK, name TEXT, city TEXT, country TEXT, star_rating INT, amenities JSONB, created_at TIMESTAMPTZ)
  • rooms(room_id UUID PK, hotel_id UUID FK, room_type TEXT, max_guests INT, base_price_cents INT)
  • inventory(inventory_id UUID PK, room_id UUID FK, date DATE, total_count INT, available_count INT, version INT) — version column enables optimistic locking
  • bookings(booking_id UUID PK, user_id UUID, room_id UUID FK, checkin DATE, checkout DATE, status TEXT, idempotency_key UUID UNIQUE, payment_ref TEXT, created_at TIMESTAMPTZ)
  • Index: inventory(room_id, date) — covers all availability range scans; bookings(user_id, created_at DESC) — covers user booking history queries
  • Shard inventory and bookings by hotel_id to distribute write load; keep hotels and rooms on a single unsharded node — they're small and rarely written
