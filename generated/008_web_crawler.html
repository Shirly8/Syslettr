Systems Design · Tier 1

Web Crawler

A web crawler looks simple — fetch a page, extract links, repeat — but at billions of URLs the hard problems are deduplication, politeness (not hammering a single host), and distributed coordination of what to crawl next. Interviewers use it to probe distributed systems depth: queues, bloom filters, DNS caching, and fault tolerance all come up naturally.

Interview

Interviewer
We want to build a general-purpose web crawler. Where do you start?
You
Before diving in — what's the target corpus size, billions of pages or something smaller? Is freshness a requirement, meaning do we re-crawl pages periodically? And do we need to respect robots.txt and crawl-delay directives?
Interviewer
Target is 10 billion pages crawled over 30 days, with re-crawl every 30 days for freshness. Yes, robots.txt must be respected. Average page is 100KB.
You
10B pages / 30 days = ~3,900 pages/sec sustained throughput. At 100KB each that's ~390MB/sec of raw HTML to process. Storage for raw pages: 10B × 100KB = ~1PB — I'd store compressed HTML in object storage (a blob store like S3, not a relational DB). URL metadata — seen status, crawl time, priority — needs a fast key-value store. I'll plan for ~500 crawler worker machines to hit ~3,900 pages/sec assuming ~10 pages/sec per worker after network latency and politeness delays.

Core Components

Interviewer"How do you manage which URLs get crawled and in what order without overwhelming individual hosts?"
URL Frontier
  • WHY: Without a structured frontier, workers pile onto the same host simultaneously, causing bans and violating robots.txt crawl-delay rules.
  • HOW: I partition the frontier into per-host queues. A router hashes each URL by hostname and places it into that host's dedicated sub-queue. Each worker pulls from one host queue at a time and enforces a minimum delay (e.g., 1 request per host per second) between requests to that host — this is politeness. A priority layer sits above the host queues and orders hosts by crawl importance (PageRank estimate, freshness deadline). I use a distributed priority queue backed by a sorted set so workers can claim the next eligible host atomically.
  • TRADEOFF: Per-host queuing adds routing overhead and a slower host can starve that queue while others are idle — requires work-stealing logic to rebalance.
Interviewer"With 10 billion URLs, how do you efficiently track which ones you've already seen?"
URL Deduplication with Bloom Filter
  • WHY: Without dedup, crawlers loop through redirect cycles and re-crawl the same page millions of times, wasting all available capacity.
  • HOW: I use a bloom filter (a probabilistic data structure — tests set membership with no false negatives, small false-positive rate) stored in shared memory across the crawler cluster. At 10B URLs with a 0.1% false-positive rate, a bloom filter needs roughly 14.4 bytes/URL × 10B ≈ 144GB — fits in a large Redis cluster. Before enqueuing any extracted URL, the worker checks the bloom filter; if it returns 'seen', discard. If 'unseen', mark it and enqueue. For the small false-positive rate I periodically reconcile against the authoritative URL metadata store.
  • TRADEOFF: False positives mean a small fraction of valid new URLs are silently skipped — acceptable for a crawler but would be catastrophic in a payment system.
Interviewer"Wouldn't DNS lookups become a bottleneck at nearly 4,000 pages per second?"
DNS Cache
  • WHY: At 4K fetches/sec, DNS resolution (translating hostname to IP) adds 20-100ms per cold lookup; without caching, half the crawler time is DNS.
  • HOW: I run a local DNS resolver cache (a TTL-respecting in-process cache, not a separate service) on each crawler worker. I pre-warm it by resolving all hostnames from the frontier batch before the batch starts. DNS TTLs are respected to avoid stale IPs causing connection failures.
  • TRADEOFF: Very short TTLs (e.g., 30s CDN entries) still cause frequent re-resolution; I accept that rather than violating TTLs, which would break correctness for CDN-shifted content.
Interviewer"What about duplicate content — different URLs pointing to the same page?"
Content Store & Dedup
  • WHY: The web has enormous content duplication — mirrors, tracking params — and storing duplicates wastes ~30% of storage and pollutes search indexes.
  • HOW: After fetching, I compute a SimHash (a locality-sensitive hash that produces similar fingerprints for similar documents) of the page body. I store fingerprints in a distributed hash table keyed by SimHash. If the incoming SimHash is within a Hamming distance (number of differing bits) threshold of an existing entry, I mark the page as near-duplicate and store only a pointer to the canonical document rather than the full HTML. Raw HTML for unique pages goes to object storage.
  • TRADEOFF: SimHash can miss near-duplicates when documents differ only in boilerplate; exact URL dedup via bloom filter handles the easy cases but SimHash is the expensive second pass.
Interviewer"How do you handle robots.txt without fetching it on every request to a domain?"
Robots.txt Manager
  • WHY: Fetching robots.txt on every page request doubles DNS + TCP overhead per host and hammers server endpoints unnecessarily.
  • HOW: I maintain a robots.txt cache keyed by host, with a TTL (time-to-live) of 24 hours. The first worker to need a host fetches its robots.txt, parses allowed/disallowed paths and crawl-delay, and writes the result into a shared cache. All subsequent workers check that cache before enqueuing or fetching any URL from that host.
  • TRADEOFF: A 24-hour TTL means webmasters can't immediately block a crawler by updating robots.txt — acceptable for most use cases, but I'd reduce the TTL to 1 hour for hostile-domain lists.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single URL frontier service becomes a write/read hotspot when 500 workers all enqueue and dequeue URLs concurrently at 3,900 ops/sec.
Fix: I partition the frontier by consistent hashing (a technique that maps keys to one of N buckets with minimal reshuffling when N changes) on hostname across multiple frontier shards — say 32 shards. Each worker is assigned a subset of shards and only interacts with those. This limits contention to 1/32 of total traffic per shard. I also batch enqueues: workers buffer 100 extracted URLs locally before writing to the frontier in a single batch call.
Tradeoff: Static shard assignment can cause hot shards if a few high-link-count domains dominate — I need a rebalance mechanism or dynamic assignment.
2Re-crawling 10B pages every 30 days means the system spends equal time on rarely-changing static pages as on high-value frequently-updated news pages.
Fix: I implement adaptive crawl scheduling with three tiers: high-frequency (news, social), medium, and low (static docs). I track a change rate (ratio of fetches that returned new content vs cached ETag — a server-provided hash of the content) per domain over rolling 7-day windows. Domains with high change rates get priority queue slots more often; stable domains are downgraded to a slower crawl cycle automatically.
Tradeoff: Newly discovered domains start with no change-rate history and default to medium frequency — may miss a viral new site's initial burst.
3A slow or unresponsive target host causes worker threads to block on TCP connections, reducing overall crawl throughput.
Fix: I set aggressive per-request timeouts — 5s connect, 15s read. Workers use async I/O (non-blocking network calls that let a single thread manage hundreds of in-flight requests) so a stalled connection doesn't monopolize a thread. Hosts that timeout more than 3 times in a row are placed in a backoff queue with exponential delay (2, 4, 8 minutes) before retry.
Tradeoff: Aggressive timeouts may fail on legitimately slow large pages (e.g., 10MB HTML); I add a size-aware timeout extension for responses that are actively streaming data.

Reference

API
POST/api/v1/crawl/seeds— Submit a batch of seed URLs to bootstrap or extend the frontier; returns a job_id
GET/api/v1/crawl/status/{job_id}— Returns crawl progress: pages fetched, queued, failed, estimated completion
GET/api/v1/pages/{url_hash}— Retrieve metadata (crawl timestamp, canonical URL, content hash) for a crawled page
DELETE/api/v1/crawl/blocklist/{hostname}— Immediately stop crawling a domain; persists to robots-override list
GET/api/v1/frontier/stats— Returns per-shard queue depths, p99 latency, and top-N hosts by queue size for ops visibility
Database & Storage
  • Redis Cluster — bloom filter (144GB bit array) and robots.txt cache fit naturally in memory with TTL support
  • Schema: url_metadata(url_hash CHAR(32) PK, raw_url TEXT, last_crawled_at TIMESTAMP, crawl_priority FLOAT, content_hash CHAR(64), status TINYINT)
  • Object Storage (S3-compatible) — raw compressed HTML keyed by url_hash; avoids storing 1PB in a relational DB
  • Index strategy: url_metadata indexed on (crawl_priority DESC, last_crawled_at ASC) to support efficient priority frontier queries
  • Key tradeoff: Redis bloom filter is in-memory so a cluster restart loses state — persist snapshots to disk every 5 minutes and replay on recovery, accepting up to 5 minutes of re-crawl duplication
