Task Queue System

A task queue looks simple — put a job in, take it out — but guaranteeing delivery exactly once across failures, retries, and distributed workers is genuinely hard. Interviewers use it to probe your understanding of distributed systems guarantees, backpressure, and failure modes that only appear at scale.

Interview

Interviewer
We need to design a task queue system — think something like a background job processor. Where do you start?
You
Before diving in — what's the job volume we're targeting, thousands per second or millions? Are jobs short-lived (sub-second) or can they run for minutes? And what's the delivery guarantee — at-least-once is fine, or do we need exactly-once semantics (each job runs exactly one time, never duplicated)?
Interviewer
Aim for about 100K job submissions per second at peak. Jobs can take anywhere from a few milliseconds to a few minutes. At-least-once delivery is acceptable, but duplicate execution should be rare. P99 processing latency (the slowest 1-in-100 job, ignoring the fast average) under 500ms for short jobs.
You
So 100K enqueues/sec — that's roughly 8.6 billion jobs per day. I'll assume an average payload of 1KB, so about 100MB/s ingress on the queue. At-least-once means I need idempotency keys (a unique ID per job so workers can detect and skip duplicates) on the worker side. I'll design for horizontal worker scaling, durable persistence on the queue broker, and a dead-letter queue (DLQ — where jobs go after too many failed retries) so nothing silently disappears.

Core Components

Interviewer"How do producers submit jobs without overwhelming the queue broker?"
Job Ingestion API
  • WHY: Without rate-limiting and buffering at ingestion, a traffic spike can overwhelm the broker and cause dropped messages or cascading failures.
  • HOW: I expose a stateless REST/gRPC layer that validates payloads, assigns a UUID job ID, and writes to the broker. I add per-producer rate limiting using a token bucket (a counter that refills at a fixed rate — producers blocked when empty) so no single caller floods the system. The API returns the job ID immediately after the broker acknowledges the write, keeping the path synchronous but fast.
  • TRADEOFF: We're bounded by broker write throughput; if the broker lags, the API back-pressures producers, which they must handle gracefully.
Interviewer"How do you make the queue itself durable and scalable to 100K writes per second?"
Queue Broker & Partitioning
  • WHY: A single broker node is a bottleneck and a single point of failure — if it crashes, in-flight jobs are lost.
  • HOW: I partition (split) the queue into N topic partitions distributed across broker nodes, keyed by job type or tenant ID so related jobs land on the same partition. Each partition is replicated (copied) across 3 broker replicas using leader-follower replication — the leader accepts writes, followers sync. A write is acknowledged only after a quorum (majority of replicas) confirms it, so no data is lost on a single node failure.
  • TRADEOFF: Quorum writes add ~5–10ms latency per enqueue versus fire-and-forget, and partition count must be chosen up front — rebalancing later is operationally expensive.
Interviewer"How do workers pull jobs and what happens when a job fails mid-execution?"
Worker Pool & Job Execution
  • WHY: Without a visibility timeout (a lease — the job is hidden from other workers while one is processing it), a crashed worker causes the job to be permanently lost or never retried.
  • HOW: Workers long-poll (wait up to N seconds for a message rather than busy-looping) the broker, receive a job with a visibility timeout — say 60 seconds. The worker must heartbeat (send periodic keep-alives) to extend the timeout while working. On success it sends an explicit ack (acknowledgment) to delete the job. On failure or timeout expiry, the job becomes visible again for another worker to retry.
  • TRADEOFF: Visibility timeouts must be longer than max expected job duration; too short and healthy long-running jobs get re-queued and executed twice.
Interviewer"What happens to jobs that keep failing — how do you avoid infinite retry loops?"
Dead-Letter Queue (DLQ)
  • WHY: Without a DLQ, a poison pill job (one that always crashes workers) can loop forever, blocking the queue and starving other jobs.
  • HOW: Each job carries a retry_count. After a configurable max (say 5 retries), the broker routes the job to a separate DLQ partition instead of re-enqueuing it. I use exponential backoff (retry delays that double each time — 1s, 2s, 4s…) to reduce thundering herd pressure. An alerting pipeline watches DLQ depth and pages on-call when it spikes, so engineers can inspect and replay or discard jobs manually.
  • TRADEOFF: Jobs in the DLQ are paused indefinitely until manually handled — you need operational tooling to replay them, or they rot.
Interviewer"How do producers check whether their job completed, and how do you avoid hammering the broker for status?"
Job Status Store
  • WHY: Producers need job lifecycle visibility (submitted → running → done/failed) without polling the broker directly, which would couple status reads to queue internals.
  • HOW: Workers write state transitions to a dedicated status store — a key-value store keyed by job_id. On status reads I put a short-TTL (time-to-live, how long a cache entry lives before expiry) read-through cache in front: cache hit returns instantly, cache miss fetches from the store and warms the cache. Terminal states (done, failed) are cheap to cache aggressively since they never change.
  • TRADEOFF: Cache adds a brief staleness window — a producer polling quickly after submission may see 'pending' for a few hundred milliseconds after the job actually finished.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A slow or stuck partition causes all workers assigned to it to stall, while other partitions are idle — uneven load kills throughput.
Fix: I implement consumer group rebalancing: workers are organized into a consumer group (a pool that collectively covers all partitions) and a coordinator reassigns partitions if a worker is slow or dies. I also add lag monitoring — if a partition's consumer lag (how far behind the worker is from the latest message) grows past a threshold, I spin up extra workers dynamically and redistribute. Long-running jobs get a separate partition pool so they can't starve short-job partitions.
Tradeoff: Rebalancing causes a brief pause (stop-the-world for a few seconds) while partitions are reassigned — during this window, no messages are consumed from affected partitions.
2The status store becomes a hotspot when thousands of producers poll job_id status at high frequency, overwhelming a single node.
Fix: I shard (split across nodes) the status store by job_id hash so reads and writes spread evenly. Terminal states (done, failed) I cache aggressively with a long TTL since they're immutable. For non-terminal states I use a short TTL and rely on worker heartbeats to push updates proactively via a pub-sub (publish-subscribe — broadcast updates to interested subscribers) channel, so producers can subscribe rather than poll.
Tradeoff: Pub-sub adds connection state overhead on the server — with millions of waiting producers, connection fan-out can itself become a bottleneck.
3At 100K jobs/sec, a single retry mechanism with fixed delays floods the broker when a downstream dependency goes down — all retried jobs arrive simultaneously.
Fix: I enforce exponential backoff with jitter (random offset added to the delay so retries don't synchronize) on the broker side: delay = min(base * 2^attempt + rand(0, 1s), max_delay). The jitter spreads retry arrivals across a window rather than a sharp spike. I also add a circuit breaker (stops sending jobs to a failing downstream after N errors, reopens after a cooldown) on the worker side to prevent accumulation entirely.
Tradeoff: Jobs may sit in backoff longer than users expect — the system trades immediacy for stability under dependency failure.

Reference

API
POST/api/v1/jobs— Enqueues a job; body has {type, payload, idempotency_key}; returns {job_id, status: 'pending'}
GET/api/v1/jobs/{job_id}— Returns current job state: pending | running | done | failed, plus result or error detail
DELETE/api/v1/jobs/{job_id}— Cancels a pending job if not yet picked up by a worker; returns 409 if already running
POST/api/v1/jobs/{job_id}/retry— Manually re-enqueues a failed or DLQ job; resets retry_count; returns new job_id
GET/api/v1/queues/{queue_name}/stats— Returns depth, consumer lag, DLQ size, and p99 processing latency for a named queue
Database & Storage
  • Key-Value Store (e.g. consistent hash-sharded KV) for job status — O(1) reads by job_id, no relational joins needed
  • Schema: jobs(job_id UUID PK, queue VARCHAR, payload JSONB, status VARCHAR, retry_count INT, created_at TIMESTAMPTZ, updated_at TIMESTAMPTZ, ttl INT)
  • Index on (queue, status, created_at) for DLQ inspector queries; primary lookup is always by job_id so no secondary index needed on hot path
  • Terminal-state entries (done/failed) carry a TTL of 7 days and are evicted automatically — storing forever would cause unbounded growth at 100K jobs/sec
