CAP Theorem

The CAP theorem sounds like a simple three-way trade-off, but the hard part is knowing which guarantees to sacrifice for your specific workload — and how to explain the real-world nuance that you can tune consistency on a per-operation basis. Interviewers ask this to separate engineers who memorize acronyms from those who can reason about what actually breaks when a network partition occurs.

Interview

Interviewer
You're designing a distributed key-value store that needs to run across three geographically separated data centers. Walk me through how you'd approach consistency and availability guarantees.
You
Before diving in — what's the primary workload, read-heavy or write-heavy? And what's the failure model we care most about: occasional node crashes, or full network partitions between data centers? Also, is there a hard SLA on read latency, or is it best-effort?
Interviewer
Mixed read/write, roughly 60/40. The main concern is cross-region partitions that could last seconds to minutes. Read p99 latency should stay under 100ms even during failures.
You
Got it. So partitions are a given — CAP theorem (a distributed system can guarantee at most two of: Consistency, Availability, Partition Tolerance simultaneously) tells us we must choose between consistency and availability when a partition happens, because we can't eliminate partitions in a geo-distributed setup. Given the 100ms p99 (99th percentile — the slow tail, not the average) read SLA, I'll lean AP (Available + Partition-tolerant) with tunable consistency — serve reads from local replicas but let operators dial up to strong consistency for critical operations. Writes will use quorum (requiring a majority of replicas to acknowledge before success) to keep drift bounded.

Core Components

Interviewer"How do you let clients choose their consistency level without making the API a nightmare to use?"
Consistency Model Selector
  • WHY: Without per-operation consistency tuning, you're forced to choose one mode for the entire system — which never fits mixed workloads.
  • HOW: I expose a consistency hint on each read/write request: eventual, bounded-staleness (reads lag by at most X seconds), or strong. The coordinator node routes based on this — eventual reads go to the nearest replica immediately, strong reads block until all replicas in quorum acknowledge. I default to bounded-staleness to stay within the 100ms SLA under normal operation.
  • TRADEOFF: Putting consistency choice in the client's hands means application bugs can silently choose the wrong level and cause correctness issues.
Interviewer"Walk me through how quorum writes and reads actually work when one of your three data centers goes dark."
Quorum Replication Engine
  • WHY: Without quorum, you have no principled way to bound how stale a read can be — any replica could return arbitrarily old data after a partition heals.
  • HOW: I use a W + R > N quorum configuration (where N=3 replicas, W=2 write acknowledgments, R=2 read quorum). A write succeeds when 2 of 3 replicas confirm. A strong read fetches from 2 of 3 and returns the highest version-stamped value — this guarantees overlap with the last successful write. If one data center partitions off, writes and strong reads still succeed using the remaining two nodes.
  • TRADEOFF: With N=3, W=2, R=2, you lose strong consistency the moment two nodes fail simultaneously — a rare but non-zero risk.
Interviewer"Once the partition heals, how do you reconcile the diverged replicas?"
Anti-Entropy Repair Process
  • WHY: Without reconciliation, a rejoining replica serves stale reads indefinitely — your eventual consistency guarantee has no time bound.
  • HOW: I run a continuous Merkle tree (a hash tree where each node summarizes its subtree, making divergence detection O(log N)) comparison between replicas. When a partition heals, the rejoining node exchanges tree hashes with peers, identifies which key ranges diverged, and pulls only the delta. Conflict resolution uses last-write-wins with vector clocks (per-replica counters that establish causal ordering) to pick the correct version.
  • TRADEOFF: Last-write-wins can silently discard concurrent writes — for financial or inventory data you'd need application-level merge logic instead.
Interviewer"How does the system actually know it's in a partition, and does it behave differently in that mode?"
Partition Detection & Mode Switch
  • WHY: Without explicit partition detection, nodes may queue writes indefinitely waiting for acknowledgment that will never come, blowing past the 100ms SLA.
  • HOW: Each coordinator tracks heartbeat timeouts on replica connections. When timeouts exceed a threshold (e.g., 500ms with three retries), I mark that replica suspect and switch strong-consistency operations to degraded mode — serving reads from remaining quorum members and queuing cross-region sync for when the link recovers. I expose a health endpoint that reports current consistency mode so load balancers can optionally route reads differently.
  • TRADEOFF: A false positive partition detection (slow network, not a real split) will unnecessarily degrade consistency guarantees for healthy nodes.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Under a partition, strong-consistency reads stall waiting for unreachable replicas, blowing past the 100ms p99 SLA.
Fix: I add a read hedge (sending the same read to two replicas simultaneously and taking the first response) with a 50ms timeout before falling back to the fastest available replica and downgrading to bounded-staleness. The coordinator logs the fallback so the ops team can detect sustained partition events. This keeps p99 under 100ms while making the consistency downgrade explicit and observable.
Tradeoff: Hedged reads double the read traffic to replicas during normal operation, increasing replica CPU load by roughly 2x.
2Anti-entropy Merkle tree sync after a long partition generates a large delta transfer that saturates the inter-DC link and delays normal traffic.
Fix: I rate-limit (throttle bandwidth consumption) the anti-entropy repair process to a configurable ceiling — say 10% of inter-DC bandwidth — and prioritize repair of recently written key ranges first using a repair queue sorted by write timestamp. This lets normal quorum traffic share the link without being crowded out during catch-up.
Tradeoff: Rate-limiting repair extends the convergence window after a long partition, meaning stale reads are possible for longer on the rejoining replica.
3Vector clock storage grows unbounded as the number of replicas and keys scales, bloating per-key metadata.
Fix: I prune vector clocks by GC-ing (garbage collecting — reclaiming unused memory/storage) entries for replicas that have been decommissioned, and by compacting clocks during anti-entropy sync: once all replicas have acknowledged a value as stable, I drop the clock entry and store only the final resolved value. This bounds clock size to O(active replicas).
Tradeoff: Clock pruning means you permanently lose the causal history for compacted keys — debugging causality issues in production becomes harder.

API
GET/api/v1/keys/{key}?consistency=eventual|bounded|strong— Returns value + version vector; consistency param controls quorum behavior, defaults to bounded-staleness
PUT/api/v1/keys/{key}— Writes value with optional If-Version header for CAS (compare-and-swap); returns new version on quorum success
DELETE/api/v1/keys/{key}— Tombstones the key (marks deleted without immediate removal) and propagates via anti-entropy
GET/api/v1/health— Returns current consistency mode (normal/degraded), replica quorum status, and partition events
GET/api/v1/keys/{key}/versions— Returns full version history for debugging causality — admin-only endpoint
Database & Storage
  • LSM-tree storage engine (Log-Structured Merge-tree — optimizes write throughput by buffering writes in memory) per replica — write-heavy workloads and natural support for range scans on version history.
  • Schema: kv_store(key VARCHAR PK, value BYTES, version_vector JSONB, written_at TIMESTAMP, tombstone BOOLEAN)
  • Index on (written_at DESC) per replica for efficient anti-entropy range queries — compare recent writes first during partition recovery.
  • LSM compaction (merging sorted files to reclaim space) adds periodic write amplification (each logical write triggers multiple physical writes) — tune compaction aggressiveness against write throughput requirements.
