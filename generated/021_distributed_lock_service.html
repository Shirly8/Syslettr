Distributed Lock Service

Distributed locks are deceptively hard because clocks drift, processes pause, and networks partition — any of which can cause two clients to believe they hold the same lock simultaneously. Interviewers use this problem to probe whether candidates understand the difference between performance and correctness guarantees in distributed systems.

Interview

Interviewer
We want to build a distributed lock service that multiple services across our fleet can use to coordinate access to shared resources. Where do you start?
You
Before diving in — what's the primary use case, mutual exclusion for critical sections or leader election? What SLA are we targeting on lock acquisition latency? And is correctness the hard constraint, or can we tolerate occasional duplicate work in exchange for higher availability?
Interviewer
Mutual exclusion is the main case — think database row-level operations and rate limiting. Acquisition p99 under 10ms. Correctness is critical; we cannot have two clients holding the same lock.
You
Got it. So strong mutual exclusion (at most one holder at a time) is the hard invariant. I'll target a cluster of 5 lock nodes using Raft consensus (a protocol where a leader node replicates operations to a majority before confirming) to get linearizable (globally ordered, real-time consistent) writes. At p99 10ms we have roughly 4-5ms for network round trips, so nodes need to be co-located regionally. I'll assume tens of thousands of lock acquisitions per second across the fleet and locks held for milliseconds to seconds.

Core Components

Interviewer"How do you prevent a client that crashes while holding a lock from blocking everyone else forever?"
Lease-Based Lock with Expiry
  • WHY: Without a time-bound, a crashed client holds the lock indefinitely and brings the protected resource to a halt.
  • HOW: Every lock is granted as a lease (a time-bounded grant, not permanent ownership) with a TTL (time-to-live, the max duration before auto-release). The client must renew the lease by sending heartbeats before TTL expires; if the lock service doesn't hear from the client, it expires the lease and makes the lock available. I set a default TTL of 10 seconds with renewal every 3 seconds — three missed renewals trigger expiry.
  • TRADEOFF: If the client is alive but experiencing a GC pause (garbage collection stop-the-world freeze) or network partition, the lease expires even though the client thinks it still holds the lock — which is exactly the split-brain (two holders believe they're sole owner) risk we need to handle downstream with fencing tokens.
Interviewer"A client's lease expires due to a GC pause, another client grabs the lock, then the first client wakes up and tries to write. How do you prevent that write from going through?"
Fencing Token
  • WHY: Lease expiry alone doesn't prevent a zombie client (a client that woke up after its lease expired) from corrupting shared state — it just means the lock service no longer recognizes it.
  • HOW: Every time a lock is granted, the lock service issues a monotonically increasing fencing token (an ever-increasing integer, like a generation number). The client passes this token with every operation to the protected resource (e.g., the database). The resource checks: if the incoming token is less than the highest token it has already seen, it rejects the request. Client A gets token 42, its lease expires, client B gets token 43. When zombie client A wakes and sends token 42 to the DB, the DB sees it already processed token 43 and rejects A's write.
  • TRADEOFF: The protected resource must be modified to understand and enforce fencing tokens — you can't retrofit this onto a resource that doesn't check them.
Interviewer"Why not just use a single Redis instance for locks? What does Raft actually give you?"
Raft Consensus Cluster
  • WHY: A single node is a single point of failure; if it crashes mid-grant, you either lose the lock state or clients get stuck.
  • HOW: I run 5 lock nodes using Raft — all writes (acquire, renew, release) go to the elected leader, which replicates the operation to at least 3 of 5 nodes before acknowledging success. This gives linearizable (every operation appears to take effect at a single point in real time) semantics. If the leader dies, a new one is elected within one election timeout (~150-300ms) without losing committed lock state.
  • TRADEOFF: Every acquire now requires a majority quorum (consensus from more than half the nodes) write — that's 2 network round trips minimum, which is why our 10ms SLA requires co-located nodes.
Interviewer"What happens when a client calls acquire and the lock is already held? Do they spin-poll or is there something smarter?"
Lock Acquisition API + Wait Queue
  • WHY: Spin-polling (repeatedly asking 'is it free yet?') at scale floods the lock service with wasted RPCs and degrades p99 latency for everyone.
  • HOW: When a lock is already held, the server registers the caller in an in-memory wait queue (ordered by arrival time or priority) and holds the connection open via long-polling (server keeps connection alive until it has something to return, up to a timeout). When the current holder releases or expires, the server picks the next waiter, grants them the lock, and returns the response on the held connection. This is sometimes called server-side push.
  • TRADEOFF: The lock service must maintain open connections per waiting client — at high concurrency this is a file-descriptor and memory pressure problem that requires careful connection limits per resource.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1The Raft leader becomes a hot spot — every lock acquisition, renewal, and release serializes through a single node, capping throughput as the fleet scales.
Fix: I partition locks across multiple independent Raft clusters, each owning a shard (subset) of the lock namespace — for example, by hashing the resource name to assign it to a cluster. Each cluster has its own leader, so write throughput scales horizontally with the number of clusters. A routing layer maps resource names to the correct cluster. Clients cache this mapping to avoid a lookup on every call.
Tradeoff: Cross-shard locking (a lock that spans two resource namespaces) now requires coordination across clusters — which I'd disallow at the API level or handle with a two-phase locking protocol that significantly increases latency and complexity.
2A single popular resource (e.g., a global rate-limit key) causes thundering herd — when its lock releases, all waiting clients simultaneously storm the leader to re-acquire.
Fix: I add jittered exponential backoff on the client side, so retry attempts are spread over a randomized window rather than all firing at once. Server-side, the wait queue already serializes access — the server grants to one waiter, sends that grant, and only after acknowledgment moves to the next. I also cap the wait queue depth per resource and return a 'try later' error to clients that would exceed it, preventing unbounded memory growth.
Tradeoff: Capping the wait queue means some valid clients get rejected under high contention — they must implement retry logic, which shifts complexity to the caller.
3Clock skew (different system clocks on client and server) makes TTL enforcement unreliable — a client's 'remaining lease time' estimate doesn't match the server's, so it renews too late.
Fix: Clients should never rely on their local clock to estimate remaining lease time. Instead, the server returns the absolute expiry timestamp and the remaining TTL in the grant response. The client uses elapsed-time since grant (monotonic clock, which only moves forward and can't be set backward) rather than wall-clock to pace renewals. Renewals should fire at 1/3 of TTL, not at TTL-ε.
Tradeoff: Monotonic clocks reset on process restart — clients that crash and recover must re-acquire fresh leases rather than attempting to resume.

Reference

API
POST/api/v1/locks/{resource}— Acquire lock on resource; body: {ttl_ms, timeout_ms}; returns {lease_id, fencing_token, expires_at} or 409 if wait queue is full
PUT/api/v1/locks/{resource}/{lease_id}/renew— Renew an existing lease before TTL expiry; returns updated {expires_at} or 404 if lease already expired
DELETE/api/v1/locks/{resource}/{lease_id}— Release lock explicitly; idempotent — returns 200 even if lease already expired
GET/api/v1/locks/{resource}— Inspect current lock state; returns {holder_lease_id, expires_at, queue_depth} for observability and debugging
GET/api/v1/health— Cluster health check; returns Raft leader identity, term, and per-node replication lag
Database & Storage
  • Replicated in-memory state machine backed by WAL (write-ahead log — changes written to disk before applied) on local SSD per Raft node — chosen because lock state is tiny but access must be sub-millisecond and linearizable
  • Schema: leases(lease_id UUID PK, resource_name VARCHAR(512), fencing_token BIGINT, expires_at TIMESTAMP, holder_metadata JSONB)
  • Index: unique index on resource_name where expires_at > now() — enforces at-most-one active lease per resource at the storage level
  • Key tradeoff: storing state only in memory + WAL means recovery after a full cluster restart requires replaying the WAL, which adds startup latency proportional to log length — mitigated by periodic snapshots (checkpoints of full state so replay starts from snapshot, not log beginning)
