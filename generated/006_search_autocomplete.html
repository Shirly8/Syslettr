Search Autocomplete

Search autocomplete looks simple but requires sub-100ms latency at massive read scale while keeping suggestions fresh without blowing up write throughput. Interviewers use it to probe prefix-tree data structures, multi-tier caching strategy, and the tension between consistency and speed.

Interview

Interviewer
We're building the autocomplete for a search bar — like Google's suggestion dropdown. Walk me through how you'd design it from scratch.
You
Before diving in — what's the DAU (daily active users) and average queries per session? Are we targeting a single language or multilingual? And do suggestions need to be personalized per user, or is a global ranking good enough?
Interviewer
500 million DAU, each user types roughly 10 queries a day. English only for now. Global ranking by query frequency is fine — no personalization.
You
That's 5 billion queries per day, roughly 58,000 queries per second (QPS). Each keystroke fires a suggestion request, and average query length is maybe 5 characters, so autocomplete requests are probably 4–5x raw QPS — call it 250,000 reads/sec at peak. Writes are much lower: we're aggregating trending queries, so maybe a few hundred trie (prefix tree — a tree where each node represents a character, enabling fast prefix lookups) updates per second after batch processing. This is extremely read-heavy, so I'll center the design on in-memory caching of hot prefixes and pre-computed suggestion lists.

Core Components

Interviewer"How does the trie actually store and return the top suggestions — walk me through the data model."
Trie Data Structure
  • WHY: A flat key-value store can't efficiently retrieve all queries sharing a prefix — a trie collapses that lookup to O(prefix length) time.
  • HOW: Each node stores a character and a sorted list of the top-K (e.g. top 10) completions with their frequency scores. On a prefix lookup I walk the trie to the terminal node of the prefix, then return that node's pre-cached top-K list directly — no subtree scan at query time. I update those cached lists during a nightly or hourly batch job that re-ranks completions by aggregated click and impression frequency.
  • TRADEOFF: Storing top-K at every node inflates memory — a trie for 1 billion unique queries can reach tens of GBs, so I can't hold the whole thing on one machine.
Interviewer"With 250K reads per second, how do you keep latency under 100ms without hammering the trie servers?"
Multi-Tier Caching
  • WHY: Trie lookups in RAM are fast but 250K QPS concentrated on a small set of hot prefixes will saturate even a fleet of servers — the top 1000 prefixes cover the majority of traffic.
  • HOW: I add two caching layers. First, a CDN (content delivery network — edge servers geographically close to users) caches the top-K suggestions for the most popular prefixes at the edge; cache TTL (time-to-live — how long a cached entry is considered valid) is 60 seconds. Second, each trie server maintains a local in-process LRU cache (drops least-recently-used entries when cache is full) of recent prefix results, absorbing repeated lookups within the same server. Only genuine cache misses reach the trie data structure.
  • TRADEOFF: A 60-second CDN TTL means newly trending queries can be stale for up to a minute at the edge — acceptable for global ranking but would fail a freshness SLA.
Interviewer"How do you keep the suggestion rankings fresh — what's the write pipeline look like?"
Query Frequency Aggregation Pipeline
  • WHY: Without aggregation, every raw search event would try to update the trie in real time, creating a write storm that destroys read performance.
  • HOW: I log every query to a Kafka topic (a distributed write-ahead log — producers write events, consumers read them in order). A stream processor consumes the topic and accumulates counts in a time-windowed in-memory counter, flushing aggregated deltas to a frequency store every 60 seconds. A separate batch job (running hourly) reads from that store, recomputes top-K per prefix, and publishes a new trie snapshot to object storage. Trie servers periodically pull and hot-swap the snapshot with zero downtime.
  • TRADEOFF: Hourly batch means rankings lag reality by up to an hour — fine for general search, problematic for breaking news queries.
Interviewer"You said the trie can hit tens of GBs — how do you scale it across servers?"
Trie Sharding & Replication
  • WHY: A single in-memory trie for billions of queries won't fit on one machine, and one server can't handle 250K QPS anyway.
  • HOW: I shard (split data across multiple machines) the trie by prefix range — server A owns 'a'–'h', server B owns 'i'–'p', server C owns 'q'–'z'. The load balancer (LB) routes each autocomplete request to the correct shard based on the first character of the prefix. Within each shard I run 3–5 read replicas for redundancy and throughput. Reads go to any replica; snapshot updates are pushed to all replicas simultaneously.
  • TRADEOFF: Static prefix-range sharding creates hotspots — prefixes starting with 's' and 'a' are far more popular than 'x', so I may need sub-sharding or weighted partitioning over time.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Prefix hotspots — prefixes like 'th' and 'wh' receive orders of magnitude more traffic than rare prefixes, saturating their trie shard replicas.
Fix: I add a dedicated distributed cache layer (e.g., an in-memory key-value store) in front of the trie shards. All autocomplete requests for any prefix check the cache first. Because the top 1,000 prefixes account for maybe 70% of all traffic, and those fit easily in a few GBs of cache, the hotspot shards see a tiny fraction of their previous QPS. I size the cache with LRU eviction and a TTL of 30–60 seconds to bound staleness.
Tradeoff: This adds a network hop for every cache miss and requires operating another distributed system, increasing operational complexity.
2Trie snapshot rollout causes a thundering herd — all trie servers simultaneously pull the new snapshot from object storage, spiking storage bandwidth and causing brief query degradation.
Fix: I introduce jittered (randomized delay added to spread load) rollout: each trie server waits for a random offset (0–10 minutes) after the snapshot is published before pulling the update. This staggers the load across the storage tier. I also blue-green (run two identical environments, cut traffic over in one step) the snapshot swap within each server — it loads the new trie into a shadow slot and atomically swaps the pointer, so requests never hit a partially-loaded trie.
Tradeoff: Jitter means some servers serve a stale trie for up to 10 extra minutes — acceptable for hourly batch ranking updates.

Reference

API
GET/api/v1/autocomplete?q={prefix}&limit={k}— Returns top-K suggestion objects [{query, score}] for the given prefix; limit defaults to 10
POST/api/v1/queries— Logs a completed query event {query, timestamp, userId} to the aggregation pipeline; returns 202 Accepted
PUT/api/v1/admin/trie/snapshot— Internal: triggers trie servers to pull the latest snapshot from object storage; used by the batch job
DELETE/api/v1/admin/queries/{query}— Removes a query from the trie and blocklist (e.g. hate speech, legal takedowns); propagates on next snapshot
Database & Storage
  • Frequency Store → Apache Cassandra (wide-column, handles high write throughput for per-query count updates with TTL-based expiry of old windows)
  • Schema: query_counts(query TEXT PK, window_start TIMESTAMP PK, count BIGINT, last_updated TIMESTAMP)
  • Index strategy: primary key is (query, window_start) — range scan by window retrieves all recent count buckets for a query in one read; no secondary indexes needed
  • Trie snapshots stored in object storage (e.g., S3-compatible) as serialized binary blobs — cheap, infinitely scalable, but not queryable; trie servers own deserialization
  • Key tradeoff: Cassandra's eventual consistency (replicas may briefly diverge) is fine for frequency counts — a slightly stale count doesn't affect correctness, only ranking freshness
