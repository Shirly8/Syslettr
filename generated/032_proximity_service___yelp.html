Systems Design · Tier 2

Proximity Service / Yelp

The core difficulty is that geographic proximity queries ('find everything within 5km of me') don't map naturally to standard database indexes — latitude/longitude are two-dimensional, so a naive range query on both columns explodes in complexity. Interviewers use this to probe whether candidates understand spatial indexing primitives, read-heavy scaling patterns, and how to serve low-latency location search at global scale.

Interview

Interviewer
We're building a Yelp-like proximity service — users search for businesses near them and see results ranked by distance. Where do you start?
You
Before diving in — what's the DAU (daily active users) target, and what's the max search radius we need to support? And are we indexing businesses globally from day one, or starting with a single region?
Interviewer
100 million DAU, each doing roughly 5 searches per day. Support radii from 500m to 20km. Global coverage, ~500 million businesses total. Search results should return in under 200ms p99.
You
So ~5 billion searches per day — about 58,000 reads per second. Writes are rare; businesses update maybe once a week on average, so that's negligible throughput. The hard problem is sub-200ms geospatial lookups at 58K QPS (queries per second) across 500M records. I'll treat this as an extremely read-heavy system and make geospatial indexing the first-class concern — everything else follows from that.

Core Components

Interviewer"How do you actually index 500 million businesses so a radius search is fast?"
Geospatial Index (Geohash)
  • WHY: A naive SQL range query on latitude AND longitude requires a full table scan — no standard B-tree index handles two-dimensional proximity efficiently at this scale.
  • HOW: I encode each business's coordinates as a geohash (a string where shared prefix = shared geographic area — e.g. 'dp3w' covers ~40km²). I store businesses in a table indexed on geohash prefix. For a radius search I compute the geohash cell of the user's location, find the right precision level for the requested radius, then query that cell plus its 8 neighbors (to avoid edge artifacts where a business just across a cell boundary gets missed).
  • TRADEOFF: Geohash cells are rectangular, not circular — I'll return some businesses outside the true radius and filter them in application code, adding a small post-processing step.
Interviewer"Walk me through the full read path for a single search request."
Business Search Service
  • WHY: The search service needs to orchestrate geohash expansion, cache lookup, DB fallback, and distance filtering — without baking all that logic into the client.
  • HOW: The client hits a load balancer, which routes to a stateless search server. The server computes the geohash cells for the query, checks a Redis cache (key = geohash cell string, value = list of business IDs + coordinates). On a cache hit it returns immediately. On a miss it queries the business DB by geohash prefix, populates the cache with a TTL (time-to-live — expiry time to avoid stale data) of 10 minutes, then filters results in-memory to the exact circle before returning the top-k sorted by distance.
  • TRADEOFF: A 10-minute TTL means newly added businesses can take up to 10 minutes to appear in results — acceptable for this use case.
Interviewer"How do businesses get added or updated, and how does that affect your index?"
Business Write Service
  • WHY: Business metadata (name, hours, rating) and location are written separately from how they're indexed — conflating them creates inconsistency.
  • HOW: A write service accepts business creation and updates via REST. On write, it computes the geohash for the business's coordinates and stores both in the primary business DB. It then publishes an event to a message queue; a consumer invalidates or updates the relevant Redis cache keys. Rating updates (very frequent) only touch the business metadata table — they don't change the geohash index.
  • TRADEOFF: Async cache invalidation via queue means there's a brief window of stale data between a business update and cache eviction.
Interviewer"What database backs the business records, and how is it structured for proximity queries?"
Business Data Store
  • WHY: Choosing the wrong DB or schema here is the single most common mistake — a generic relational DB with no spatial index can't serve 58K QPS at sub-200ms.
  • HOW: I use a relational DB (Postgres with PostGIS extension, or MySQL with a geohash column) as the source of truth. The key index is a composite B-tree on (geohash_prefix, business_id) — this makes prefix scans (all businesses whose geohash starts with 'dp3w') very fast. I also store lat/lng as floats for the post-query Haversine (exact great-circle distance formula) filter. The DB is read-replica scaled: one primary for writes, multiple replicas for search queries.
  • TRADEOFF: Read replicas introduce replication lag (typically <1s) — a newly written business might not appear on replicas immediately.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
158K search QPS is too high for any single DB node — geohash prefix scans on 500M rows under load will exceed CPU and I/O limits.
Fix: I scale reads horizontally with read replicas (copies of the primary DB that serve SELECT queries). The search service round-robins across replicas. For hot geohash cells (dense cities like Manhattan), I also add a Redis cache layer in front — the vast majority of requests for 'restaurants near Times Square' hit identical geohash cells, so cache hit rate is very high and DB load drops dramatically.
Tradeoff: More replicas increase replication lag risk and operational complexity; Redis adds another failure point to manage.
2A single geohash precision doesn't work across all search radii — precision 6 covers ~1.2km² (fine for 500m search), but a 20km search would require scanning thousands of cells.
Fix: I select geohash precision dynamically based on the requested radius: radius ≤ 1km → precision 6 (~1.2km²), radius ≤ 5km → precision 5 (~25km²), radius ≤ 20km → precision 4 (~630km²). At precision 4 I query at most 9 cells to cover the full 20km radius. I always post-filter results with Haversine to trim the rectangular cell overhang down to the actual circle.
Tradeoff: Lower precision means each cache key covers a larger area and holds more businesses, slightly increasing cache memory usage and result-set size to filter.
3Dense urban areas (Manhattan, central Tokyo) create geohash hot spots — a single geohash cell has millions of users querying it simultaneously, overwhelming that cache shard.
Fix: I shard the Redis cache by geohash prefix using consistent hashing (a distribution algorithm where each key maps to one of N nodes; adding/removing nodes only remaps ~1/N keys). Hot-spot cells get replicated across multiple shards, and the search service uses a weighted routing rule to spread load. I also add a local in-process LRU cache (least-recently-used eviction — drops oldest unused entries) on each search server so the top 1000 most queried cells never even hit Redis.
Tradeoff: In-process caches are per-server and not shared — a freshly deployed server starts cold and has elevated Redis load until its local cache warms up.

Reference

API
GET/api/v1/search?lat={lat}&lng={lng}&radius={meters}&category={cat}&limit={n}— Returns top-N businesses within radius sorted by distance; 200ms p99 SLA
GET/api/v1/businesses/{business_id}— Returns full business detail (hours, photos, rating) by ID; cached heavily
POST/api/v1/businesses— Creates a new business listing; computes and stores geohash; returns business_id
PUT/api/v1/businesses/{business_id}— Updates business metadata or location; invalidates relevant geohash cache keys
POST/api/v1/businesses/{business_id}/reviews— Submits a review + rating; triggers async rating aggregation
GET/api/v1/businesses/{business_id}/reviews?page={p}&limit={n}— Paginated review list for a business
Database & Storage
  • Primary DB: PostgreSQL — relational, supports composite indexes on geohash + business_id, ACID (all-or-nothing transactions) for consistent writes
  • Schema: businesses(business_id UUID PK, name VARCHAR(255), geohash VARCHAR(12), lat FLOAT, lng FLOAT, category VARCHAR(64), avg_rating FLOAT, created_at TIMESTAMP)
  • Schema: reviews(review_id UUID PK, business_id UUID FK, user_id UUID, rating TINYINT, body TEXT, created_at TIMESTAMP)
  • Index: CREATE INDEX idx_geohash ON businesses(geohash, business_id) — enables fast prefix scans for all businesses in a geohash cell
  • Index: CREATE INDEX idx_reviews_biz ON reviews(business_id, created_at DESC) — supports paginated review fetch per business
  • Tradeoff: geohash is stored as a varchar and queries use LIKE 'dp3w%' prefix match — this works well on B-tree indexes but is not as clean as PostGIS geometry types; PostGIS would give richer spatial operators at the cost of added operational complexity
