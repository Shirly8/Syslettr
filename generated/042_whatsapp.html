Systems Design · Tier 2

WhatsApp

WhatsApp is deceptively hard because delivering a message exactly once, in order, with sub-second latency to a potentially offline recipient across unreliable mobile networks requires solving distributed state problems most engineers underestimate. Interviewers use it to probe real-time delivery pipelines, presence systems, and the gap between 'sent' and 'delivered' semantics.

Core Components

Interviewer"How do you maintain 400 million concurrent persistent connections without the connection servers becoming a bottleneck?"
Connection Layer (WebSocket Gateway)
  • WHY: Without a dedicated connection tier, stateful connections pollute your business logic servers and make horizontal scaling unpredictable.
  • HOW: I'd run a fleet of stateless-ish gateway servers — each holds open WebSocket connections and maps connection ID to user ID in a local in-memory table plus a shared registry (Redis). Each gateway machine can handle ~100K connections with proper OS tuning (file descriptor limits, epoll), so I need ~4,000 gateway nodes. Gateways don't process business logic — they only route inbound messages upstream and push outbound messages down.
  • TRADEOFF: Adding the registry lookup (Redis round-trip) on every outbound push adds ~1ms latency but lets any backend node find where a user is connected.
Interviewer"What happens when the recipient is offline — how do you guarantee delivery without losing messages?"
Message Delivery & Offline Queue
  • WHY: Without durable offline storage, any message sent to an offline user is lost when the sending connection closes.
  • HOW: When the message service receives a message, it writes it to a durable message store (Cassandra, keyed by recipient user ID and a monotonic sequence number) and attempts real-time push via the gateway. If the registry shows the user is offline or the push ACK (acknowledgment — confirmation the gateway delivered to the client) doesn't come back within 200ms, the message stays in the queue. When the user reconnects, the gateway fetches undelivered messages for that user ordered by sequence ID and drains the queue. On client ACK, we mark delivered.
  • TRADEOFF: Cassandra's eventual consistency means in a partition scenario, two nodes could briefly disagree on delivery state — we accept at-most-once duplicate delivery and handle deduplication client-side.
Interviewer"How do you handle sending a message to a 256-member group without it becoming a synchronous bottleneck?"
Group Messaging Fan-out
  • WHY: Synchronously fanning out to 256 recipients in the request path would make group message latency unbounded and tie up the sending client's request for seconds.
  • HOW: I'd use async fan-out via a message queue (Kafka). The sender's message hits the message service, which writes it once to the group's message store and publishes a single fan-out job to Kafka. A pool of fan-out workers consumes that job, looks up group membership, and enqueues individual delivery tasks per recipient — either pushing immediately if online or writing to their offline queue. This decouples the sender's latency from the number of recipients.
  • TRADEOFF: Recipients may see the message up to a few hundred milliseconds later than the sender's 'sent' confirmation — asynchrony creates a visible delivery window.
Interviewer"How do you know if a user is online, and how do you broadcast that to their contacts?"
Presence System
  • WHY: Without presence, you can't do real-time push — you'd have to fall back to polling, which kills battery and server resources.
  • HOW: Each gateway node maintains a heartbeat (a periodic signal — every 30s — proving the connection is alive) per connected user and writes a TTL-keyed (time-to-live — auto-expires after a timeout) entry to a presence Redis cluster. When a user's status changes, I publish a presence event to Kafka. A presence fan-out service subscribes, looks up the user's contact list, and pushes status updates only to contacts who are themselves online — avoiding wasted work for offline contacts.
  • TRADEOFF: Presence is eventually consistent — a contact could see you as 'online' for up to 30 seconds after you disconnect if the TTL hasn't expired.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single Kafka topic for all message fan-out becomes a sequential bottleneck under 925K messages/sec — consumer lag (the growing backlog of unprocessed events) causes delivery delays.
Fix: I'd partition (split) the Kafka topic by sender user ID — this lets fan-out workers process different users' messages in parallel with no coordination. With 256 partitions, each handles ~3,600 messages/sec, well within a single worker's capacity. Each partition guarantees ordering for a given user, which preserves message sequence without global locks.
Tradeoff: Partition skew — a celebrity user sending at extreme rate will overload their partition; I'd monitor per-partition lag and apply rate limiting at the gateway for any single user.
2The presence Redis cluster becomes a hot-write target at 400M concurrent users each heartbeating every 30 seconds — that's ~13M writes/sec.
Fix: I'd batch presence updates at the gateway layer — each gateway node aggregates heartbeats locally for 5 seconds and writes a single batch update to Redis, collapsing 5 heartbeats into 1 write per user. This reduces Redis write load by 5x. I'd also shard (split) the presence Redis cluster by user ID range across 64 nodes, keeping each node under 200K writes/sec.
Tradeoff: Presence staleness window increases to up to 35 seconds (5s batch + 30s TTL) — acceptable for a chat app but not for a trading platform.
3Cassandra message store write amplification — writing each message to N replicas (copies on different nodes for fault tolerance) means a 925K msg/sec ingestion rate becomes ~2.7M Cassandra writes/sec at replication factor 3.
Fix: I'd use a write-optimized Cassandra configuration with LOCAL_QUORUM consistency (write succeeds when majority of replicas in the same data center confirm — avoids cross-DC latency) and batch writes per user ID using Cassandra's partition key to colocate a user's messages on the same node. This keeps the write path single-hop for the coordinator. I'd also size partitions to cap at 100MB to avoid hotspot tombstones (markers left when deleting old messages).
Tradeoff: LOCAL_QUORUM means a full data-center failure could temporarily block writes — acceptable if we have async cross-DC replication for durability.

Reference

API
POST/api/v1/messages— Send a message — body: {recipient_id, content_encrypted, type}; returns {message_id, timestamp, status:'sent'}
GET/api/v1/messages/{conversation_id}?before={msg_id}&limit=50— Paginated message history for a conversation; returns ordered list of message objects
POST/api/v1/messages/{message_id}/ack— Client confirms delivery or read; body: {status:'delivered'|'read'}; triggers receipt event to sender
GET/api/v1/presence/{user_id}— Returns online status and last-seen timestamp for a user
POST/api/v1/groups— Create group — body: {name, member_ids[]}; returns {group_id}
POST/api/v1/media/upload— Returns a pre-signed URL (a temporary authorized link to blob storage) for direct client-to-storage upload; avoids routing media through app servers
Database & Storage
  • Cassandra — for the message store and offline queue: write-optimized, scales horizontally, time-series access pattern fits LSM-tree (log-structured merge-tree — writes are fast, reads merge sorted files) storage model.
  • Schema: messages(recipient_id UUID PK, bucket INT PK, sent_at TIMEUUID PK, sender_id UUID, content BLOB, status TINYINT) — partitioned by recipient + time bucket so a user's unread messages are one partition scan.
  • MySQL — for user accounts and group metadata: relational, ACID (atomicity/consistency/isolation/durability), low write volume, needs joins between users and groups.
  • Schema: users(user_id BIGINT PK, phone_hash VARCHAR, created_at DATETIME); groups(group_id BIGINT PK, name VARCHAR, created_at DATETIME); group_members(group_id BIGINT PK, user_id BIGINT PK, joined_at DATETIME).
  • Redis — connection registry and presence: userID → {gateway_node_id, TTL}; group member lists cached as Redis Sets for O(1) membership checks.
  • Index strategy: Cassandra queries are always by partition key (recipient_id + bucket) — no secondary indexes needed; MySQL indexes on phone_hash for login lookup and group_id for member retrieval.
  • Key tradeoff: Cassandra's eventual consistency means a message written to replica A might not immediately be readable from replica B — we accept this for throughput and use read-repair (background reconciliation of inconsistent replicas) to heal over time.
