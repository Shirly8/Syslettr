Systems Design · Tier 2

Twitter / Social Graph

Twitter's feed delivery looks simple — post a tweet, followers see it — but the social graph creates a fan-out (broadcasting one write to many recipients) problem that can instantly overwhelm any naive architecture at 500M users. Interviewers use it to probe write amplification, hybrid delivery strategies, and how you reason about hot partitions caused by celebrity accounts.

Interview

Interviewer
We're building a simplified Twitter. Users can post tweets, follow other users, and see a home timeline of tweets from people they follow. Where do you start?
You
Before diving in — what's the scale? Are we talking 100M or 500M daily active users? And is the core hard requirement the home timeline, or do we also need to nail search and trending? Last one: what's the acceptable timeline delivery latency — under a second, or is a few seconds acceptable?
Interviewer
500M daily active users. Home timeline is the core — search is out of scope. Timelines should load in under 500ms for p99 (99th percentile — the slow tail, not the average).
You
Good. Assume average user has 200 followers. At 500M DAU with roughly 100M tweets/day, that's ~1,160 tweet writes/sec. Fan-out (propagating each tweet to follower inboxes) multiplies that by 200 — so ~230K fan-out writes/sec in the naive case. Timeline reads are probably 10x tweet writes, so ~11,600 reads/sec, but each read hits a pre-materialized (pre-computed and stored) feed so it needs to be fast. The celebrity problem — accounts with 10M+ followers — means we can't do pure fan-out on write, so I'll plan a hybrid model. Storage-wise, storing 100M tweets/day at ~1KB each is ~36TB/year — manageable with tiered storage.

Core Components

Interviewer"Walk me through what happens the moment a user hits 'Tweet' — what does your write path look like?"
Tweet Ingestion Service
  • WHY: Without a dedicated ingestion layer, fan-out logic bleeds into the API tier and any spike in tweet volume stalls user-facing requests.
  • HOW: The API server validates the tweet, writes it to the Tweet Store (append-heavy, sharded by tweet ID), then publishes an event to a fan-out queue (a message queue that decouples write from delivery). A pool of Fan-out Workers consumes these events asynchronously and writes tweet IDs into each follower's Timeline Cache (a pre-materialized list of tweet IDs per user stored in memory).
  • TRADEOFF: Async fan-out means followers don't see the tweet instantly — there's a delivery lag of ~100–500ms under normal load.
Interviewer"How do you handle celebrities — accounts with millions of followers? You can't fan-out to 10M inboxes on every tweet."
Timeline Cache & Fan-out Strategy
  • WHY: A celebrity tweeting triggers 10M+ cache writes synchronously — that's a write storm that buries fan-out workers and delays normal users' feeds.
  • HOW: I split on follower count. For regular users (under ~1M followers), I use fan-out on write — tweet IDs are pushed into each follower's Timeline Cache entry immediately. For celebrities, I use fan-out on read — their tweets are NOT pre-pushed; instead, when a user requests their timeline, the Timeline Service fetches the celebrity's recent tweets directly from the Tweet Store and merges (combines) them with the pre-materialized feed on the fly. A Celebrity Registry (a lookup table of high-follower accounts) tells the Timeline Service which accounts need on-read merging.
  • TRADEOFF: Hybrid adds complexity — the merge step on read adds latency, and the Celebrity Registry needs to stay fresh as accounts grow.
Interviewer"How do you store and query the follower/following relationships efficiently?"
Social Graph Store
  • WHY: Every fan-out write needs the full follower list for a user — if that query is slow, fan-out latency blows up.
  • HOW: I store the social graph in a graph-optimized key-value store — each user maps to a sorted set of follower IDs. For the fan-out worker to get all followers of user X, it's a single O(1) key lookup returning a list. I shard (split data across machines) by user ID so no single node owns the full graph. Hot follow lists for celebrities are cached in memory with a short TTL (time to live — how long a cache entry lives before expiry).
  • TRADEOFF: Storing both follower and following sets doubles write cost on follow/unfollow, but makes both directions fast.
Interviewer"A user opens their app — what's the exact read path to serve their home timeline?"
Timeline Read Service
  • WHY: This is the hottest read path in the system — 500M users potentially opening their app at peak hour.
  • HOW: The Timeline Service checks the user's Timeline Cache first — it holds the top ~800 tweet IDs for that user pre-sorted by recency. It hydrates (fetches full tweet data) those IDs from a Tweet Cache (in-memory store of recent tweet content), falling back to the Tweet Store for misses. For users following celebrities, it merges the on-read fetched celebrity tweets with the cached regular-user feed before returning, sorted by timestamp.
  • TRADEOFF: Cache hydration means tweet edits (rare) or deletes require cache invalidation, which adds operational complexity.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A celebrity with 50M followers posts a tweet — fan-out workers queue 50M writes that block all other users' feeds for seconds.
Fix: Skip fan-out on write for celebrity accounts entirely. Fan-out workers check the Celebrity Registry before processing; if the tweet author is a celebrity, they only write to a small 'celebrity tweet' pointer store. On read, the Timeline Service fetches and merges those tweets inline. This caps fan-out writes at ~1M for the largest non-celebrity accounts.
Tradeoff: Read path is slightly slower for users who follow many celebrities — the merge adds ~20–50ms latency on timeline fetch.
2Timeline Cache entries for inactive users (inactive for weeks) consume memory that could serve active users.
Fix: Apply LRU eviction (drops least-recently-used entries when cache is full) on the Timeline Cache, keyed by last-read timestamp. Users who haven't opened the app in 7+ days get their cache entry evicted. On their next login, the Timeline Service reconstructs their feed from the Tweet Store — this 'cold read' path is acceptable since it's infrequent and can tolerate 1–2s latency.
Tradeoff: First load after inactivity is noticeably slower — I'd display a loading state in the UI to cover the cold-read latency.
3The social graph shard (machine) holding follower lists for a mega-popular account becomes a hot partition, receiving all fan-out lookup traffic.
Fix: Replicate (copy) the follower list for the top ~10K high-follower accounts to multiple read replicas (copies of data for read scaling). Fan-out workers randomly select a replica for each lookup, distributing read load. Writes to the follower list still go through the primary, but follows/unfollows are infrequent compared to reads.
Tradeoff: Replication lag (delay between primary and replica) means a new follower may not see the celebrity's next tweet immediately — acceptable eventual consistency.

Reference

API
POST/api/v1/tweets— Creates a tweet; body includes text, media IDs; returns tweet_id and created_at timestamp
GET/api/v1/timelines/home— Returns paginated home feed; query params: cursor (pagination token), count (max 100); returns array of hydrated tweet objects
POST/api/v1/users/{user_id}/follows— Follow a user; adds edge to social graph; returns 200 on success, 409 if already following
DELETE/api/v1/users/{user_id}/follows— Unfollow a user; removes edge from social graph
GET/api/v1/users/{user_id}/followers— Returns paginated follower list; cursor-based pagination; supports count up to 200 per page
GET/api/v1/tweets/{tweet_id}— Fetches a single hydrated tweet by ID; used for cache-miss fallback and direct link resolution
Database & Storage
  • Tweet Store — Wide-column store (e.g., Cassandra-style): append-heavy writes, time-series access patterns, natural sharding by tweet_id
  • Schema: tweets(tweet_id BIGINT PK, author_id BIGINT, content TEXT, media_ids LIST, created_at TIMESTAMP, like_count INT)
  • Schema: users(user_id BIGINT PK, username VARCHAR, follower_count INT, is_celebrity BOOL, created_at TIMESTAMP)
  • Schema: social_graph(follower_id BIGINT PK, followee_id BIGINT PK, created_at TIMESTAMP) — composite PK, stored in graph key-value store with sorted sets per user
  • Schema: timeline_cache(user_id BIGINT PK, tweet_ids LIST, last_updated TIMESTAMP) — in-memory store, 800 tweet IDs max per user
  • Index strategy: tweets indexed by (author_id, created_at DESC) for celebrity on-read fetch; social_graph indexed in both directions (follower→followees and followee→followers) for bidirectional graph traversal
  • Partition key for tweets is tweet_id (time-sortable Snowflake ID — encodes timestamp + machine ID + sequence) to distribute writes across shards while preserving rough time ordering
  • Key tradeoff: Denormalizing like/retweet counts into the tweet row avoids joins but risks stale counts — acceptable since counts are eventually consistent anyway
