Key-Value Store

A key-value store looks trivial until you distribute it — then you're fighting CAP theorem, clock skew, and hot-key amplification simultaneously. Interviewers use it to probe whether you understand replication strategies, consistency models, and how to reason about the tradeoffs between availability and correctness.

Interview

Interviewer
Design a distributed key-value store like DynamoDB or Redis. Where do you start?
You
Before diving in — what's the scale? Millions of keys or billions? And do we need strong consistency (every read sees the latest write) or is eventual consistency acceptable? Also, what's the expected read-to-write ratio?
Interviewer
Billions of keys, roughly 500K reads/sec and 50K writes/sec. Eventual consistency is fine. Keys are up to 256 bytes, values up to 1MB. p99 latency under 10ms for reads.
You
So roughly 10:1 read-to-write ratio — heavily read-biased. I'll lean on caching (keeping hot keys in memory to avoid disk hits) and read replicas. At 500K reads/sec with a 1MB max value size, bandwidth at peak is ~500GB/s theoretical ceiling, but typical payloads will be much smaller — I'll assume 1KB average, so ~500MB/s read throughput. For storage, if we have 1B keys averaging 10KB each, that's ~10TB — I'll shard (split data across multiple machines) across a cluster. Eventual consistency means replicas can lag briefly, which simplifies our write path significantly.

Core Components

Interviewer"How do you decide which node stores which key, and what happens when a node goes down?"
Consistent Hashing Ring
  • WHY: Without a stable mapping from key to node, adding or removing a node forces a full reshuffling of all keys — catastrophically expensive at scale.
  • HOW: I put each node on a hash ring (a circular keyspace from 0 to 2^64 — 1). A key hashes to a position on the ring, and I walk clockwise to find its owner node. To avoid hotspots when nodes have unequal capacity, each physical node gets 150 virtual nodes (vnodes — extra ring positions for the same machine) spread around the ring. When a node fails, only its slice of the ring — typically 1/N of all keys — needs to be re-homed to the next node clockwise.
  • TRADEOFF: Vnodes add coordination overhead and make rebalancing logic more complex to reason about and debug.
Interviewer"With eventual consistency, how do you make sure writes don't get lost when a node crashes mid-write?"
Replication & Quorum Writes
  • WHY: If you write to only one node and it dies before replicating, that data is gone — no durability guarantee.
  • HOW: I use a replication factor of 3 — every key is written to N=3 nodes (the owner plus the next 2 clockwise on the ring). Writes use W=2 quorum (write succeeds when 2 of 3 nodes acknowledge). Reads use R=2 quorum. Since W + R > N (2 + 2 > 3), at least one quorum overlap exists — reads always see at least one node with the latest write. For conflict resolution on diverged replicas, I use last-write-wins with a vector clock (a per-key version counter per node that tracks causality).
  • TRADEOFF: W=2 quorum means a slow replica can tank write latency — you're as fast as your second-fastest node.
Interviewer"What's actually on disk, and how do you make writes fast without sacrificing reads too much?"
Storage Engine (LSM Tree)
  • WHY: A B-tree (balanced tree with in-place updates) does random I/O on writes — at 50K writes/sec, that saturates disk quickly.
  • HOW: I use an LSM tree (Log-Structured Merge-tree — batches writes sequentially). Writes land in a memtable (an in-memory sorted buffer). When the memtable hits ~64MB, it flushes to an immutable SSTable (Sorted String Table — an immutable sorted file on disk). Background compaction merges SSTables to remove deleted/overwritten keys. Each SSTable has a Bloom filter (probabilistic index that rules out key misses with no false negatives) so reads skip files that definitely don't contain the key.
  • TRADEOFF: Compaction uses significant I/O bandwidth and CPU — it competes with live traffic and can cause latency spikes.
Interviewer"How do you hit that p99 latency (99th percentile — the slow tail, not the average) under 10ms for reads?"
Read Cache Layer
  • WHY: At 500K reads/sec, hitting disk for every read is impossible — even SSDs saturate around 100K–500K IOPS and add 0.1–1ms per op before you account for Bloom filter lookups across multiple SSTable levels.
  • HOW: I put an in-memory cache in front of the storage engine on each node — sized to hold the hottest 20% of keys, which handles ~80% of reads (Pareto distribution holds empirically here). I use LRU eviction (drops least-recently-used entries when the cache is full). For ultra-hot keys, I also add a thin read-through cache tier at the coordinator layer so the same key isn't fetching from 3 replicas on every request.
  • TRADEOFF: Local per-node caches mean different nodes may serve stale values for the same key — acceptable under eventual consistency but worth being explicit about.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1Hot keys — a single key (e.g. a celebrity profile) gets hammered by 100K+ reads/sec, overwhelming the 3 nodes responsible for it on the ring.
Fix: I add key-level read replicas beyond the base replication factor — spinning up 10–20 ephemeral read replicas for hot keys detected via a sliding-window counter. The coordinator routes to any of these replicas using weighted random selection. I also add a short TTL (time-to-live — auto-expiry duration) in-process cache at the coordinator so repeat reads for the same hot key within 100ms never even reach storage nodes.
Tradeoff: Ephemeral replicas need to be torn down when the key cools down — the detection and lifecycle logic adds operational complexity.
2Compaction storms — background LSM tree compaction spikes disk I/O and causes p99 latency to spike 10x, violating the 10ms SLA.
Fix: I rate-limit compaction I/O to a ceiling (e.g. 50MB/s per node) using token-bucket throttling (a rate limiter that refills at a fixed rate — bursts are absorbed, sustained overload is blocked). I also stagger compaction schedules across nodes in the same replica group so they don't compact simultaneously. For urgent reads during a compaction event, I add a fast-path that only checks the memtable and the most recent SSTable level before falling back to deeper levels.
Tradeoff: Rate-limiting compaction means SSTables pile up longer — read amplification (number of files checked per read) increases and read latency slowly degrades between compaction windows.
3Network partition causes split-brain — two coordinator nodes disagree on the cluster topology and route writes to different nodes for the same key.
Fix: I use a gossip protocol (peer-to-peer topology propagation — each node tells a few random peers what it knows) for soft state like node health, but for hard state like ring membership changes I require a quorum of nodes to agree via a distributed consensus protocol (a Paxos/Raft-style vote — majority must agree before state changes). Ring topology changes are gated behind this consensus step so no two coordinators can have conflicting views simultaneously.
Tradeoff: Consensus-gated membership changes slow down node additions and removals — you can't add capacity instantly during a traffic spike.

Reference

API
PUT/api/v1/keys/{key}— Upserts value for key; body is raw bytes up to 1MB; returns 200 with vector clock version or 409 on version conflict
GET/api/v1/keys/{key}— Returns value + current vector clock version; optional ?consistency=strong forces quorum read; 404 if key not found
DELETE/api/v1/keys/{key}— Tombstones the key (marks deleted without immediate removal); returns 204; physical deletion happens at next compaction
POST/api/v1/keys/batch— Batch GET up to 100 keys in one request; reduces round-trips for bulk reads; returns map of key → value
GET/api/v1/nodes/health— Returns cluster topology, ring assignments, and per-node latency stats; used by coordinator and ops dashboards
Database & Storage
  • LSM-tree based storage engine (custom or RocksDB-compatible) — sequential write throughput is 10x better than B-tree for write-heavy workloads; matches our 50K writes/sec requirement without random I/O
  • Schema: kv_store(key BYTES(256) PK, value BYTES(1MB), version VECTOR_CLOCK, ttl_epoch INT64, tombstone BOOL, updated_at INT64)
  • Index strategy: keys sorted within each SSTable level enabling binary search; Bloom filter per SSTable eliminates 99%+ of unnecessary disk reads for missing keys
  • Key tradeoff: LSM trees trade read amplification (multiple SSTable levels checked per read) for write performance — compaction tuning is critical to keep read latency within SLA
