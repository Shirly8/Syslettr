Distributed Message Queue

A distributed message queue looks simple — producers write, consumers read — but guaranteeing exactly-once delivery, ordered processing, and durability under broker failure requires careful tradeoffs most engineers haven't thought through. Interviewers use it to test whether you understand replication, consumer group coordination, and the fundamental tension between throughput and consistency.

Interview

Interviewer
We need to build a distributed message queue from scratch — something like Kafka or SQS. Where do you start?
You
Before diving in — what's the throughput target? Millions of messages per day or per second? Do consumers need strict ordering, or is best-effort fine? And what's the durability guarantee — can we lose a message if a broker crashes?
Interviewer
Targeting 1 million messages per second at peak. Ordering matters within a topic partition. No message loss — survive single broker failure. Consumers can be slightly behind but must eventually catch up.
You
Got it. So 1M msg/sec, partitioned ordering (strict order within a partition, not globally), and at-least-once delivery (every message delivered even if a duplicate is possible on failure). Assuming average message size of 1KB, that's ~1GB/sec write throughput. I'll design around a log-structured (append-only, ordered file) storage model with replication factor 3, meaning each partition has 3 copies across brokers. Consumer groups (independent sets of consumers that each read the full topic) handle fan-out without the queue knowing about downstream services.

Core Components

Interviewer"How do you physically store messages on a broker, and how does that let you hit 1GB/sec write throughput?"
Topic Partitions & Log Storage
  • WHY: Random writes to a database at 1GB/sec would immediately saturate disk I/O — sequential log writes are 10–100x faster on spinning and flash disks.
  • HOW: Each topic partition maps to an append-only log file on disk. Producers write only to the tail; the OS page cache (in-memory buffer the OS maintains for recent file reads) absorbs bursts before flushing to disk. I segment logs into fixed-size chunks (e.g., 1GB each) so old segments can be deleted or compacted independently without locking the write path.
  • TRADEOFF: Append-only means you can't update or delete a specific message — you compact (merge old segments, keeping only latest value per key) or expire by time, which adds operational complexity.
Interviewer"You said replication factor 3. Walk me through how writes stay consistent when a broker goes down."
Replication & Leader Election
  • WHY: Without replication, a single broker crash permanently loses all messages in its partitions.
  • HOW: Each partition has one leader broker and two follower brokers. Producers write only to the leader; followers pull and replicate in order. The leader maintains an ISR (in-sync replicas — followers confirmed caught up within a lag threshold). A write is only acknowledged to the producer once all ISR members have it. If the leader crashes, the controller (a designated coordinator broker) elects a new leader from the ISR within seconds.
  • TRADEOFF: Waiting for all ISR members to ack adds write latency (~5–20ms); you can tune acks=1 (only leader confirms) for lower latency but risk losing messages if the leader crashes before followers catch up.
Interviewer"How do multiple consumers divide work, and what happens if one crashes mid-processing?"
Consumer Groups & Offset Tracking
  • WHY: Without coordination, two consumers in the same group would process the same message, and a crash would lose progress.
  • HOW: The group coordinator (a broker responsible for a consumer group's membership) assigns partitions to consumers using a partition assignment protocol — each partition is owned by exactly one consumer in the group at a time. Each consumer commits its offset (the index of the next message to read) to a dedicated internal topic after processing. On crash, the group coordinator detects the missed heartbeat and triggers rebalance (redistributes partitions among surviving consumers), which picks up from the last committed offset.
  • TRADEOFF: Rebalance pauses all consumers in the group for seconds — with many consumers and partitions, rebalance storms can cause visible lag spikes.
Interviewer"How do you actually hit 1GB/sec without overwhelming the brokers on spiky traffic?"
Producer Batching & Backpressure
  • WHY: Sending 1 million tiny 1KB messages individually means 1M syscalls and network round-trips per second — neither the OS nor the network can sustain that.
  • HOW: Producers buffer messages in memory and flush in batches (e.g., 64KB or every 5ms, whichever comes first). This amortizes network overhead across hundreds of messages per round-trip. If a broker's write queue grows too deep, it signals the producer to slow down — this is backpressure (upstream slows to match downstream capacity), preventing OOM on the broker.
  • TRADEOFF: Batching adds up to 5ms of additional latency per message, which is unacceptable for real-time control systems but fine for analytics pipelines.

Architecture

Bottlenecks

Interviewer"What would break in this design at scale?"
1A single hot partition (e.g., all messages keyed on user_id=1) concentrates all writes on one broker, saturating its disk and network while others sit idle.
Fix: I add a partition key salting strategy: append a random suffix (0–N) to the partition key for high-volume keys, distributing their messages across N partitions. The consumer reconciles ordering within each salted sub-partition. Alternatively, I add a dedicated overflow partition for detected hot keys — the router identifies keys exceeding a write rate threshold and redirects them.
Tradeoff: Salting breaks strict per-key ordering across the salt buckets — consumers must do client-side merge sorting if global order for that key matters.
2Consumer rebalancing (partition reassignment when a consumer joins or leaves) pauses the entire consumer group, causing latency spikes under churn.
Fix: I switch to static membership — each consumer gets a persistent member ID (stable identifier across restarts). On restart, the broker holds the partition assignment for a configurable grace period instead of triggering immediate rebalance. This turns most 'crash + restart' events from full group pauses into zero-rebalance recoveries. For rolling deploys, I use incremental cooperative rebalance (a protocol that only reassigns partitions that need to move, not the whole group) to avoid stopping all consumers at once.
Tradeoff: Static membership delays rebalance detection — if a consumer crashes and never comes back, its partitions are frozen until the session timeout expires (typically 30–300 seconds).
3Disk throughput on a single broker becomes a ceiling around 500MB/sec per node — at 1GB/sec total, two brokers are already near capacity with no headroom.
Fix: I scale the broker fleet horizontally by adding more nodes and rebalancing partition leadership across them. Each partition's leader is capped at ~100MB/sec, so 10 brokers with 10 partition leaders each gives 1GB/sec aggregate write bandwidth. I use tiered storage (offload older log segments to object storage like a cheap blob store) to keep local disk holding only the hot, recent data that consumers are actively reading.
Tradeoff: Tiered storage adds read latency for consumers replaying old data — instead of local disk microseconds, they pay object storage round-trip latency (~50–200ms per segment fetch).

Reference

API
POST/api/v1/topics/{topic}/messages— Publishes a batch of messages; body is [{key, value, headers}]; returns {partition, offset} per message
GET/api/v1/topics/{topic}/partitions/{partition}/messages— Polls messages from a given offset; query params: offset, max_bytes, max_wait_ms; returns [{offset, key, value, timestamp}]
POST/api/v1/consumer-groups/{group}/offsets— Commits consumer offsets; body is [{topic, partition, offset}]; idempotent
GET/api/v1/consumer-groups/{group}/offsets— Fetches committed offsets per partition for a consumer group — used on restart to resume from last checkpoint
POST/api/v1/topics— Creates a topic; body is {name, partition_count, replication_factor, retention_ms}
GET/api/v1/topics/{topic}/metadata— Returns partition leaders, ISR membership, and partition count — producers use this to route directly to leader brokers
Database & Storage
  • Log files on local SSD: messages are stored as raw binary segment files on broker disk — not in a relational DB; sequential I/O is the whole point
  • Schema (index file per segment): offset BIGINT PK, position BIGINT, size INT — maps logical offset to byte position in the data file for O(1) seek
  • Offset metadata in embedded KV store (e.g., RocksDB on broker): key=(group_id, topic, partition), value=committed_offset — fast point lookups for consumer resume
  • Topic/broker metadata in distributed coordination store: key=partition_leader_map, value=broker_id — replicated across all brokers so any node can answer metadata requests
  • Index strategy: sparse index (one entry per 4KB of log data) keeps index files small enough to memory-map (load into virtual memory for zero-copy reads) — full sequential scan for gaps
  • Key tradeoff: storing messages as raw files means no secondary indexes, no ad-hoc queries — you can only read by offset range, which forces consumers to pull in order rather than filter server-side
